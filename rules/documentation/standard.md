# ドキュメント記述ルール（標準）

> 標準 v0.1。ULD（ULS Loop Development）の標準ルールで、uld-kit から配布されます。プロジェクト固有の追記・上書きは同じフォルダの `project.md` にあります。

ドキュメントの**書き方**のルールです。何を設計とみなすかは扱いません。ドキュメントの中身（プロダクトが何であるか）は `docs/` が持ち、ここには書きません。ドメインモデル図は設計そのものなので、記法も含めて [model-design](../model-design/standard.md) にあります。

## 基本方針

- ドキュメントは日本語で書く。識別子やコード片は英語の物理名をそのまま使う。
- ドキュメントは簡潔に書く。同じ内容を複数箇所に書かず、重複しそうなときは一方からリンクで参照する。
- 各ドキュメントには説明対象そのもの（ドメイン・アーキテクチャ・テスト戦略など）の説明だけを書く。書き方・運用のルール（記法、図とコードの同期手順、ステータス管理の方針など）は `rules/` 配下にのみ記述し、docs/ 側のドキュメントに混ぜない。
- 実装コードを正とし、コード変更時は対応するドキュメントも同じ変更で同期する。ただしドメインモデル図は設計そのものなので設計先行（図 → 実装の順）で更新する。記法と同期手順は [model-design](../model-design/standard.md) の「ドメインモデル図ルール」にある。
- 用語・指標の定義文書（どのファイルが該当するかは `project.md` に書く）も設計先行で更新する。定義を変更するときは、実装より先に定義のドキュメントを直す。定義の誤解が数値や振る舞いの誤読に直結するため。

## 生き資料とログ資料

リポジトリ内のドキュメントは、どちらかに分類します。曖昧なものを作りません。

| | 生き資料（メンテする） | ログ資料（残すが上書きしない） |
| --- | --- | --- |
| 意味 | 常に「現在の姿」を表す。古くなったら直す義務がある | そのとき何を聞き、何に合意したかの記録。直さない（直したくなったら新しいフローを流す） |
| 置き場 | `docs/` `rules/` `packages/` `apps/` `fixtures/` | `.designs/` |
| 更新 | コード変更・設計変更と同じ変更で同期する | フロー完了時に凍結する |

- **生き資料の正体は、文書よりテストコードです。** 文書としてメンテ義務を負わせるのは、テストでは表現できない少数精鋭（モデル図・ユースケース記述・用語集・OpenAPI・アーキテクチャ文書・ルール）だけに絞ります。メンテ義務のある文書を増やすほど乖離リスクが増えるため、ここは意図的に少なくします。
- ログ資料を後から書き換えないでください。内容を変えたい場合は、新しいフローを流して新しい記録を作ります。

### 仕様の根拠は生き資料とコードだけ

要求を起こす・設計する・実装する・レビューするとき、**「いま何がどう振る舞うか」「何が合意済みか」の根拠にするのは生き資料（`docs/` `rules/` `packages/` `apps/` `fixtures/`）とテストコードだけ**です。`.designs/` の記録には当時の合意しか無く、その後の変更が反映されている保証がありません。読んだ側はそれを正として扱いかねないため、読む範囲を先に絞ります。

- **`.designs/` で読んでよいのは、いま作業している要求（REQ）自身のフォルダだけ。** 書式はテンプレート（[design-records](../design-records/standard.md) の `templates/`）から、進行中の合意は自分の REQ の記録から取る
- **過去の REQ は読まない。** 書き方の見本にも、仕様の確認にも、「同じ内容が合意済みでないか」の重複確認にも使わない。人が明示的に指した記録だけを例外とし、その場合も仕様の根拠は生き資料で確かめる
- **合意済みで未実装の仕様は、生き資料に「（未実装）」で載っていることが唯一の証拠。** 載っていない合意は、次のフローでは「まだ決まっていない」として扱い、ヒアリングで確認する。生き資料に載せる時期は [branch](../branch/standard.md) のフェーズ表（設計フェーズの出口）に従う
- 差分ルートで `request.md` から既存の `REQ-xxx/UC-yy` を参照するのは**経緯を辿るリンク**であり、拡張する仕様の根拠は `docs/usecases/` の受け入れ基準で確認する

### 規約を変更したときの追随

規約（`rules/`）を変更したら、**その規約を参照している成果物を同じ変更で追随させます。** 規約だけを直して参照側を放置すると、古い規約に基づく記述がリポジトリに残り、次に読む人（と AI）がそれを正だと信じます。

- **生き資料** — 追随させる。これは同期の義務があるものの定義そのもの
- **未マージのログ資料** — 追随させる。まだ凍結していない下書きであり、レビュー中の修正と同じ扱い
- **マージ済みのログ資料** — **書き換えない。** そのとき何に合意したかの記録であり、当時の規約に基づいていることに意味がある。規約が変わった事実は、規約側の変更履歴と、次に流すフローの記録が引き受ける

特に見落としやすいのは、ブランチ名・ディレクトリ名・フェーズ名のような**構造を指す語**です。規約の本文からは消えても、それを引用した説明文に残ります。

### 語彙の移行は横断作業として扱う

用語を言い換える変更（数える単位の変更・分類値の改称・語の統一）は、**リポジトリ全体に散った引用を追う横断作業**です。末端のタスクに「ドキュメント同期」として混ぜてはいけません。

- **移行対象のインベントリを作る。** 廃止語と置換後の語を対にした表を持ち、対象ファイルを列挙する。表が無いと、実装する側もレビューする側も「これで全部か」を判定できない
- **残存を機械検出する。** 判定が grep の網羅性に依存すると、レビューが見つけた分だけ直る形になり「残りゼロ」を証明できません。**このクラスの指摘は機械チェックなしには収束しません**
- **独立した移行単位として起こす。** 名前が「同期」でも、実体が語彙移行なら別の単位にする。末端タスクに押し込むと、周ごとに別ファイルが挙がるモグラ叩きになる

## 章立て

- **全体像 → 原則・理由 → 詳細の順に並べる。** 読者はまず地図（構成・俯瞰図・一覧）で全体をつかみ、そのあとに設計原則や理由、個別の詳細を読む。重要な内容でも、全体像より先には置かない。
- **1 セクション 1 主題。** セクションにはその見出しの主題だけを書く。主題と異なる重要な内容（横断的な原則など）を別セクションの冒頭に埋め込まず、独立したセクションに昇格させる。
- **説明は読者に疑問が生まれる位置に置く。** ある記述を読んだ直後に生まれる疑問（例: 俯瞰図に取り込みレコードがないのはなぜか）には、その近くのセクションで答える。
- **帰結・補足は元になる主題のサブセクションにする。** 独立した主題に見えても、ある原則や決定の帰結にすぎない内容は、その親の配下に従属させる。

## ユースケース記述の書き方

`docs/usecases/` のユースケース記述は、システムの現在の振る舞いを利用者目線で表す生き資料です。**実装より先に書き**、振る舞いの変更と同じ変更で同期します。受け入れ基準 ID とテストとのトレースは [acceptance-testing](../acceptance-testing/standard.md) の「仕様トレーサビリティ」、ファイル名の形式は [naming](../naming/standard.md) を参照してください。

- **1 ユースケース = 利用者のゴール 1 つ。** きっかけと目的が別なら別のユースケースに分ける。要求フロー（REQ）の単位を引きずらない
- **名前は現在の振る舞いで付ける。**「〜の是正」「〜対応」のような変更の経緯を名前にしない。経緯は `.designs/`（ログ資料）が引き受ける
- **構成は「概要 → 動作の全体像（シーケンス図）→ 正常系の動き → 異常系・境界の動き」の順。** 概要は、アクター・目的・きっかけ・事前条件・要求の経緯（`.designs/` へのリンク）の表にする
- **フローが背骨。** 番号付きステップの下に、そのステップが保証する受け入れ基準（ID 付き）をぶら下げる。フローから切り離した受け入れ基準の羅列（要求仕様書式）にしない
- **実装の語彙を書かない。** クラス名・API パス・パッケージ名・処理タイミングは設計判断であり、モデル図・OpenAPI・設計メモの領分
- **異常系には理由を添える。** 各異常系の基準の下に、なぜそう振る舞うのかを 1 段落で書く
- **シーケンス図は 1 ユースケースに 1 枚。** 粒度は「利用者 / システム（境界付けられたコンテキスト）/ 外部システム」。アクセス**しない**ことにも表現価値がある（外部システムをライフラインだけ置き、ノートで明示する）。配色は「図の配色（mermaid）」に従う
- **定義は重複させない。** 用語・指標の定義は既存の生き資料（例: `docs/product/`）へリンクする。プロセスの約束（「実装より先に〜を更新する」など）はユースケースではなく `rules/` に書く
- ユースケースを追加・改名したら、`docs/usecases/README.md` の一覧を同じ変更で更新する

## ジャーニー記述の書き方

`docs/journeys/` のジャーニー記述は、複数のユースケースを貫くジャーニーを**ストーリー**として表す生き資料です。ユースケース記述とはフォルダを分けます。ユースケース記述は「利用者のゴール 1 つ」の振る舞いと受け入れ基準を持ち、ジャーニー記述は複数のゴールをまたぐ流れだけを持つためです。テストとのトレースは [acceptance-testing](../acceptance-testing/standard.md) の「E2E テスト」と「仕様トレーサビリティ」を参照してください。

- **1 ジャーニー = ユースケースを貫く流れ 1 本。** 単一ユースケースの正常系は結合テストが覆うため、単一ユースケースだけのジャーニーは書かない
- **ストーリーとして書く。** 誰が、いつ、何をして、何を見て、何を判断するかを利用者の語彙で語る。手順書・チェックリスト・期待値の表にしない。テストが再現する外部システムの活動と期待値はテストコード側が持つ（[acceptance-testing](../acceptance-testing/standard.md) の「E2E テスト」）
- **正常系だけを書く。** 異常系・境界は各ユースケースの受け入れ基準が引き受ける
- **受け入れ基準を定義しない。** 通るユースケースにはリンクで触れ、基準 ID を書かない。太字で定義するのはジャーニーのケース ID（`E2E-01-01`）だけ。1 つのジャーニー（ファイル）は 1 本以上のケースを「ケース」の章に持ち、ストーリーはケースごとに書く
- **構成は「概要 → ケース（ストーリー → ケース ID）」の順。** 概要は、アクター・ゴール・通るユースケース・確かめることの表にする。「ケース」の章にケースごとの節を置き、各ストーリーの末尾に、その流れが成り立つことをケース ID（`E2E-01-01`）として 1 行で置く
- **実装の語彙を書かない。** ユースケース記述と同じ
- ジャーニーを追加・改名したら、`docs/journeys/README.md` の一覧を同じ変更で更新する

## 図の配色（mermaid）

ドメインモデル図以外の mermaid 図（ユースケース記述のシーケンス図など）に適用します。ドメインモデル図の配色は [model-design](../model-design/standard.md) にあります。

閲覧側のテーマ（ライト・ダーク）は制御できないため、**図が自前の配色を完全に持ち、テーマの自動配色に依存しない**ことを原則とします。片方のテーマでしか確認していない図は、もう片方で線や文字が背景に沈みます。

- 線・文字は必ず**不透明な明色の下地**の上に置く。シーケンス図ならメッセージが並ぶ領域を `rect rgb(...)` で囲み、その上に濃色の線・文字を描く
- 半透明（`rgba`）の下地は使わない。ページ背景が透けて、テーマによって下地の実際の色が変わるため
- ページ背景に直接載る要素（アクター・participant の箱、ライフライン、rect の外の線）は `%%{init: {'theme': 'base', 'themeVariables': {...}}}%%` で塗り・枠・文字色をすべて明示し、テーマ任せの色を残さない。init ディレクティブは 1 行で書く（複数行はレンダラーによって解釈が揺れる）
- ページ背景に直接触れる線（ライフラインなど）は中間色にし、白背景・黒背景のどちらでも見える濃さにする
- シーケンス図では `actor`（人型）を使わず `participant`（箱）を使う。人型のラベルは下地のないページ背景に直接描かれ、テーマによって沈むため
- 図を追加・変更したら `mmdc` でダークテーマ（`-t dark -b '#1e1e1e'`）とライトテーマの両方でレンダリングし、すべての線と文字が読めることを確認する。背景色だけを暗くしても閲覧環境のダークテーマは再現できない
- 標準の組: 下地 `rgb(235, 235, 242)`（隣接する区分を分けるときは `rgb(222, 222, 232)` を併用）、下地上の線・文字 `#33334a`、アクター塗り `#e8e8f0`・枠とライフライン `#88889a`・アクター文字 `#1a1a2e`、ノート `#fff5ad` / 文字 `#333333` / 枠 `#aaaa33`

スキル本文の書き方（ツール非依存・規約をプロンプトに書き写さない）は [skills](../skills/standard.md) にあります。
