# レビュールール（標準）

> 標準 v0.1。ULD（ULS Loop Development）の標準ルールで、uld-kit から配布されます。プロジェクト固有の追記・上書きは同じフォルダの `project.md` にあります。

AI レビューと人レビューの共通基準です。レビューする側も、レビューを受ける前のセルフチェックにも、同じこのファイルを使います。

## レビューに渡すもの

AI レビューには余計なものを渡しません。実装側は作業の過程でコンテキストが汚染されますが、レビュー側はレビューだけに集中したコンテキストで見ることで精度が上がります。

- 渡すのは **差分 + 変更対象に対応する `rules/` のトピック + 対象の仕様**だけとする。規約本文をプロンプトに書き写さない（[skills](../skills/standard.md)）。

## 重要度

| 重要度 | 定義 | 扱い |
| --- | --- | --- |
| critical | バグ、アーキテクチャ境界違反、規約違反 | 修正必須。収束条件を満たさない |
| major | 修正すべき問題 | 修正必須。収束条件を満たさない |
| minor | 好みレベルの改善提案 | 任意対応 |

- 指摘には必ずファイルパスと具体的な修正提案を付ける。指摘のみで修正案を示さない指摘は出さない。
- 修正必須でない好みレベルの指摘は minor にする。

## 収束条件

人にレビューを依頼できるのは、次の両方を満たしたときだけです。

1. **機械的チェックの全通過** — 周回中は `npm run check:fast`、コミット前に `npm run check` が通っている（前提条件。使い分けは [testing](../testing/standard.md) の「検証コマンド」）
2. **AI レビューの要修正指摘がゼロ** — critical / major があれば自動修正し、なくなるまで回す

- **minor だけが残った状態は収束。** minor を直すかは任意で、直した場合も再レビューには回さない。再レビュー（新しい周回）を起こすのは、要修正指摘またはチェック失敗を直したときだけ。理由は、AI レビュー 1 周に規約と差分の読み直しで数分かかり、任意対応のために周回を増やすと 1 子タスクの所要時間の大半がレビューになるため（実測では minor のために全タスクが 1 周以上増えた）

収束しない場合は反復上限で打ち切り、残存指摘と修正履歴の要約を添えて人にエスカレーションします。エスカレーションの第一解釈は「タスク分解が甘い」であり、実装の問題として扱う前にタスク分解のやり直しを検討します。

## 観点

規約への適合は、このファイルに書き写さず、**変更対象に対応するトピックの `rules/` を読んで**照合します（引き方は [rules/README.md](../README.md) の「トピック一覧」）。実装なら development、ドメインモデルなら model-design、テストなら testing と acceptance-testing、PR なら pull-request です。ここには規約に還元できない観点だけを置きます。

- プロダクトの目的と原則に沿っているか。
- バグ、エッジケースの見落とし、設計メモや仕様との乖離がないか。
- 判定できないケース（unknown）を黙って既定値に寄せず、明示的に扱っているか。
- 判断の仮定（分類・帰属の根拠など）がドキュメントか reason として残っているか。

## 指摘のルール還元

レビュー指摘は使い捨てにせず、次から同じ指摘が出ないようにルールへ還元します。

- **機械化できる指摘** → lint ルール、`scripts/` の機械チェック、アーキテクチャチェックに落とす。推論に頼るのは機械化できないところだけにする
- **機械化できない指摘** → 該当トピックの `rules/<topic>/project.md` に追記する
- 還元先は**常に `project.md`**。標準（`standard.md`）へ自動では入れない。複数プロジェクトで同じルールが繰り返し採取されたとき、標準のメンテナーが明示的に取り込む
- 還元したルールは**走行中のループには効かせず、次のループから適用**する。走行中に前提が変わると、それまでの検証・承認の前提が崩れ、再現性と計測が濁るため
- 標準と矛盾する追記は、「理由つき上書き」として明示宣言する。宣言なしに矛盾した記述を置かない

この振り分けを怠るとルールが無限に肥大し、AI レビューが遅く・ブレるようになります。
