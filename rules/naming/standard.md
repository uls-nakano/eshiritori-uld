# 命名・言語ルール（標準）

> 標準 v0.1。ULD（ULS Loop Development）の標準ルールで、uld-kit から配布されます。プロジェクト固有の追記・上書きは同じフォルダの `project.md` にあります。

## 言語の使い分け

識別子は英語、人が読む説明は日本語、が原則です。

| 対象 | 言語 |
| --- | --- |
| 変数名・関数名・クラス名・型名・ファイル名 | 英語 |
| コード内のコメント | 日本語 |
| テストの `describe` / `it` / `test` 名 | 日本語 |
| OpenAPI の summary・description・schema/parameter の説明 | 日本語 |
| ドキュメント | 日本語（識別子やコード片は英語の物理名をそのまま使う） |
| DomainError の `detail` | 英語（安定した説明として API と調査で使う） |
| ErrorCode | 英語 snake_case |
| error log の message | 日本語 |

例外: `docs/usecases/` のユースケース記述のファイル名は `UC-{番号}-{日本語のユースケース名}.md`、`docs/journeys/` のジャーニー記述のファイル名は `E2E-{番号}-{日本語のジャーニー名}.md` 、`docs/domain/` の境界ごとの詳細ファイルは `<コードのフォルダ名>-<日本語の境界名>.md` とする。ファイル一覧を見ただけでどのユースケース・ジャーニー・境界かを読み取れるようにするため。

## 識別子の命名

- クラス名と Value Object 名は PascalCase、関数とメソッドは camelCase、定数は UPPER_SNAKE_CASE にする。
- クラス名とファイル名を一致させ、1 ファイルに公開 class は 1 つだけ置く。小さな型定義も、ドメイン概念を持つなら専用ファイルに分ける。
- default export は原則避け、named export を使う。
- 型のみの import は `import type { X } from "..."` を使う。
- private member に `_` prefix は付けない。

## コメント

- class、function、公開 type/interface、重要な定数や変数には、日本語コメントで役割を説明する。
- 情報の書き分けは「**コードには How、テストコードには What、コミットログには Why、コードコメントには Why not**」を原則とする。
- 処理中のコメントは行の内容をなぞらず、コードから読み取れない設計判断（採らなかった選択肢とその理由）を書く。
- Use case など手続き的な処理では、流れの節目に設計判断の根拠コメントを置く。根拠は `docs/` の設計ドキュメントと整合させ、推測で理由を書かない。
- 変数名そのものは英語の識別子を使い、コメントで日本語の意味を補足する。

## ユビキタス言語

- ドメインの用語は `docs/domain/ubiquitous-language.md` を正とする。
- 論理名（日本語）はソースコードの日本語コメントの表現に合わせ、モデル図とコードで用語を揺らさない。
- 論理名には「情報」「データ」「主体」のような抽象語・曖昧語を使わない。何を表すか・何に使うかが伝わる具体的な言葉を選ぶ。
- 新しいドメイン用語を導入するときは、`docs/domain/ubiquitous-language.md` に追加してから使う。
- **ユビキタス言語の語を、別の意味でコードやテストの名前に使わない。** ドメインで意味が決まっている語（例: 「ハーネス」）を、テストの共有土台のような別の概念の名前に流用すると、読み手が用語集の意味で読んでしまう。別の概念には、それが何であるかを表す別の名前を付ける。

スキルの命名は [skills](../skills/standard.md) にあります。
