# PR ルール（標準）

> 標準 v0.1。ULD（ULS Loop Development）の標準ルールで、uld-kit から配布されます。プロジェクト固有の追記・上書きは同じフォルダの `project.md` にあります。

PR の積み方（スタック）、人に見せてよい条件、本文の書き方のルールです。ブランチの命名とコミットは [branch](../branch/standard.md)、レビューする側の基準は [review](../review/standard.md) にあります。

## 実装フェーズの PR — スタックで積む

移行単位（スライス）の実装は、**子タスクごとの PR を積み上げた 1 つのスタック**として作ります。

```text
develop
 └── task/REQ-001-UC-01/1.1.1-<slug>   ← スタックの底。段数と束ね方は設計 PR の tasks.md（索引）で見せる
      └── task/REQ-001-UC-01/1.2.1-<slug>
           └── …
```

- **スタックの底は最初の子タスク**。スタックの段数と束ね方の索引（`tasks.md`）は設計 PR で `develop` に着地済みで、底の PR には含めない。実装中に束ね方が変わった子タスク PR だけが `tasks.md` の更新を含む（[branch](../branch/standard.md) の「フェーズごとの PR と承認」）
- コミット・push・PR 作成・レビューガイドの更新は `node scripts/uld/uld.mjs finish-task` が行う。amend と force push は行わず、同じ head ブランチの PR が既にあれば止まる
- 2 件目以降の子タスクは、直前の子タスクのブランチを base にして積む。2 件目以降の base を `develop` にしない
- **リポジトリ設定「マージ時に head ブランチを自動削除する」（GitHub の `delete_branch_on_merge`）を on にしておく。** GitHub が上位 PR の base を新しい base へ付け替えるのは、下位 PR のマージで head ブランチが削除されたときだけ。この設定が off だと下位をマージしても上位は閉じたブランチを向いたままになり、そのままマージすると成果物が `develop` に届かない。設定は `gh api repos/<owner>/<repo> --jq .delete_branch_on_merge` で確かめられる
- 上の設定が使えない場合だけ、下位 PR をマージする前に `gh pr edit <上位 PR> --base develop` で手で付け替える
- マージ後は `git log origin/develop` と `npm run check:trace` の件数で、成果物が `develop` に着地したことを確かめる

### 読む単位と通す単位を分ける

- **子タスク PR ごとに人のレビューはしない。** 検証はハーネス（機械チェック + AI レビュー）で行う
- **人のレビューはスライス単位で 1 回**。ただし読むときはスタックを下から順にたどり、**タスク 1 件ずつの差分として読む**
- 目的は読ませる量の削減です。スライス全体を 1 つの巨大な差分で見せると読み通せません。ゲートは 1 つのまま、読む単位だけを小さくします
- したがって**人のレビューが終わるまで子タスク PR をマージしない**。先にマージすると差分が畳まれ、タスク単位で読めなくなる
- レビューを通ったらスタックをまとめてマージする

### 制約

- 同一フェーズ内の依存しないタスクも、スタックは線形なので直列に積む。並列実行が必要になったときに別スタックへ分ける（現時点では将来課題）
- スタックは同一リポジトリ内でのみ作れる

## 通す条件

- PR を人に見せてよいのは、機械チェックが全て通り、かつ AI レビューの要修正指摘がゼロになったときだけとする（[review](../review/standard.md) の「収束条件」）。
- domain/application で 100% 未満のカバレッジがある状態ではコミット・プッシュ・マージしない。
- PR 本文は次の「PR 本文はレビュー依頼書として書く」に従う。

## PR 本文はレビュー依頼書として書く

人が PR を読む時点で、機械チェックと AI レビューは通過済みです。本文の役割は作業報告ではなく、**ハーネスが判定できないこと＝人の判断が要る点を先頭に出すこと**です。

本文の骨格は `.github/PULL_REQUEST_TEMPLATE.md` が持ちます（一目で → 要確認 → 差分の読み方 → 畳んだエビデンス）。テンプレートを埋めるときは次に従います。

### 判断は「やったこと → 課題 → 解決」の順で書く

レビュアーが知りたいのは「何を判断したか」であり、判断に至るまでの作業の経過ではありません。判断を書くときは次の 3 つを、この順で分けて書きます。

1. **やったこと** — 何を決め、何をしたか。太字 1 行
2. **課題** — その判断が無いと何が困るか。何が決まっていなかったか
3. **解決** — どう解いたか。捨てた選択肢があればその理由

作業の経過（何を調べ、何を試したか）は書かない。設計メモに残っているので、必要ならリンクで示す。「やったことが列挙されているが、なぜそれが要ったのかが分からない」本文は、レビュアーが判断の妥当性を評価できず、読む負荷だけが残る

### 一目で分かる形にする

- **先頭は表 1 つ（一目で）。** やったこと・課題・解決・触った層・要確認の件数を、各 1 行で並べる。文章の TL;DR にしない。文章は読み通さないと要点が取れないが、表は行ラベルで目が止まる
- **要確認は 1 件 1 チェックボックス。** 太字 1 行の「やったこと」の下に、課題と解決を 1 行ずつの子リストで書く。複数の項目を 1 つのチェックボックスにまとめない。レビュアーは項目を 1 件ずつ確認してチェックを付け、チェック済みが確認の記録として残る
- **各行は 1 行に収める。** 収まらないなら削り、詳細は設計メモへのリンクで示す。本文の文字数はそのまま読む負荷になる
- 要確認の件数は分類ごとに書き、**該当しない分類は 0 と書く**。空欄では「該当なし」と「申告漏れ」を区別できない（unknown case を明示的に扱うのと同じ理由）
- 分類は見出しではなく行頭のタグ（〔仕様〕〔設計〕〔予定外〕〔名前〕）で示し、タグの順に並べる。見出しと「なし」の行は読む量を増やすだけで、件数は表が持っている

### 要確認の 4 分類

4 分類は「人だけが持っていてハーネスが持たない情報」から導いています。意図の持ち主にしか判定できない**仕様の解釈**〔仕様〕、規約に書き切れない構造のセンスが要る**設計の選択**〔設計〕、承認者の権限に属する**予定になかった変更**〔予定外〕、ドメイン知識が要る**新しく付けた名前**〔名前〕。

- 〔予定外〕だけは課題・解決に加えて**確認してほしいこと**を書く。許容するかどうかの判断材料まで書き手が揃える
- 〔名前〕は課題・解決を持たず、**名前 — 意味と選んだ理由**の 1 行で書く。名前の判断は「この語で概念を指してよいか」であり、課題と解決に分けると同じことを 2 度書くことになる
- 要確認に書くのは人の判断が要ることだけ。ハーネスが保証済みの事項（検証結果・カバレッジ・採番・追加した fixture）は本文に再掲せず、`<details>` のエビデンス欄に畳む（消すのではなく、読む対象から外す）
- 採番のない `chore/*` の PR も同じテンプレートを使う

### スタックの底の PR にレビューガイドを置く

人のレビューはスライス単位で 1 回、スタックを下から順に読みます。どの段に注意を配分するかを読み始める前に決められるよう、スタックの底の PR（base が `develop`）の本文にレビューガイドを置きます。

```markdown
## レビューガイド

下から順に読みます。要確認ありは 2 段中 1 段です。

| 順 | PR | タスク | 要確認 |
| --- | --- | --- | --- |
| 1 | #21 | 1.1.1 <要約> | 名前 1 |
| 2 | #22 | 1.2.1 <要約> | なし |
```

- 子タスク PR を積むたびに、底の PR のレビューガイドへ 1 行追記し、冒頭の段数と要確認ありの段数を更新する。要確認の列は分類タグと件数（例: 仕様 1・設計 2）で書き、0 件の分類は省く
- スタックが 1 段だけの間はレビューガイドを置かない。2 段目の子タスク PR を積むときに底の PR へ新設する。単独で完結する `chore/*` の PR にも置かない（1 段の配分表は「一目で」・要確認欄と重複するだけで、注意の配分という目的に寄与しない）
- 「要確認: なし」の段は差分の流し読みでよい。読む量の削減はスタックの目的（読む単位と通す単位を分ける）の続きであり、レビューガイドはその配分表になる

## PR の層と KPI の分母

このプロセスの第一 KPI（人の指摘なしマージ率）の分母は、**人がレビューする単位**に置きます。判定は単純で、**base が `develop` の PR が分母**です。

| PR | 意味 | KPI の分母 |
| --- | --- | --- |
| `scenario/*` → `develop` | シナリオフェーズの承認の単位 | **分母** |
| `design/*` → `develop` | 設計フェーズの承認の単位 | **分母** |
| `task/*` → `develop`（スタックの底） | 実装スタックの人レビューの単位 | **分母** |
| `chore/*` → `develop` | 採番を持たない作業 | **分母** |
| `task/*` → スタックの下位ブランチ | ハーネス内の検証単位 | 含めない |
| `develop` → `main` | リリース PR | 含めない |

上流成果物の PR を分母に含めるのは意図的です。人の指摘なしで通る割合を上流にも広げて測ることで、シナリオフェーズや設計フェーズのハーネスの効き具合が同じ指標で見えます。

**人の修正要求は子タスク PR に付きます。** 分母は底の PR 1 本ですが、指摘の有無を判定するときは**スタック配下の子 PR の指摘も数えます**。これを怠ると「底の PR にコメントが無い＝指摘ゼロ」と誤判定し、KPI が構造的に嘘をつきます。

スタックは `base.ref` を辿って復元できます（各 PR の base は別の PR の head を指し、最後に `develop` へ着く）。ただしマージ先はスタックのマージのたびに付け替わるため、まとまりの判定には作業ブランチ名の採番を使います。ブランチ命名が崩れると分母の判定も指摘の集計も壊れるため、命名は好みではなく計測の一部です（[branch](../branch/standard.md) の「命名」）。

### チャットで受けた修正依頼は PR に人の指摘として書き起こす

人が PR の変更に対する修正を、PR のレビューではなく AI との会話（チャット）で依頼することがあります。**AI は修正に着手する前に、その依頼を PR のレビューとして書き起こします。** KPI は PR に付いた人の指摘の有無で率を出すため、会話の中だけで修正された変更は「人の指摘なし」に数えられ、率が実態より良く見えます。

- **投稿は PR のレビュー（review body）にする。** 会話タブのコメント（issue comment）も取り込みと集計の対象だが、書き起こしはレビューの経路に揃え、読む人がレビューの履歴と差分を同じ場所で突き合わせられるようにする。`gh` なら `gh pr review <PR> --comment --body "..."` を使い、`gh pr comment` は使わない
- **先頭にレビューバッジを付ける。** 依頼の強さに合わせて `[MUST]`（修正必須）/ `[SHOULD]`（推奨）/ `[NITS]`（軽微）を選ぶ。バッジが無いと対応可能な指摘として数えられない
- **本文は依頼者の言葉をできるだけそのまま書き、末尾に「（チャットで受けた指摘の書き起こし）」と添える。** 書き起こすのは人が言ったことだけで、AI 自身の解釈や AI が見つけた別の問題を混ぜない。AI の指摘は AI レビューの経路で PR に付く
- 投稿は AI が操作していても依頼者の GitHub アカウントで行われるため、指摘の帰属は人になる。これは意図どおりで、指摘を出したのは人であり AI は転記しているだけ
- 依頼が既に PR のレビューやレビューコメントとして付いている場合は書き起こさない（二重に数える）
- 依頼が複数の PR（スタック）にまたがるときは、修正が入る PR ごとに書き起こす。指摘はレビュー単位に数え上げられるため、どの子 PR に付いても集計上は同じだが、読む人が差分と指摘を突き合わせられる場所に置く
