# 開発フローの記録ルール（標準）

> 標準 v0.1。ULD（ULS Loop Development）の標準ルールで、uld-kit から配布されます。プロジェクト固有の追記・上書きは同じフォルダの `project.md` にあります。

開発フローの記録（`.designs/`）の構成・採番・凍結と、記録を書き起こすテンプレートのルールです。記録は**ログ資料**で、「そのとき何を聞き、何に合意したか」を残し、後から書き換えません。生き資料とログ資料の区別と、記録を仕様の根拠にしない理由は
[documentation](../documentation/standard.md)
の「生き資料とログ資料」にあります。採番とブランチ・コミット・PR の対応は
[branch](../branch/standard.md) の「採番の鎖」にあります。

## テンプレート

記録は `templates/`
のテンプレートから書き起こします。テンプレートは記録の**書式**を定める規約の一部で、ここに置くのは次の理由からです。

- **規約は `rules/` にのみ存在する。** 記録の書式も規約であり、ログ資料のフォルダに置くと「規約は
  `rules/`」の原則に穴が開く
- **配布対象を `rules/` に閉じる。** `.designs/`
  の記録の実体にはヒアリング内容（顧客名・個人名・社内固有の情報）が入るため他プロジェクトへ配布しない。書式だけを配布するには、記録と別の場所に置く必要がある
- **過去の記録を見本にしない。**
  書式の見本を過去の REQ に求めると、そこに書かれた当時の合意を正として扱う導線になる。見本はテンプレートだけにする

| テンプレート                           | 書き起こす記録                                        | 置き場                                                                         |
| -------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------ |
| [request.md](templates/request.md)     | 元の要望・背景・ルート選択                            | `.designs/REQ-xxx-<要求名>/request.md`                                         |
| [hearing.md](templates/hearing.md)     | ヒアリングシートと確定した回答                        | `.designs/REQ-xxx/hearing.md`（移行単位の追加ヒアリングは `UC-yy/hearing.md`） |
| [plan.md](templates/plan.md)           | シナリオ計画（移行単位への分割・優先順・依存）        | `.designs/REQ-xxx/plan.md`                                                     |
| [usecase.md](templates/usecase.md)     | ユースケース定義（受け入れ基準は EARS）               | `.designs/REQ-xxx/UC-yy/usecase.md`                                            |
| [scenarios.md](templates/scenarios.md) | 合格シナリオ集（正常系 + 異常系）                     | `.designs/REQ-xxx/UC-yy/scenarios.md`                                          |
| [tasks.md](templates/tasks.md)         | 実装スタックの索引（段数と束ね方。設計フェーズで初版、実装フェーズで更新可） | `.designs/REQ-xxx/UC-yy/tasks.md`                                              |
| [review.md](templates/review.md)       | レビュー記録                                          | `.designs/REQ-xxx/UC-yy/reviews/{YYYY-MM-DD}-{対象}.md`                        |

- テンプレートのプレースホルダ（`{...}`
  `___`）は書き起こすときにすべて埋めるか、該当しない旨を書く。空のまま残さない。**例外は
  `hearing.md` の回答欄（`回答: ___`）で、これは人が埋めるまで空のまま PR に出す**（下記）
- テンプレートは Prettier の対象外にする（プレースホルダが整形に馴染まないため）

### ヒアリングの回答

`hearing.md` の「回答:」と「確認事項（Yes / No）」は**人（依頼者・業務側）の判断を書く欄**です。

- AI が書くのは、要望の理解の要約・質問・選択肢と選択の観点・推奨（あれば「推奨: 1。理由: …」と質問側に書く）まで。回答欄は空（`回答: ___`）のままシナリオ PR に出し、人が PR 上で（またはチャットで答えたことを AI が書き起こして）埋める
- **AI の想定で回答欄を埋めない。** 「AI の仮定」「後で確認する」と注記しても同じで、回答が入っていない
  `hearing.md` は未回答として扱う。回答が揃ってシナリオ PR がマージされるまで、設計フェーズに進まない（[branch](../branch/standard.md) の「フェーズごとの PR と承認」）
- **1 つの論点は 1 か所でだけ聞く。** 質問（Q）で聞いたことを確認事項（Yes / No）で言い換えて聞き直さない。2 か所で聞くと回答が食い違い、どちらが正かを決めるために設計の冒頭で確認をやり直すことになる
- **画面の構成を選ばせる質問には、選択肢ごとの HTML のラフを添える。** テキストの図は並べ方の違いが伝わりにくく、質問のやり直しや、チャットと PR で逆の回答が返る原因になる
- **設計に入る前に、回答どうしと、チャットで先に得た回答とを突き合わせる。** 食い違い（PR 上の記入がチャットの回答と逆、Q と確認事項の矛盾、回答によって行き先を失った項目）が見つかったら、設計を書き始めずに確認し、移行単位の追加ヒアリング（`UC-yy/hearing.md`）に書き起こす
- 依頼者がその場にいない自律セッションでは、質問と推奨まで書いて PR を出し、**そこで止まる**。回答が無いまま設計・実装を進めると、仮定が 1 つ違っただけで以降の成果物がすべて手戻りになる。ゲートの実効性は
  `npm run check:branch` が担う（シナリオ成果物が `develop` に無い
  `design/` `task/` ブランチを止める）

## 構成

```text
.designs/
├── events/                      # ループのイベントログ（追記のみ）
├── reviews/                     # 採番に紐づかない作業（chore）へのレビュー記録
└── REQ-001-<要求名>/            # 第1階層 = そもそもの要求
    ├── request.md               #   元の要望・ユーザーストーリー（チケット URL・依頼者・背景）
    ├── hearing.md               #   初回ヒアリングシートと回答（要求全体の把握）
    ├── plan.md                  #   シナリオ計画（移行単位への分割・優先順・依存）
    │
    ├── UC-01-<移行単位名>/      # 第2階層 = 移行単位（この単位でパイプラインが流れる）
    │   ├── hearing.md           #   この単位の追加ヒアリング（あれば）
    │   ├── usecase.md           #   ユースケース定義（受け入れ基準は EARS・NFR 欄あり）
    │   ├── scenarios.md         #   合格シナリオ集（正常系 + 異常系）
    │   ├── mockups/             #   画面ラフ
    │   ├── tasks.md             #   実装スタックの索引（設計 PR で初版、束ね方が変わった子タスク PR で更新）
    │   └── reviews/             #   AI レビュー・人レビュー・差分確認の記録
    └── UC-02-<移行単位名>/      # 後続単位（先行単位の設計・実装と並行して進んでよい）
```

第 1 階層には分割前の共通物だけを置きます。分割後は**移行単位がパイプラインを流れる主役**になるため、ヒアリング〜タスクの一式は移行単位のフォルダに閉じます。

## 採番

| 単位     | 採番                                 | 例              |
| -------- | ------------------------------------ | --------------- |
| 要求     | `REQ-{3桁連番}`                      | `REQ-001`       |
| 移行単位 | REQ 内の連番 `UC-{2桁}`              | `REQ-001/UC-02` |
| シナリオ | 移行単位内の連番 `S-{UC番号}-{連番}` | `S-02-03`       |
| タスク   | `{slice}.{phase}.{連番}`             | `1.2.1`         |

- **採番は不変です。** フォルダ名の `<要求名>` `<移行単位名>`
  は言い換えてよいですが、採番は変えません
- 差分ルート（既存ユースケースの拡張）は**新しい REQ を起こし**、`request.md` から対象の既存
  `REQ-xxx/UC-yy`
  を参照します。ログは不変、変更は新しいフローで、が原則です。参照は経緯を辿るリンクで、拡張する仕様の根拠は
  `docs/usecases/` の受け入れ基準（生き資料）で確認します

## 凍結（クローズ）

移行単位（UC フォルダ）を凍結してよいのは、次の 3 つが揃ったときです。

1. シナリオが結合テストになった
2. モデル・用語集・OpenAPI の差分更新が済んだ
3. `scenarios.md` の「結合テストへの対応」表が埋まり、`tasks.md` の全タスクがチェック済みになった

つまり**クローズ条件 = 生き資料への反映完了**です。凍結後は編集しません。REQ フォルダの凍結は、配下の全移行単位がクローズしたときです。

## 読む範囲

- **過去の REQ を仕様の根拠にしない。**
  読んでよいのは作業中の REQ 自身のフォルダだけで、何がどう振る舞うか・何が合意済みかは生き資料とコードが決めます（[documentation](../documentation/standard.md)
  の「仕様の根拠は生き資料とコードだけ」）
- `.designs/`
  には業務側とのヒアリング内容（顧客名・個人名・社内固有の情報）が入ります。標準を他プロジェクトへ配布する際、記録の実体は含めません（配布するのは
  `rules/` だけ）
- `.designs/` は Prettier / markdownlint の対象外です（自由記述の回答が整形・検査に馴染まないため）
