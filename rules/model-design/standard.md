# モデル設計ルール（標準）

> 標準 v0.1。ULD（ULS Loop Development）の標準ルールで、uld-kit から配布されます。プロジェクト固有の追記・上書きは同じフォルダの `project.md` にあります。

ドメインモデル（Entity・Value Object・Domain Service）の設計ルールと、その表現であるモデル図の記法です。**設計フェーズと実装フェーズの両方で読みます。** 設計の考え方と図の書き方を同じ場所に置くのは、モデル図がドキュメントである前に設計そのものだからです。

## Entity と Value Object

- Entity は ID とライフサイクルを持つものに限定する。
- **識別子を持つことは Entity の条件ではない。** 判断の軸は**ライフサイクル**（生成され、変化し、永続化され、後から同じものとして取り出される）を持つかどうか。まとまりのキーとして識別子を持つだけの導出値は Value Object にする。
- **永続化しない導出値は Value Object にする。** 毎回同じ入力から組み立て直されるものは、同一性ではなく値で比較できる。`equals` を識別子の一致で実装したくなったら、それは Entity のつもりで設計している合図なので、まずライフサイクルの有無を確認する。
- **置き場は「永続化されるか」で決める。** 永続化される判断結果と、集計のたびに組み立てる導出値は、同じ境界に混ぜない。前者は集約の境界へ、後者は集計のモデル群へ置く。
- **境界（`domain/` 直下のフォルダ）の名前は、集約の境界なら集約ルートの名前にする**（`PullRequest` なら `pull-request/`）。集約以外の境界は、何を分類・計算するかを表す名前にする（例: `reviewer-classification/`）。集約に活動や用途の名前を付けると、フォルダ名から集約ルートを辿れなくなるため。境界は Entity / Value Object / Domain Service の種類では分けず、集約と同じ階層に並べる。
- Value Object は不変にし、値の等価性で比較する。
- Value Object の不正値は factory で拒否する。
- 識別子、日時範囲、比率、分類ラベル、信頼度、バージョンなどのドメイン概念は primitive ではなく Value Object として表現する。
- Value Object は `readonly` property を持ち、`equals(other)` で値の等価性を判定できるようにする。
- 共通の値表現は継承よりコンポジションを優先し、重複した検証ロジックを避ける。
- Repository port や use case input では、ドメイン識別子を `string` などの primitive で受け取らず、対応する Value Object を使う。

## Tell, Don't Ask

- ドメインオブジェクトの内部値を getter で取得して外部で業務判定しない。判定はその知識を持つオブジェクト側の関数として実装する。例: `mergedAt === null` を外部で判定せず `PullRequest.isMergedWithin(period)` を用意する。
- 実値の意味（文字列リテラルの値や null が表す状態）はその値を持つオブジェクトだけが知る。外部からは `equals` または `isXxx` 系の判定関数で比較し、`.value === "ai"` のような実値比較を書かない。
- getter の用途は永続化 mapper・DTO 変換などのデータ変換に限る。getter の戻り値を条件式に使いたくなったら、判定関数の追加を先に検討する。

## Domain Service

- Domain Service は Entity/Value Object に自然に置けないルールだけを持つ。
- Domain Service は状態を持たない。判定や計算に必要な情報は引数で受け取り、結果を戻り値で返す。
- Domain Service に private member/property を持たせない。状態が必要になった場合は、Domain Service ではなく Entity/Value Object の責務として設計し直す。
- 状態を持つものは Entity または Value Object として表現する。ライフサイクルや identity があるものは Entity、値の等価性で扱うものは Value Object にする。

## 依存

- Domain から外部ライブラリに依存しない（依存方向の全体は [architecture](../architecture/standard.md)）。
- ドメインモデルの変更は先に図で設計してから実装する（設計先行）。記法は後述の「ドメインモデル図ルール」に従う。

## モデルが CRUD の入れ物にならないための防波堤

画面や API の都合をモデルに持ち込むと、ドメインモデルは属性の入れ物に退化します。これを防ぐ仕組みを 4 つ持ちます。

1. **モデル設計ルール**（このファイル）— 状態遷移はモデルに宿らせる。画面の都合をモデルに持ち込まない
2. **設計版 AI レビュー** — 設計成果物に対するレビュー
3. **シナリオ整合チェック** — 合格シナリオ集の業務ルールがモデル側にロジックを押し込む
4. **実装順序** — domain から実装して単体テストを通す（[development](../development/standard.md) の「実装順序」）

## ドメインモデル図ルール

### 共通

- ドメインモデル図は `docs/domain/` 配下に Mermaid で記述する。ドメインモデルの変更は先に図で設計してから実装し、domain 層のコード変更時は図も同期する。
- ファイル構成: `docs/domain/` 直下には `README.md`（プロジェクト全体の概要 = パッケージ一覧・保存の大原則）と `ubiquitous-language.md` を置き、パッケージごとのフォルダを切る。各パッケージフォルダは `README.md`（パッケージ内の境界一覧と集約俯瞰図）+「1 境界 = 1 ファイル」の詳細ファイルで構成する。詳細ファイルの名前は `<コードのフォルダ名>-<日本語の境界名>.md`（例: `pull-request-プルリクエスト集約.md`）とし、見出しは「日本語の境界名（コードのフォルダ名）」にする。英語のフォルダ名だけでは何の境界かが読み取れず、日本語名だけではコードのどこに当たるかが辿れないため、両方を併記する。
- 境界を追加したら詳細ファイルを新設し、パッケージ README の俯瞰図とリンク一覧に反映する。パッケージを追加したらフォルダと README を新設し、プロジェクト README のパッケージ一覧に反映する。
- 未実装かどうかのステータス（【設計】ラベルなど）は図では管理しない。
- 1 つの巨大な図にせず、集約レベルの俯瞰図と、集約（またはモデル群）ごとの詳細図に分割する。
- 論理名（日本語）と物理名（英語）を併記する。論理名はソースコードの日本語 JSDoc コメントの表現に合わせ、図とコードで用語を揺らさない（図側を先に改名した場合は実装同期時に JSDoc を追従させる）。
- 論理名には「情報」「データ」「主体」のような抽象語・曖昧語を使わない。何を表すか・何に使うかが伝わる具体的な言葉を選ぶ（例: 「レビュー指摘の主体情報」ではなく「レビュー指摘の分類入力」）。
- 関連には多重度を記載する。例: `"1"`、`"0..1"`、`"0..*"`、`"5"`
- 関連線には日本語のラベルで関係の意味を書く。ラベルに半角コロン `:` を含めない（classDiagram のパースエラーになる）。関連は 1 行につき 1 本書く。
- モデル図には**静的な関係**（保持・参照・依存・永続化）だけを書く。データの流れ・処理順序・時系列は図に書かず、本文で説明する。
- 図は `direction TB`（縦方向）で描く。横方向（LR）はページ幅に合わせて縮小され文字が読みにくくなる。
- クラスは種類ごとに `style` 文で色分けする。配色: Entity・Aggregate Root = `fill:#FFE0B2,stroke:#E65100`（オレンジ）、Value Object = `fill:#C8E6C9,stroke:#1B5E20`（緑）、Domain Service = `fill:#BBDEFB,stroke:#0D47A1`（青）、Repository / Application Port = `fill:#E1BEE7,stroke:#4A148C`（紫）、Raw Record = `fill:#ECEFF1,stroke:#546E7A`（グレー）、入力型 = `fill:#FFF9C4,stroke:#F57F17`（黄）。`classDef` / `:::` / `cssClass` は使わない（レンダラーによって効かない）。
- mermaid ブロックの先頭には**テーマ指定行**（`%%{init: ...}%%`）を置く。配色を閲覧環境のテーマに委ねると、ダークテーマでは文字色と関連線が明色に切り替わり、淡色の塗りの上の文字と多重度ラベルが読めなくなる。文字色・線色・多重度ラベルの下地を図側で固定し、ライトテーマ・ダークテーマのどちらでも同じ見え方にする。指定行は全図で同一で、実体は `npm run check:model-trace` のスクリプトが持つ `themeDirective` にある。新しい図にはそれをそのままコピーし、`npm run check:model-trace` で一致を検証する。
- 図を変更したら mermaid ブロックを抽出し、`mmdc` で全図がレンダリングできることを、ライトテーマとダークテーマ（`-t dark`）の両方で検証する。背景色（`-b`）だけを暗くしても閲覧環境のダークテーマは再現できない（手順は `uld-domain-model` スキルを参照）。
- 図だけで完結させず、各要素の責務・不変条件の説明を同じファイルに併記する。ユビキタス言語の表は `docs/domain/ubiquitous-language.md` に集約し、境界のファイルには重複させない。
- **本文に書くのは「役割」と「設計判断（Why not）」だけ。** クラスごとに章を設け（章 `##` の直前に `---` で区切る）、そのクラスが何のためにあるか、どんな設計判断をしたか（採らなかった選択肢とその理由）を書く。関数を持たないクラスも章として記述し、関数がない旨を明記する。
- **関数の What（条件ごとの結果・入力仕様・拒否条件とエラーコード・境界値）は書かない。** What は colocate 単体テストが動く仕様として持つ（トップレベル `describe` = 関数名。[testing](../testing/standard.md) の「テストの記述スタイル」参照）。本文には「仕様は `<クラス名>.test.ts` の `describe` を参照」の導線を置く。同じ仕様を 2 か所に書くと必ず乖離するため。
- **これから作る振る舞いを練る場所は設計メモ（`.designs/`）。** 設計フェーズで条件→結果を列挙したくなったら、モデル docs ではなく設計メモに書き、実装完了とともにテストが仕様の正になる。
- 図に載る公開メソッドと colocate テストの `describe` の対応は `npm run check:model-trace` が検証する（引数なしの getter は除外）。図にあってテストの無い関数（仕様の抜け）と、その逆（図の更新漏れ）を検出する。図にあって実装にまだ無い関数は設計先行（図 → 実装の順）の状態として許容し、実装した時点から describe の有無を検出する。設計フェーズが既存クラスへ関数を足した図をマージしても検証が赤くならないようにするため。

### 俯瞰図

- 俯瞰図はパッケージの README に置き、`classDiagram` でそのパッケージの domain 層の集約・モデル群の間の静的な関係だけを示す。domain 層の外の要素（外部システム・取り込みレコードなど）や Repository port は俯瞰図には書かず、本文や詳細図で扱う。
- 書くのは集約ルートと、境界をまたぐ関係に現れる要素（Domain Service・Value Object・入力型）だけ。属性・操作は書かない。
- クラス名はラベル構文で論理名・物理名を併記し、ステレオタイプに「役割 / 所属境界」を書く。所属境界は日本語の境界名で書く。例: `<<Aggregate Root / プルリクエスト集約>>`
- 関連には多重度と日本語ラベルを書く。

### 詳細図

- 詳細図は境界ごとに `classDiagram` で描き、属性・操作まで記述する。
- クラス名はラベル構文で上段に論理名、下段に物理名を書く。例: `class RepoId["リポジトリ識別子<br>RepoId"]`
- 属性として書くのはモデルが保持する状態（private フィールド）だけとし、「物理名 : 型（論理名）」形式で全角括弧の日本語論理名を付記する。例: `-valueText : string（識別子の実値）`
- getter を含む副作用のない参照・導出は、属性ではなく `()` 付きの関数として書く。例: `+isMerged() boolean（マージ済みか）`。モデルが本質として保持する情報（属性）と、そこから導出される値（関数）を図上で区別できるようにするため
- メソッドは物理名のみで記述する。static factory は Mermaid の classifier `$` を行末に付ける必要があるため、日本語は付記しない。例: `+create(value) RepoId$`
- 各クラスにステレオタイプで DDD 上の役割を明示する。例: `<<Entity / Aggregate Root>>`、`<<Value Object>>`、`<<Domain Service>>`、`<<Repository Port>>`、`<<入力型>>`（Domain Service の引数専用で同一性も検証も持たない型）
- 関連には多重度付きで意味を書く。例: `RepoFlowMetrics "1" *-- "1" RepoId : 対象リポジトリ`、`PullRequestRepository ..> "0..*" PullRequest : 判断結果を永続化・復元`
- 他の境界のクラスを参照する場合は、クラス名とステレオタイプだけの簡略表記にし、属性・操作は所属境界の詳細図にだけ書く。
