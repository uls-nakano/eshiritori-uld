# ブランチ・コミットルール（標準）

> 標準 v0.1。ULD（ULS Loop Development）の標準ルールで、uld-kit から配布されます。プロジェクト固有の追記・上書きは同じフォルダの `project.md` にあります。

ブランチの構成・命名・採番の鎖と、コミットのルールです。PR の積み方・通す条件・本文の書き方は [pull-request](../pull-request/standard.md) にあります。

## ブランチ構成

- 本番ブランチ（既定は `main`）は本番投入可能な状態を保つ。
- 統合ブランチ（既定は `develop`）を integration branch とし、**マージ先は常に `develop`** とする。
- 両者の名前は `uld.config.json` の `branches.protected`（本番）/ `branches.integration`（統合）で変えられる。以降は既定値の名前で書く。
- `main` / `develop` へ直接プッシュしない。`main` / `develop` 上に未コミットの変更がある状態は `npm run check:branch` が機械検出する。

## フェーズごとの PR と承認

各フェーズの出口で PR を作り、**人の承認を得てから次のフェーズへ進みます。**

| フェーズ | ブランチ | 出す成果物 | 人の承認 |
| --- | --- | --- | --- |
| シナリオ | `scenario/REQ-{番号}-<slug>` | `request.md` `hearing.md` `plan.md` `usecase.md` `scenarios.md` | **要る**（承認してマージ） |
| 設計 | `design/REQ-{番号}-UC-{番号}-<slug>` | ドメインモデル図・画面・OpenAPI・ERD・ユースケース記述とジャーニー記述の最終形（新しい基準は「（未実装）」、置き換える基準は「（廃止予定）」を付ける。[acceptance-testing](../acceptance-testing/standard.md) の「仕様トレーサビリティ」）、`tasks.md`（実装スタックの段数と束ね方の索引） | **要る**（承認してマージ） |
| 実装 | `task/{採番}/{タスクID}-<slug>` | コード（束ね方が変わったときは `tasks.md` の更新） | **要る**（スタックをまとめてレビューし、まとめてマージ） |

**人が見るのは、決めるべきこと（仕様・構造）と、結果（コード）です。作業の段取りは見ません。** 例外は実装スタックの段数と束ね方で、これは人が後で読む PR の数と順そのものなので、設計 PR の索引（`tasks.md`）として見せます。

- **フェーズの出口の PR を出したら、そこで止まる。** 次のフェーズのブランチを切らない・成果物を書き始めない。承認は「PR が `develop` にマージされたこと」で、チャットの了解や AI 自身の判断では代えられない。「自律的に進める」「確認を求めない」という運用上の指示は作業の段取りに対するもので、この承認ゲートを免除しない。ゲートを飛ばすと、シナリオ → 設計 → 実装が 1 本のスタックに積まれ、人がヒアリングに答える前に実装が終わってしまう（仮定が 1 つ違えば全段が手戻りになる）
- **止まるのはフェーズの出口だけで、フェーズの中では止まらない。** 実装フェーズは索引（`tasks.md`）の全段を続けて流し、子タスクの切れ目で人に確認を求めない。人のレビューはスライス単位で 1 回（[pull-request](../pull-request/standard.md) の「読む単位と通す単位を分ける」）なので、段の切れ目で待っても人が決められることは無く、待ち時間だけが増える（実測で、切れ目に確認を 1 回挟んだ段は次の起動まで 258 分空き、確認を挟まなかった段は 4〜10 分で繋がった）。フェーズの中で止まってよいのは、ハーネスが人の判断を求めて止まったとき（子タスクの規模超過・観測点なし・反復上限でのエスカレーション）と、受け入れ基準や契約を変える必要が出たときに限る
- **ヒアリングの回答は人が書く。** AI が書けるのは質問・選択肢・推奨と、その根拠まで。回答欄を AI の想定で埋めて次へ進まない（書式は [design-records](../design-records/standard.md) の「ヒアリングの回答」）。依頼者が不在なら、回答欄を空のままシナリオ PR を出して止まる
- **設計・実装のブランチは、前のフェーズの成果物が `develop` に着地していることを前提にする。** `design/REQ-xxx-UC-yy-*` はその REQ の `request.md` `hearing.md` `plan.md` と UC の `usecase.md` `scenarios.md` が、`task/REQ-xxx-UC-yy/*` はさらに設計フェーズの受け入れ基準（`docs/usecases` の ID 定義）が `origin/develop` に存在しなければならない。`npm run check:branch` が機械検出する（着地前に切ったブランチでは失敗する）
- **シナリオフェーズの出口をマージで確定させる**のは、業務側と閉じたことを確定させるため。口約束のまま設計へ進むと、以降のすべてが合意していない前提の上に積み上がる
- **設計フェーズの出口をマージで確定させる**のは、成果物がすべて**生き資料**（現在の姿）だから。マージせずに長く開いておくと `develop` 上の「現在の姿」が古いままになる。移行単位は並行して流れるため、後続の単位が先行単位のモデルや OpenAPI を参照できなくなる
- **タスク分割のうち人が見るのは段数と束ね方だけで、詳細には承認を置かない。** 索引（`tasks.md`。書式は [design-records](../design-records/standard.md) のテンプレート）を設計 PR に含め、要確認〔設計〕1 件として「何段のスタックをどう積むか」を示す。人はここで自分が後で読む PR の数と順を決められる（9 段は多い、この 2 段は束ねてよい、など）。各タスクの実装方針・テスト項目・完了条件は実装フェーズの設計メモが持ち、その良し悪しは**ハーネスが判定する** — 分割が甘ければ実装が収束せず、エスカレーションで「分解が甘い」として返ってくる。実装中に束ね方が変わったら、その子タスク PR で `tasks.md` を更新し、要確認〔予定外〕に載せる（索引は設計フェーズで初版を出し、実装フェーズで更新してよいログ資料の例外）
- **ただし子タスクの規模には上限を置く。** 実装ループの設計工程で影響ファイルが 15 を超えた子タスクは、実装に入る前に分割案を人に提示する。分割せずに進めるのは人がそれを承認したときだけで、承認はイベントログの `design_completed` に `oversizeDecision: "approved_by_user"` として残す（`node scripts/uld/uld.mjs record-loop-event` が承認の無い上限超えの記録を拒む）。上限を置くのは、規模の判断を AI の推論に任せると 1 タスクで 40 ファイル規模の変更が人の判断を経ずに進み、レビューで読み切れない差分になるため。15 は、これまでの子タスクの実績（イベントログ上の最大は 8 件）に余裕を持たせ、1 回のレビューで読み切れる量として置いた値で、実績が溜まったら見直す
- **子タスクの単位は「1 観測点」に置く。1 クラス 1 タスクは実装の順序であって、ループと PR の単位ではない。** 観測点とは、人がその変更の正しさを判定できるテストのこと。fixture を読めば規則が正しいか分かる domain の単体テスト、受け入れ基準 ID を持つ結合テスト・story・E2E がそれにあたる。モックの往復を確かめるだけのテスト（route・Server Action・取得用の lib など受け渡しだけの層の単体テスト）は観測点ではない
  - **判断の要るロジックを持つ層は単独のタスクにする。** その層の単体テストが観測点になり、レビューは規則の妥当性に集中できる。実装は domain 側から末端で始める意図（[development](../development/standard.md) の「実装順序」）はここで守る
  - **受け渡しだけの層は、その先にある観測点まで 1 タスクに束ねる。** route と結合テスト、取得用の lib と表示 component の story、Server Action と画面組み込み、のように。タスク内の実装順序は設計メモで末端から並べ、TDD の進め方は変えない
  - **画面は「表示」と「組み込み」で 2 段に分ける。** 表示 component とその story を 1 段、ページの配線・入口（既存画面からのリンク）・取得の組み立てを次の 1 段にする。束ねると、1 段の中に層の違う判断（表示の見せ方・状態の union・ページの配線・既存画面への影響）が同居し、レビューが周ごとに別の層の要修正を拾って修正ループが伸びる。実測で、表示と組み込みを 1 段に束ねた段だけが修正 5 周（上限）・82 分に達し、同じスライスの他の 4 段は 0〜2 周・22〜99 分だった。その 5 周で拾われたのは、死んだリンク・story の fixture が契約の並び順に反する・観測点が緩い・play コメントにログ資料の ID が混入・型ガードの漏れ、と毎回違う層の指摘だった
  - **E2E は束ねずに別のタスクにする。** 画面組み込みの段は配線が集まって規模が上限に触れやすく、E2E は観測点として独立している
  - **生き資料の同期を独立したタスクにしない。** ユースケース記述・モデル図・アーキテクチャ文書・用語集は、それを古くする変更を入れた段が同じ変更で直す（[documentation](../documentation/standard.md) の「コード変更時は対応するドキュメントも同じ変更で同期する」）。まとめて直す「ドキュメント同期」の段を最後に置かない。置くと、(1) その段は観測点を持たないので単独の PR では正しさを判定できず、実装ループの停止条件に当たる、(2) 生き資料が古い状態で 1 段ぶんの PR をまたぎ、その間にスタックを読む人が古い記述を正だと信じる、(3) どの段で何が古くなったかを後から突き合わせる作業が増える。乖離が段をまたいで残るのは、段の中で直し忘れた合図であり、まとめ直す場所を用意して解く問題ではない。例外は**語彙の移行**（廃止語を全体で置き換える横断作業）で、これは同期ではなく別の移行単位として起こす（[documentation](../documentation/standard.md) の「語彙の移行は横断作業として扱う」）
  - 束ねるのは、観測点の無いタスクを単独の PR にすると、レビュアーが後続の PR まで読まなければ正しさを判断できず、PR の数だけが増えるため。加えて 1 ループには固定費（`check:fast` と AI レビューで数分〜十数分）が掛かり、単独では何も観測できない差分に固定費とレビューを払うことになる。ErrorCode → GitHub 応答の分類 → route → 結合テスト、のような 4 段を単独の PR に分けた実績では、人のレビューは結合テストの段まで読まないと最初の 3 段の正しさを判断できなかった
  - 束ねた結果が上限 15 に近づいたら、束ね方ではなく規模の側を上限の規約で扱う（分割案を人に提示する）。上限は束ねの安全弁であり、束ねの基準にファイル数は使わない

### どのフェーズでも、マージするものは単体でリポジトリを緑に保つ

**設計フェーズがマージしてよいのは、それだけで `npm run check` が通る成果物だけです。**

ドメインモデル図・画面・ERD の図は、マージしてもコードに影響しません。しかし**生成の入力になるファイル**は違います。DB スキーマ定義（ORM の client 型を生成する）や OpenAPI specification（API 型・client・server contract を生成する）は、単独でマージすると生成物と利用側が追随せず typecheck や契約チェックが落ちます。

これらは**設計であると同時にコード**です。設計フェーズで先にマージすると、マイグレーションと読み書きコードが揃う実装フェーズの後半まで、**リポジトリが赤いまま**になります。

- 生成の入力になるファイルは、**生成物と利用側の追随を同じ変更に含める**
- 同じ変更に含められないなら、**設計フェーズではマージしない**。設計としての内容はドメインモデル図や ERD の図で表し、生成の入力になるファイルは実装フェーズで変える
- 赤いベースラインは**後続のすべての子タスクに相続されます**。実装ループの収束条件は `npm run check` の全通過なので、どの子タスクも自力では緑にできず、反復上限まで回ってエスカレーションします

## 命名

```text
シナリオ: scenario/REQ-001-<slug>
設計:     design/REQ-001-UC-01-<slug>
子タスク: task/REQ-001-UC-01/1.2.1-<slug>
```

- **親子の紐付けは採番だけに掛ける。** 採番（`REQ-001-UC-01`、タスク ID `1.2.1`）は不変だが、`<slug>` はヒアリングの結果で言い換わる。slug を親子の一致条件にすると、言い換えた瞬間にトレーサビリティが黙って外れる。
- 親の導出規則: `task/{採番}/...` に対して、同じ採番を持つ `design/{採番}-*` と `scenario/REQ-{番号}-*` をたどる。
- **`task/REQ-001-UC-01` というブランチ自体を作らない。** git の ref は階層なので、作ると配下に子ブランチを切れなくなる。
- 採番は `.designs/` の階層に対応する（`REQ-001-<要求名>/UC-01-<移行単位名>/`）。
- **ブランチ命名は好みではなく計測の一部。** 人がレビューする単位と KPI の分母はブランチの base と作業ブランチ名から判定する（[pull-request](../pull-request/standard.md) の「PR の層と KPI の分母」）。命名が崩れると分母の判定も指摘の集計も壊れる。

### 採番を持たない作業

土台整備・小改修・依存更新など、`.designs/` の要求に紐づかない作業は `chore/<slug>` を使う。マージ先は `develop` で、PR の扱いは他のフェーズの PR と同じ（KPI の分母に入る）。

- **利用者から見える振る舞いの追加・変更は chore にしない。** 受け入れ基準（`docs/usecases/` の `UC-xx 要件 n`）を新設・変更する作業は、既存ユースケースの拡張であり「採番の鎖」の差分ルートにあたる。バグの指摘や小さな要望として届いても、新しい REQ を起こしてヒアリングで範囲を決めてから `task/` で実装する。chore で進めると、何をどこまで作るかを AI が決めたまま実装が始まり、人が範囲を判断する機会（ヒアリング）が抜ける
- 判定は `npm run check:branch` が機械的に行う。`chore/` ブランチで `docs/usecases/` に受け入れ基準の定義が増えていれば失敗する
- 受け入れ基準を増やさない範囲での不具合修正（既存の基準を満たすように直す）や、開発者向けの運用機能（[docs/usecases/README.md](../../docs/usecases/README.md) がユースケースとして書かないと定めているもの）は chore でよい

## 採番の鎖

要望からテストまでを 1 本の鎖でつなぎ、機械チェック可能にします。

```text
REQ-001（要求）
  → REQ-001/UC-01（移行単位）
    → シナリオ ID（S-01-03・ログ資料内）
      → タスク ID（{slice}.{phase}.{連番} = 1.2.1）
        → コミット（[1.2.1] …）
          → 子タスク PR（スタックの 1 段）
            → テスト名（受け入れ基準 ID = UC-01 要件 6）
```

- シナリオ ID は移行単位内の連番、タスク ID は `{slice}.{phase}.{連番}`。
- シナリオ ID はログ資料（`.designs/` の scenarios.md）の中だけで使い、テスト名には入れない。シナリオとテストの対応は scenarios.md の「結合テストへの対応」表が記録し、テスト名は生き資料の受け入れ基準 ID でつなぐ（[acceptance-testing](../acceptance-testing/standard.md) の「仕様トレーサビリティ」）。
- 差分ルート（既存ユースケースの拡張）は新しい REQ を起こし、`request.md` から対象の既存 `REQ-xxx/UC-yy` を参照する。この参照は経緯を辿るリンクで、拡張する仕様の根拠は `docs/usecases/` の受け入れ基準（生き資料）で確認する（[documentation](../documentation/standard.md) の「仕様の根拠は生き資料とコードだけ」）。

## コミット

- 子タスクは 1 タスク 1 コミットを原則とし、**コミットメッセージの先頭にタスク ID を付ける**。書式: `[1.2.1] <変更内容の要約>`
- タスク ID を持たない作業（シナリオ・設計フェーズの成果物、土台整備）はタスク ID を省略し、`<type>(<scope>): <変更内容の要約>` の形式にしてよい。
- 変更したファイルだけを明示的に `git add` する。`git add .` は使わない。
- コミットログには Why を書く（[naming](../naming/standard.md) の情報の書き分け）。
- コミット前とプッシュ前に `npm run check` を実行する（[testing](../testing/standard.md) の「検証コマンド」）。
