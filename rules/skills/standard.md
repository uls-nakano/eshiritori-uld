# スキルルール（標準）

> 標準 v0.2。ULD（ULS Loop Development）の標準ルールで、uld-kit から配布されます。プロジェクト固有の追記・上書きは同じフォルダの `project.md` にあります。

スキル（各リポジトリの `.claude/skills/*/SKILL.md`。標準の部品は uld-kit の `skills/` が原本）の命名と本文の書き方のルールです。スキル本文の日本語・章立てなど文書一般のルールは [documentation](../documentation/standard.md) を参照してください。

## 命名

標準プロセス（**ULD = ULS Loop Development**）の部品となるスキルは `uld-` を接頭辞にします（`uld-impl` `uld-impl-fast` `uld-task-design` `uld-implement` `uld-review` `uld-rules` `uld-domain-model` `uld-init`）。スキル一覧で標準の部品がひと固まりに見え、補完で全部引けるようにするためです。原本は uld-kit の `skills/` にあり、`npx --yes github:uls-nakano/uld-kit#<tag> init` が各リポジトリの `.claude/skills/` へコピーします。**コピーされたスキルはリポジトリ側で直接編集しません**（食い違いは `node scripts/uld/uld.mjs check-kit` が検出します）。変更は uld-kit 側で行い、版上げで配り直します。

- フェーズ名を先に置き、レビューは後ろに付ける（`uld-scenario` と `uld-scenario-review` のように、各フェーズの本体とレビューが一覧で隣り合うため）
- **プロジェクト固有のスキルは `uld` の名前空間を使わない。** 各リポジトリの `.claude/skills/` に置きます。`uld` に入れるのは標準の部品として他プロジェクトへ配布できるものだけです。例えば、特定リポジトリのドキュメント記法に依存するスキルは `uld` に入れません
- 他所から流用したスキルを改造して標準の部品として取り込む場合も、名前は `uld-` 系に付け替えます。出自の原本と実体を取り違えないようにするためです

### 工程スキルと実行系スキルを名前で分ける

フェーズを工程に割ったときは、**工程スキル（手順の実体・ツール非依存）と実行系スキル（工程の起動と待ち合わせ・ツール固有）の両方に名前が要ります**。実行系だけを差し替えて速度や並列度を変えられるようにするためで、この分離は後述の「本文はツールに依存させない」と対応します。

- 工程スキルはその工程が何をするかで名付ける（例: `uld-task-design` / `uld-implement` / `uld-review`）
- 実行系スキルはフェーズ名を基点に、方式が分かる語を足す（例: `uld-impl` = ワークフロー方式、`uld-impl-fast` = 工程スキルをサブエージェントで束ねる方式）
- **同じフェーズに実行系が複数あってよい。** 速度と品質の釣り合いが違う方式を並べて比較できる状態を保ちます

## 1 フェーズ = 1 セッション

シナリオ・設計・実装の各フェーズは、**別々のセッション（またはワークフローの別々の実行）で回します**。1 セッションの中でフェーズをまたいで続けません。

- **承認ゲートが構造になる。** フェーズの出口は「PR を出して止まる」で、人の回答とマージを待つ（[branch](../branch/standard.md) の「フェーズごとの PR と承認」）。同じセッションで続けると、止まることがモデルの自制に依存し、「自律的に進める」という運用指示に押されてゲートを飛ばす。セッションが終われば、次のフェーズは人が起動するしかない
- **コンテキストが肥大しない。** フェーズをまたいだ文脈はセッションの記憶ではなくリポジトリの状態（`.designs/` と生き資料）だけで受け渡す（下の「本文はツールに依存させない」）。前のフェーズの調査や議論を抱えたまま次に進むと、セッションが重くなり、判断が前のフェーズの仮定に引きずられる
- **工程ごとにモデルとエフォートを選べる。** 設計メモ（計画）と実装を分けている狙いの 1 つは、精密なメモを前提にすれば実装は軽いモデルでも回せること。セッション境界と工程エージェントの境界がそれを可能にする

実装フェーズの入口は、前のフェーズの成果物が `develop` に着地していることを確かめてから起動します（`npm run check:branch`）。

### 実行系の既定

同じフェーズに実行系が複数あるとき、**既定はワークフロー方式**（`uld-impl`）です。各工程を新しいコンテキストのエージェントが担い、工程間の受け渡しを設計メモのファイルで行う方式で、メインセッションは起動と結果の受け取りだけを持ちます。ワークフロー script（`uld-impl.js`）も uld-kit が原本で、`npx --yes github:uls-nakano/uld-kit#<tag> init` が各リポジトリの `.claude/workflows/` にコピーします。

工程スキルをメインセッションで束ねる方式（`uld-impl-fast`）は、設計と実装の調査を使い回せるぶん 1 タスク目は速いものの、子タスクを続けて回すとメインセッションの文脈が肥大し、実装の細かな逸脱が増えてレビューの周回が増えます（実測: ワークフロー方式は半数が 0 周で収束、束ねる方式は全件が 1 周以上）。影響ファイルが数件の chore を 1 件だけ回すときに限って使います。どちらもイベントログに `runner` を記録し、KPI で比較できる状態を保ちます。

## 本文はツールに依存させない

スキルは**手順の記述であり、特定の AI ツールに依存させません**。実行系（サブエージェントの起動・並列実行・工程間の待ち合わせ）だけがツール固有で、そこは実行系スキルまたはワークフロー側に閉じ込めます。

スキル本文に次を**書きません**。

- 特定ツールの機能名（`Workflow`、`devin_session_create`、サブエージェント、並列実行など）
- 特定ツールのブランチ命名（`devin/{timestamp}-*` など）
- セッション間通知の手段（API 通知、curl コマンドなど）

代わりに次の抽象で書きます。

- 「ヒアリングシートを**提示し、回答を待つ**」（提示先がチャットか PR コメントかは実行系が決める）
- 「前工程の成果物を `.designs/REQ-xxx/UC-yy/` から**読む**」（前のセッションの記憶に頼らない）
- 「完了条件: {ファイル} が存在し、{機械チェック} が通ること」（誰が実行しても同じ判定になる）

**フェーズ間の受け渡しは、セッションの記憶ではなくリポジトリの状態だけで行います。** チャットで受け取った情報は、後工程が読む場所（`.designs/` 配下のファイル）に必ず永続化してください。ファイル化しないと、次のフェーズにその情報は一切伝わりません。

### 例外: 実行系を起動するスキル

ワークフローの起動そのものを担うスキルは、性質上ツール固有です。この場合は本文の冒頭に**ツール固有である旨と、対応する手順がどこにあるか**を明記してください。手順の実体は必ずツール非依存の側に置き、実行系のスキルは起動と結果の受け渡しだけを担当します。

## 規約をプロンプトに書き写さない

スキル本文やワークフローのプロンプトに、規約の本文をコピーしないでください。`rules/` が single source of truth であり、コピーは二重管理になって必ず乖離します。渡すのは「どのトピックを読むか」の参照だけにします。
