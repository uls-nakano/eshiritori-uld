# 受け入れテストルール（標準）

> 標準 v0.2。ULD（ULS Loop Development）の標準ルールで、uld-kit から配布されます。プロジェクト固有の追記・上書きは同じフォルダの `project.md` にあります。

アプリを起動して外から確かめるテストのルールです。受け入れ基準（ユースケース記述）は HTTP 結合テストと Storybook で、ジャーニー（ジャーニー記述）は E2E で検証し、ID で文書とテストを突き合わせます。単体テストの書き方と検証コマンドは [testing](../testing/standard.md)、ユースケース記述・ジャーニー記述の書き方は [documentation](../documentation/standard.md) にあります。

## 置き場

- **HTTP 結合テストと E2E は、リポジトリルートの `tests/` ワークスペースに置く。** これらは各アプリの一部ではなくアプリを対象にするテストであり、E2E のように複数のアプリを起動するものはどのアプリにも属さないため。
- **結合テストと E2E で共有するもの（外部システムのスタブなど）は `tests/support/` に置き、1 つの実装を使う。** 結合テストだけで使う組み立て・HTTP ヘルパーは `tests/integration/support/` に、E2E は `tests/e2e/` に置き、E2E の実行環境の組み立ては `tests/e2e/` の設定ファイルが持つ。
- **`tests/` から import できるのは composition root と各 package の公開 API だけで、production コードは `tests/` を import しない。** import 境界の機械チェック（[architecture](../architecture/standard.md) の「import 境界の機械チェック」）が検出する。

## HTTP 結合テスト

結合テストは REST API 経由で受け入れ基準を検証します。

- **実 DB を使う。** どの処理のテストかに関わらず、永続化をモックやインメモリの代替に置き換えない。repository の実装・マイグレーション・制約まで経路に含めたうえで受け入れ基準を確かめるため。
- **前提の準備は実 DB への直書きでよい。** 準備のために API を順に呼ぶと、検証したい基準と関係のない endpoint の不具合でテストが落ち、またテスト用の注入口を production に作ることになるため。書き込みはオートコミットで確定させる（サーバーは自分の接続で読むため、未コミットの行は見えない）。実行と検証は下記のとおり HTTP で行う。
- **server と依存の組み立ては composition root の production と同じ手順を import して使う。** 結合テストが自前で組み立てると、production と違う構成を検証してしまう。
- **ファイルはユースケース記述と同じ単位で分割し、`uc-{番号}-{内容の英語名}.integration.test.ts` と命名する。** あるユースケースのテストが別のユースケースの基準を兼ねて検証する場合は、テストを移さず ID を並記する。
- **実行と検証は HTTP で行い、応答は OpenAPI の生成型で受ける。** ユースケースを直接呼ぶと route と presenter の詰め替えが検証から漏れる。生成型で受けることで、契約と突き合わせていることを型の上でも表す。
- **外部システムはローカルのスタブサーバーに置き換え、production の設定項目（外部 API のベース URL）で向き先を変える。** composition にフェイクを注入する口は開けない。本物のクライアント（ページング・失敗時の変換）まで結合テストの経路に含めるため、また設定項目なら別環境（エンタープライズ版など）への向け替えと同じ正当な用途を持つため。スタブは登録された応答だけを返す。
- **サーバーは 1 ファイル 1 本を共有してよい。** endpoint はリクエスト間で状態を持たず、実 DB 込みの起動・切断をテストごとに繰り返すのは重いため。

### 分離

- **トランザクションではなく「データの分割」で分離する。** ロールバックのトランザクションは HTTP 境界を越えられない（サーバーは自分の接続で動くため、テスト側の未コミットの書き込みが見えない）。シナリオごとに別の識別子を使い、テスト同士がそもそも同じ行を触らない形にする。
- **削除クリーンアップは使わない。** 同じ識別子への再実行が upsert で同じ結果に収束すること（冪等）が、この分離の前提になる。
- 追記専用のテーブルがある場合、再実行で行は増える。件数の絶対値をアサートするテストは、前の実行の行が混入しない識別子の取り方にするか、実行前の DB リセットを前提条件として文書化する。

### 本文の書き方

- **テスト本体には「前提・操作・期待」の節コメントを置く。** 受け入れ基準 ID と保証内容はテスト名が持ち、そこへ至る手順は本文の節コメントが持つ。ラベルは `// 前提:` `// 操作:` `// 期待:` の 3 語に固定し、各 1〜2 行。長いテストでは前提と操作の組を繰り返してよい。
- 節コメントの内容は利用者の語彙（ユースケース記述と同じ言葉）で書き、関数名・endpoint・テーブル名は書かない。これはコードの言い換えではなく、テストが再現しているシナリオ（What）の記述であり、読み手がユースケース記述の文面とテストを往復できるようにするため。
- 行ごとの処理説明は引き続き書かない（[naming](../naming/standard.md) のコメント規約）。設計判断の根拠（採らなかった選択肢）は従来どおり別のコメントとして残す。

## E2E テスト

E2E テストは、ジャーニー記述に書かれたユースケースを貫く流れが、本物の UI と API を通してつながって動くことを確かめます。受け入れ基準（異常系・境界を含む）の検証責務は結合テストと Storybook にあるため、E2E は**基本的な正常系が 1 本つながること**だけを保証し、異常系・境界は書きません。

- **`e2e-{番号}-{内容の英語名}.e2e.test.ts` と命名する。** ファイル名の番号はジャーニー ID と同じにし、結合テストの `uc-{番号}-…` と同じくファイル一覧からトレース先が読めるようにする。
- **UI と API は production と同じ起動コマンドで、別プロセスとして起動する。** 結合テストが通さないプロセス起動（設定の読み込み・パッケージの解決）と、UI から API への HTTP 越境を経路に含めるため。
- **外部システムは結合テストと同じスタブ（`tests/support/` の実装）を独立プロセスで起動し、production の設定項目で向ける。** スタブの応答は起動時に読み込む fixture（テストと同じ directory の `fixtures/`）だけで決め、テストからスタブへ登録する口は作らない。何が表示されるべきかが、fixture とテストの冒頭コメントだけから読める状態を保つため。
- **テストが書き込む対象の識別子は実行ごとに一意にする。** 削除クリーンアップを使わないため、固定値だと前の実行の結果が絶対値のアサートに混入する。一意な値は実行環境の組み立てが 1 回だけ決め、スタブ・UI・テストの全プロセスへ環境変数で配る。
- **ポートは開発サーバーと別番号にする。** 開発サーバーを動かしたまま E2E を実行できるようにするため。
- **テスト本体は手順ごとに区切り、手順名はジャーニー記述のストーリーと同じ言葉にする。** 読み手がジャーニー記述とテストを往復できるようにするため。
- **スタブに登録する活動（前提）と、そこから導かれる期待値は、テストの冒頭コメントに `前提:` `期待:` で書く。** ジャーニー記述はストーリーだけを持ち、fixture の内容や期待値の表を持たない。数字を文書とテストの両方に持つと必ず片方が古くなるため、生き資料としての正体をテストコードに置く（[documentation](../documentation/standard.md) の「生き資料とログ資料」）。
- **`npm run check` には含めない。** ブラウザと UI のビルドを伴い重いため、CI の専用ジョブと手動実行で走らせる。

## 仕様トレーサビリティ

ドキュメントに書かれた仕様がテストで漏れなく検証されているかを、ID の突き合わせで確認できる状態を保ちます。

- 現在の受け入れ基準は `docs/usecases/UC-{番号}-{日本語のユースケース名}.md` に生き資料として置く（ファイル名の形式は [naming](../naming/standard.md)、書き方は [documentation](../documentation/standard.md)）。`.designs/` はログ資料であり、テストからのリンク対象にしない。
- 受け入れ基準の ID は `UC-01 要件 6` の形式（ユースケース番号 + ユースケース内の通し番号）とする。
- **ID は振り直さない。** 基準を廃止しても番号を詰めず、欠番として残す。廃止した基準は行を消さずに状態マーク「（廃止）」を付けて残す（下記）。フローを組み替えても ID は変えない（ID は文書内の位置ではなくラベル）。振り直すとテスト側のリンクが一斉に壊れるため。
- **基準の状態は ID の直後の状態マークで表し、テストの有無と機械で突き合わせる。** 書式は `**UC-02 要件 13**（未実装）` のように ID の直後に全角括弧。マーク無し（効いている）と「（廃止予定）」はテストが要る。「（未実装）」と「（廃止）」はテストがあってはならない。ジャーニーのケース ID も同じ（`**E2E-01-02**（未実装）`）。
  - **（未実装）**: 設計フェーズで合意し、実装がまだの基準。生き資料を実装より先に書き、レビューで最終形を確認できるようにするため（[documentation](../documentation/standard.md) の「実装より先に書く」）。実装でテストを足す変更と同じ変更でマークを外す
  - **（廃止予定）**: 別の基準に置き換えると決めたが、置き換え先が未実装でテストがまだ効いている基準。置き換え先の「（未実装）」と対で書き、どちらへ移るかを本文に記す
  - **（廃止）**: 退役した基準。行（ジャーニーはケースの節）は消さず欠番として残し、置き換え先があれば ID で示す。テストは同じ変更で消す
  - `check:trace` は「効いている基準にテストが無い」「未実装・廃止の基準にテストがある」の両方を止める。生き資料の状態と実装の実態が食い違ったまま残らないため
- **受け入れ基準の検証責務は結合テストと Storybook（表示系の基準）に置く。** 受け入れ基準は利用者から見える振る舞いの保証なので、内部構造の再配置に影響されない API 境界・画面で検証する。単体テストには受け入れ基準 ID を置かない。
- 結合テストは、テスト名の**先頭**に受け入れ基準 ID を置く: `UC-01 要件 6: <説明>`。ID が先頭に並ぶことで、名前順に並べたとき抜けている基準に気づきやすくなる。ID で grep すれば仕様とテストが双方向に引ける状態を保つ。
- シナリオ ID（`S-01-01` 形式）はテスト名にもコード・テストのコメントにも入れない。シナリオはログ資料（`.designs/` の scenarios.md）であり、どのシナリオがどのテストになったかはフロー完了時に scenarios.md の「結合テストへの対応」表が記録する。生きたテスト名がログ向けの採番を抱え続けないようにするため。
- 1 つのテストが複数の基準を検証する場合は ID を並記してよい（`UC-01 要件 8 / UC-02 要件 7: <説明>`）。逆に、基準 1 つを複数のテストで検証してもよい。
- **コード・テスト・story のコメントで参照する受け入れ基準は `docs/usecases/` の ID（`UC-02 要件 17`）だけにする。** `.designs/` のユースケース定義の要件番号（`要件 2-4` の形）はログ資料の番号で、読み手が生き資料から辿れない。まだ実装していない ID をコメントに書くと `check:trace` が「テストあり」と数えて状態マークの矛盾になるので、ID を書くのはその基準を検証するテストにだけにする。ログ資料の番号（要件番号と、下のシナリオ ID）の混入は `check:trace` が検出する。
- 結合テストでも Storybook でも観測できない受け入れ基準が出た場合に限り、単体テストのテスト名先頭に同じ形式で置く。
- **E2E テストはジャーニーのケース ID でトレースする。** ジャーニー記述（`docs/journeys/E2E-{番号}-{日本語のジャーニー名}.md`）は 1 つのジャーニー（`E2E-01`）が 1 本以上のケースを持ち、ケース ID `E2E-01-01`（ジャーニーの番号 + ジャーニーの中の通し番号）を太字で定義して、E2E テスト名の先頭に置く: `E2E-01-01: <説明>`。ジャーニーの中で筋が置き換わるとき（起動方法が変わるなど）は、ジャーニーを増やさず新しいケース番号で書き、元のケースは欠番として残す（受け入れ基準の ID と同じ運用）。
- **E2E テストに受け入れ基準 ID を置かない。** 置くと `check:trace` が「E2E にしか現れない基準」も充足と数え、受け入れ基準の検証責務が結合テスト・Storybook にあることが崩れるため。ジャーニー記述の中で通るユースケースに触れるときは、基準 ID ではなくユースケースへのリンクで書く。
- `npm run check:trace` が、効いている基準（マーク無し・廃止予定）の ID がテストに 1 件も現れない抜けと、テスト側にあってユースケース記述に無い ID（書き間違い）、未実装・廃止の基準にテストが存在する状態マーク不一致を検出する。ジャーニーのケース ID についても同じ検出を行い、加えて E2E テスト以外に置かれたケース ID と、E2E テストに置かれた受け入れ基準 ID を配置違反として検出する。
