## 1. 実装方針

ボトムアップで進める。順序は、application（`JoinRoom`・`GetRoom`）、エラーコード、API 契約（OpenAPI と生成）、composition root（`apps/api`）、結合テスト（`tests/`）。domain の値と集約、adapter は変えない。依存の追加も無い。

### 1-1. エラーコード（`packages/room/src/errors/RoomErrorCode.ts`）

`not_member` を足す。意味は「部屋のメンバーでない（トークンが部屋のどのメンバーのものでもない、またはトークンが無い）」。

- 部屋の状態を取る要求で、本人を確かめられなかったときに返す（1-3）
- `room_not_found` に寄せない。画面（1.12.1）が「部屋はあるが、このブラウザはメンバーでない」ときに参加画面へ戻す分岐を、「部屋が無い（期限切れ）」と分けられるようにするため
- `not_host` には寄せない。`not_host` は開始の要求のための値で、メンバーでない人を含めて「ホストでない」を表す。意味が違う
- `RoomErrorCode` は `errors/` にあり、モデル図（`src/domain` が対象）の外にある

### 1-2. application の `JoinRoom`（`packages/room/src/application/JoinRoom.ts`）

```ts
export interface JoinRoomInput { readonly roomCode: string; readonly nickname: string }
export interface JoinRoomOutput {
  readonly room: RoomSnapshotDto;
  readonly playerId: string;     // 加わったメンバーのプレイヤー識別子
  readonly playerToken: string;  // 加わったメンバーのトークン。この応答でだけ返す
}
export class JoinRoom {
  constructor(repository: RoomRepository, random: RandomSource, clock: Clock)
  execute(input: JoinRoomInput): Promise<Result<JoinRoomOutput, RoomError>>
}
```

処理の流れ:

1. `RoomCode.create(input.roomCode)` を呼ぶ。失敗（書式の誤り）は `room_not_found` のまま返す
2. `Nickname.create(input.nickname)` を呼ぶ。失敗はそのまま返す
3. `const now = this.#clock.now()` を 1 回だけ読む。期限の判断と参加の時刻に同じ値を使う
4. 最大 `MAX_JOIN_ATTEMPTS = 10` 回、次を繰り返す
   - `repository.findByCode(code)` で部屋を読む。無いか、`room.isExpiredAt(now)` なら `failure(new RoomError("room_not_found", "Room was not found."))` を返す
   - `room.join(nickname, now, random)` を呼ぶ。失敗（開始済み・満員・重複）は保存せずにそのまま返す
   - `repository.save(room)` を呼ぶ。成功なら `success({ room: toRoomSnapshotDto(room), playerId: member.playerId.value, playerToken: member.token.value })` を返す
   - `save_conflict` なら `getLogger().warn("部屋への参加がほかの書き込みと重なったため読み直します", { roomCode, attempt })` を出して、次の回で読み直す
5. 上限まで衝突が続いたら、`getLogger().error("部屋への参加が書き込みの重なりで決まりませんでした", { roomCode, attempts })` を出し、`Error("Could not join the room after repeated save conflicts.")` を throw する（API は 500）

判断:

- **検査の順は「部屋コードの書式 → ニックネーム → 部屋の有無と期限 → 集約の判断（開始済み → 満員 → 重複）」にする。** 入力だけで決まる誤りは、DB を読む前に返す。部屋コードを先にするのは、参加画面の入力欄の並び（部屋コード → ニックネーム）に合わせるため（1.6.1 と同じ考え方）。この順だと、「書式は正しいが無い部屋コード」と「空のニックネーム」が同時に来たときは、ニックネームの誤りが先に返る（要確認〔仕様〕）
- **衝突したら読み直して、集約の判断からやり直す。** 1.4.1 と docs/domain の「use case が読み直して判断をやり直す」のとおり。7 人の部屋への同時参加は、負けた側が読み直した部屋（8 人）で `room_full` になる（UC-02 要件 6）
- **上限は 10 回にする。** CreateRoom の 3 回とは理由が違う。参加の衝突は乱数の故障ではなく、ほかの人の書き込みが成功したことを意味する。待機中の部屋で成功しうる書き込みは、ほかの人の参加（最大 7 件）と開始（1 件）だけなので、負け続けた要求も 9 回目の読み直しまでに満員か開始済みで決着する。この段のどの操作の組み合わせでも上限に届かない回数にして、届いたら異常とみなす。3 回にすると、8 人が招待 URL を同時に開いたときに 500 が返りうる（要確認〔設計〕）
- **「無い・期限切れ」の判断は use case に書く。** docs/domain の「期限切れの部屋も復元して返す。存在しないとみなすかは use case が `isExpiredAt` で尋ねる」のとおり。`GetRoom` にも同じ 3 行が入る。1.7.2 の `StartGame` で 3 か所目になるので、そこで application の関数に括り出すかを判断する（この段で括り出すとファイルが 1 件増え、上限を超えるため）
- トークンとニックネームはログに出さない（部屋コードと回数だけ）

### 1-3. application の `GetRoom`（`packages/room/src/application/GetRoom.ts`）

```ts
export interface GetRoomInput { readonly roomCode: string; readonly playerToken: string }
export interface GetRoomOutput {
  readonly room: RoomSnapshotDto;
  readonly playerId: string;  // 要求した本人（トークンの持ち主）のプレイヤー識別子
}
export class GetRoom {
  constructor(repository: RoomRepository, clock: Clock)
  execute(input: GetRoomInput): Promise<Result<GetRoomOutput, RoomError>>
}
```

処理の流れは次のとおり。

1. `RoomCode.create` を呼ぶ。失敗は `room_not_found`
2. `findByCode` で部屋を読む。無いか期限切れなら `room_not_found`
3. `room.findMember(PlayerToken.create(input.playerToken))` を呼ぶ。いなければ `failure(new RoomError("not_member", "The player is not a member of the room."))`
4. いれば `success({ room: toRoomSnapshotDto(room), playerId: member.playerId.value })`

判断:

- **本人のトークンを要る形にする。** docs/architecture の「プレイヤーの識別」（以降の操作はトークンで本人を確かめる）と、1.4.1 の「トークンを持つブラウザは join を呼ばずに部屋の状態を取る」に合わせる。画面（1.12.1）は、保存したトークンで部屋の状態を取り、取れれば待機室を出し、`not_member` なら参加画面に戻す。部屋コードだけで誰でも読める形にしない。後続の移行単位で部屋の状態に描画や回答が載ると、メンバーでない人に見せてよいかの判断が要るため（要確認〔設計〕）
- **応答に本人のプレイヤー識別子を入れる。** 画面が「メンバー一覧のどれが自分か」を、トークンから決めるため。トークンは返さない（要求した本人が既に持っている）
- **保存しない。** 期限を延ばさない（1.4.1 の要確認〔仕様〕で合意済み）。`repository.save` を呼ばないことを単体テストで確かめる
- 期限切れの判断の後に、メンバーかを確かめる。無い部屋・期限切れの部屋には、トークンの有無にかかわらず `room_not_found` を返す（招待 URL を開き直したら部屋が消えていた場面。シナリオ S-01-06）

`JoinRoom`・`GetRoom` と、`type JoinRoomInput`・`type JoinRoomOutput`・`type GetRoomInput`・`type GetRoomOutput` を足す。

### 1-5. API 契約（`packages/api-contract/openapi.yaml`）

| 項目 | 内容 |
| --- | --- |
| `POST /rooms/{roomCode}/members`（`operationId: joinRoom`） | 本文は `JoinRoomRequest`（必須）。`201` は `JoinRoomResponse`。`400`・`404`・`409`・`500` は `ErrorResponse` |
| `GET /rooms/{roomCode}`（`operationId: getRoom`） | `security: [{ playerToken: [] }]`。`200` は `GetRoomResponse`。`403`・`404`・`500` は `ErrorResponse` |
| path の `roomCode` | `string`。description に「大文字小文字・全角半角・前後の空白の違いはそろえて扱う。書式の誤りは room.room_not_found」と書く |
| `components.securitySchemes.playerToken` | `type: http`、`scheme: bearer`。description に「部屋を作る・入る応答の `player.playerToken`」と書く |
| `JoinRoomRequest` | `nickname: string`（required）。制約は description に書く（1.6.1 と同じ方針） |
| `JoinRoomResponse` | `room: RoomSnapshot`、`player: PlayerCredential`（どちらも required）。`CreateRoomResponse` と同じ形だが、operation ごとに名前を分ける |
| `GetRoomResponse` | `room: RoomSnapshot`、`playerId: string`（どちらも required。後者は要求した本人の識別子） |
| `ErrorResponse.code` の description | 値の列挙に `room.room_not_found`・`room.room_full`・`room.game_already_started`・`room.nickname_taken`・`room.not_member` を足す |

- **トークンは `Authorization: Bearer <トークン>` で受け取る。** GET には本文が無く、query に置くとアクセスログや履歴に残るため。1.7.2 の開始の要求も、同じ受け取り方にそろえる（要確認〔設計〕）
- **進行状態（`status`）は、この段でも `RoomSnapshot` と `RoomSnapshotDto` に足さない。** 1.6.1 は「1.7.1 の `GetRoom` か 1.7.2 で足す」としていた。この段の基準（参加の可否）は進行状態を返さなくても観測でき、足すと影響ファイル（`RoomSnapshotDto.ts`・`CreateRoom.test.ts`）が 2 件増えて上限 15 を超える。開始で状態が変わる 1.7.2 で足す。画面が状態を使う 1.12.1 より前の段なので、間に合う（要確認〔予定外〕）
- 編集後に `npm run generate:api` で `src/generated/schema.ts` を作り直し、コミットに含める

### 1-6. HTTP の入口（`apps/api/src/createApp.ts`）

`ApiUseCases` に `joinRoom: JoinRoom` と `getRoom: GetRoom` を足し、route を 2 つ足す。3 つの route で重なる処理は、ファイル内の関数に括り出す。

| 関数 | 内容 |
| --- | --- |
| `readJson(c): Promise<Result<unknown, ErrorResponse>>` | `c.req.json()` を試し、例外なら `request.invalid_json` の失敗を返す。`POST /rooms` もこれに置き換える |
| `roomErrorResponse(c, error: RoomError)` | `c.json({ code, detail }, statusOf(error))` |
| `toRoomSnapshot(dto: RoomSnapshotDto): components["schemas"]["RoomSnapshot"]` | DTO から契約の形への詰め替え。`POST /rooms` の inline の詰め替えもこれに置き換える |
| `readBearerToken(c): string` | `Authorization` が `Bearer <値>`（scheme は大文字小文字を区別しない）なら値を返し、それ以外（ヘッダーが無い・形が違う）は `""` を返す |
| `isJoinRoomRequest(body)` | オブジェクトで、`nickname` が string か。値の範囲は見ない |

`POST /rooms/:roomCode/members` の処理:

1. `readJson` で本文を読む。失敗なら 400 を返す
2. `isJoinRoomRequest` を通す。外れたら `400 request.invalid_body` を返す
3. `joinRoom.execute({ roomCode: c.req.param("roomCode"), nickname })` を呼ぶ
4. 失敗なら `roomErrorResponse` を返す。成功なら `201` で `{ room: toRoomSnapshot(...), player: { playerId, playerToken } } satisfies JoinRoomResponse` を返す

`GET /rooms/:roomCode` の処理:

1. `getRoom.execute({ roomCode: c.req.param("roomCode"), playerToken: readBearerToken(c) })` を呼ぶ
2. 失敗なら `roomErrorResponse` を返す。成功なら `200` で `{ room, playerId } satisfies GetRoomResponse` を返す

判断:

- **`statusOf` に `not_member` → 403 を足す。** `switch` が網羅を強いるので、足し忘れは型検査で落ちる
- **トークンが無い・形が違う要求は、空のトークンとして use case に渡し、`room.not_member`（403）にする。** 401 と専用の `request.*` コードを足す案は採らない。画面にとってはどちらも「このブラウザはメンバーと確かめられない」で、同じ扱いになる。要求の形の誤り（`request.*`）は本文の JSON と形に限る（要確認〔設計〕）
- トークンはログに出さない。`onError` の context は従来どおり method と path だけ

### 1-7. composition root（`apps/api/src/composition.ts`）

時計 `{ now: () => new Date() }` と `CryptoRandomSource` を 1 つずつ作り、`CreateRoom`・`JoinRoom`（repository・random・clock）・`GetRoom`（repository・clock）に渡す。`createApp({ createRoom, joinRoom, getRoom })` を返す。設定と起動口は変えない。

### 1-8. 結合テストの土台（`tests/integration/support/`）

#### `startServer.ts`

`TestServer` に `getJson<TBody>(path: string, playerToken?: string): Promise<{ status: number; body: TBody }>` を足す。`playerToken` があれば `Authorization: Bearer <トークン>` を付ける。キャストと eslint-disable は `postJson` と同じ理由で同じ形にする（契約の生成型で受けるためのハーネスだけのキャスト）。

#### `seedRoom.ts`（新規）

```ts
export interface SeededMember { readonly playerId: string; readonly playerToken: string; readonly nickname: string }
export interface SeededRoom { readonly code: string; readonly members: readonly SeededMember[] } // 先頭がホスト
export interface SeedRoomOptions {
  readonly nicknames: readonly string[];      // 先頭がホスト。1〜8 人
  readonly status?: "waiting" | "started";    // 既定は "waiting"
  readonly lastUpdatedAt?: Date;              // 既定はいま
}
export async function seedRoom(options: SeedRoomOptions): Promise<SeededRoom>
```

- 前提の部屋を、部屋の表に直に書く（rules/acceptance-testing の「前提の準備は実 DB への直書きでよい」）。この段の API では作れない前提が 2 つあるため。1 つは「ゲームが始まった部屋」（開始の API は 1.7.2）、もう 1 つは「最後の更新から 24 時間たった部屋」（待てない）。8 人の部屋も、参加の API を 7 回呼んで作らずに直に書く。検証したい基準と別の要求で前提が崩れないようにするため
- 表と client は `readApiConfig(process.env)`・`createDynamoDbClient(config)`・`config.roomTableName` から取る（tests を `@eshiritori/room` に依存させない。1.6.1 の `startServer` と同じ）
- 項目は `PutItemCommand` で、属性値の形（`S`・`N`・`L`・`M`）を手で組む。`@aws-sdk/lib-dynamodb` を tests の依存に足さないため。属性は `RoomItemMapper` が読む形にそろえる（`roomCode`・`members[{playerId, token, nickname}]`・`hostPlayerId`・`roundCount`（1）・`status`・`lastUpdatedAt`（ISO 文字列）・`revision`（1）・`expiresAt`（最後の更新の 24 時間後のエポック秒））
- `ConditionExpression: "attribute_not_exists(roomCode)"` を付け、既にある部屋を上書きしない
- 部屋コードは英大文字と数字 6 文字を `node:crypto` の `randomInt` で毎回作り、プレイヤー識別子とトークンも `randomBytes` の base64url で作る。テストごとに別の部屋になる（データの分割）
- 書き終えたら `client.destroy()` を呼ぶ
- なぜ直に書くかと、項目の形を mapper とそろえていることを、関数の doc comment に残す

## 4. テスト計画

観測点は `tests/integration/uc-02-join-room.integration.test.ts` にする。application には単体テストを置き、カバレッジ 100% を満たす。単体テストのテスト名に受け入れ基準 ID を置かない。

### `JoinRoom.test.ts`（application の単体テスト。fake で置き換える）

- fake はテストファイルの中に置く
  - 部屋リポジトリ：`findByCode` は、渡された部屋の列を順に返し（尽きたら最後の部屋を返す）、受け取った部屋コードを記録する。`save` は、保存した部屋を記録し、最初の N 回だけ `save_conflict` を返す。`implements RoomRepository` にする
  - 時計：`{ now: () => ROOM_CREATED_AT }` を使う
  - 乱数：部屋の fixture と別の `sequenceRandom()` を使う
- 前提の部屋は `fixtures/roomFixtures.ts` の `roomWith` で作る。開始済みの部屋は `roomWith` の後にホストのトークンで `start` する
- log の検査は `MemoryLogger` を `setLogger` で差し替え、`afterEach` で戻す（`CreateRoom.test.ts` と同じ）
- `describe("execute")` に置くテスト:
  - 入れる部屋のとき
    - ニックネームのメンバーを最後に加えた部屋を保存する
    - 返すプレイヤー識別子とトークンが、加わったメンバーのものになる（ホストのものではない）
    - 返す写しが、保存した部屋と一致し、トークンを含まない
    - 最後に更新した時刻を、時計の時刻にする
  - 部屋コードを、大文字小文字・前後の空白をそろえて探す（`" abc123 "` → `ABC123` で `findByCode` が呼ばれる）
  - 部屋コードの書式が誤りのとき、`room_not_found` を返して部屋を探さない
  - ニックネームが空・空白だけ・11 文字のとき、`nickname_empty`・`nickname_too_long` を返して部屋を探さない（`it.each`）
  - 部屋コードとニックネームがどちらも誤りのとき、部屋コードの誤りを返す
  - 部屋が無いとき、`room_not_found` を返して保存しない
  - 最後の更新から 24 時間たった部屋は `room_not_found` を返して保存しない。24 時間に 1 ミリ秒足りない部屋には入れる（境界）
  - ゲームが始まった部屋・8 人の部屋・同じニックネームのメンバーがいる部屋のとき、`game_already_started`・`room_full`・`nickname_taken` を返して保存しない（`it.each`）
  - 保存が 1 回衝突したとき
    - 部屋を読み直し、読み直した部屋に加えて保存する（`findByCode` 2 回・`save` 2 回）
    - 読み直した部屋が 8 人になっていたら、`room_full` を返して保存しない（7 人の部屋への同時参加）
    - 部屋コードと回数を warn の log に出す
  - 衝突が上限まで続いたとき
    - error の log を出して throw する
    - 保存を 10 回で止める

## 5. リスク・注意点

- **`seedRoom` が項目の形を写している。** `RoomItemMapper` の形が変わると、書いた前提の部屋を復元できず 500 になり、結合テストが落ちて気づける（黙って通ることは無い）。1.7.2 の結合テスト（開始済み・1 人だけの部屋）も同じ土台を使う想定
- **生成物の取り残し。** `openapi.yaml` を変えたら `npm run generate:api` を必ず回す（1.6.1 のリスクと同じ。`check` は気づかない）。`satisfies` で詰め替える応答の型が古いままだと、型検査では通ってしまう組み合わせがありうる
- **path の部屋コードのデコード。** Hono の `c.req.param()` はパーセントエンコードを戻した値を返す想定で、全角の部屋コードも `RoomCode.create` がそろえる。結合テストは小文字だけを試す。全角を URL に載せる場面は画面（1.12.1）で確かめる
- **`Authorization` ヘッダーと CORS。** 画面を別のオリジンから配信すると、`Authorization` 付きの GET はプリフライトを伴う。この段の API は CORS を設定しない。画面の配線（1.12.1）で、開発サーバーのプロキシか CORS の設定を決める
- **同時参加のテストの揺れ。** 2 つの要求が直列に届いても並行に届いても結果は同じなので、テストは揺れない。ただし DynamoDB Local の応答が遅いと 10 秒の `testTimeout` に近づく。落ちたら時間を見直す
- **TTL。** DynamoDB Local は TTL で項目を消さないので、期限切れの部屋は表に残ったまま、ドメインの判断（`isExpiredAt`）で「見つからない」になる。結合テストはその判断を通る。AWS では TTL で先に消えていることがあるが、どちらでも結果は `room_not_found` で同じ
- **「無い・期限切れ」の判断が 2 か所に入る。** `JoinRoom` と `GetRoom` に同じ 3 行が入る。1.7.2 で 3 か所目になるときに括り出しを判断する（1-2）
- **`status` を返さない。** 1.12.1 が「待機室かゲーム画面か」を決めるのに要るので、1.7.2 で必ず足す。1.7.2 の設計メモに引き継ぐ
