## 1. 実装方針

domain・application は変えない。adapter（`packages/room/src/adapters/`）と、ローカルの DB を動かす道具だけを足す。

### 1-1. 依存の追加

| 依存 | 置き場 | 理由 |
| --- | --- | --- |
| `@aws-sdk/client-dynamodb`（^3） | `packages/room/package.json` の `dependencies` | client・`ConditionalCheckFailedException`・表の作成 |
| `@aws-sdk/lib-dynamodb`（^3、client と同じ版） | `packages/room/package.json` の `dependencies` | 属性値の型付き表現（`{ S: ... }`）を手で書かずに、素の object で読み書きする。mapper が「項目の形 ↔ 集約」だけに集中できる |
| `@types/node`（^22。`engines` の `>=22` に合わせる） | ルートの `devDependencies` | `node:crypto` と、テスト・スクリプトの `process.env` の型 |
| `tsx`（^4） | ルートの `devDependencies` | `scripts/create-tables.ts` を動かす（1-6） |
| `@aws-sdk/client-dynamodb`（room と同じ範囲） | ルートの **`dependencies`** | `scripts/create-tables.ts` が import する。knip はルートのファイルの import をルートの `package.json` と突き合わせるため、ルートにも載せる |

- **ルートに載せる AWS SDK は `devDependencies` にしない。** dependency-cruiser の `combinedDependencies: true` は、package とルートの `package.json` をキーごと（`dependencies` 同士・`devDependencies` 同士）に合わせる（`node_modules/dependency-cruiser/src/extract/resolve/merge-manifests.mjs` で確かめた）。ルートの `devDependencies` に同じ名前があると、room の adapter からの import にも `npm-dev` が付き、`not-to-dev-dep` に当たる。ルートは `private` なので `dependencies` に置いても公開の意味は変わらない
- knip が `@eshiritori/room`（スクリプトが import する workspace）をルートの unlisted dependency として報告した場合は、同じ理由でルートの `dependencies` に `"@eshiritori/room": "*"` を足す。報告されなければ足さない
- `@types/node` を入れると、どの workspace の型環境にも Node の型が入る（`tsconfig` に `types` が無いため）。domain から `node:` の module を import しても型検査で落ちなくなるので、1-7 で `domain-is-pure` に `core` を足して塞ぐ。`shared-kernel` の `ConsoleLogger.ts` の `declare const console` は module 内の宣言なので衝突しない。この段では消さない

### 1-2. 表の定義（`src/adapters/persistence/roomTable.ts`）

関数を持たない定数 1 つ `roomTable` を export する。

```ts
export const roomTable = {
  /** 表の名前の既定値。repository は名前を引数で受け取る（AWS の環境ごとに変えられるように）。 */
  name: "eshiritori-rooms",
  /** 期限切れの項目を DynamoDB が消すときに見る属性（エポック秒）。 */
  timeToLiveAttributeName: "expiresAt",
  /** 表を作るときの入力（表の名前を除く）。 */
  createTableInput: {
    AttributeDefinitions: [{ AttributeName: "roomCode", AttributeType: "S" }],
    KeySchema: [{ AttributeName: "roomCode", KeyType: "HASH" }],
    BillingMode: "PAY_PER_REQUEST",
  },
} as const satisfies { ... }; // createTableInput は Omit<CreateTableCommandInput, "TableName"> を満たす
```

- **部屋コードをそのまま partition key にする**（`pk`・`sk` の汎用名にしない）。表は部屋の 1 種類の項目だけを持ち（接続表は 1.8.1 で別の表）、部屋コードで 1 件を引く以外の読み方がこのスライスに無いため
- `PAY_PER_REQUEST` は docs/architecture の「DynamoDB（オンデマンド）」に合わせる
- 関数にしないのは、スクリプトだけが呼ぶ関数はテストから実行されずカバレッジから漏れるため。定数なら import した時点で計測が済む。この file の colocate テストは置かない（振る舞いを持たない定義で、repository の実 DB テストがこの定義で作った表に対して通ることで確かめられる）

### 1-3. 項目と集約の対応（`src/adapters/persistence/RoomItemMapper.ts`）

#### 項目の形 `RoomItem`（同じ file に export する interface）

| 属性 | 型 | 集約の値 |
| --- | --- | --- |
| `roomCode` | string | `room.code.value` |
| `members` | `{ playerId: string; token: string; nickname: string }[]` | `room.members` を**並びを保って**（開始前は入った順、開始後は描く順） |
| `hostPlayerId` | string | `room.hostPlayerId.value` |
| `roundCount` | number | `room.roundCount.value` |
| `status` | `"waiting" \| "started"` | `room.status.hasStarted() ? "started" : "waiting"`（`RoomStatus` は実値の getter を持たない。1.2.1 の決定） |
| `lastUpdatedAt` | string | `room.lastUpdatedAt.toISOString()`（UTC・ミリ秒まで） |
| `revision` | number | **書き込む**改訂番号（下記） |
| `expiresAt` | number | `Math.ceil((lastUpdatedAt のミリ秒 + 24 時間) / 1000)`（TTL 用のエポック秒） |

- **最後に更新した時刻は ISO 8601 の文字列で持つ。** ミリ秒まで往復で変わらず、DynamoDB Local を調べるときに読める。TTL は数値（エポック秒）しか受け付けないので、別の属性 `expiresAt` に持つ（S-01-06 の「期限の判断に使う時刻の保存」）
- **`expiresAt` は切り上げる。** 切り捨てると最大 999 ミリ秒だけドメインの期限より早く消えうる。DynamoDB の削除は時刻より遅れることはあっても早まらないので、切り上げればドメインが「まだある」と判断する部屋が消えることはない
- **24 時間は mapper の非公開の定数として持つ**（`Room` の `ROOM_LIFETIME_MILLISECONDS` は公開されていない）。知識が 2 か所になるので、mapper の単体テストで `room.isExpiredAt(new Date(expiresAt * 1000))` が `true`、1 秒前が `false` であることを確かめ、片方だけ変わったら落ちるようにする（要確認〔設計〕）
- トークンを平文で持つ（ドメインが `PlayerToken.equals` で保存した値と比べるため）。5. を参照

#### クラスと関数

`RoomItemMapper` は状態を持たない instance class（`no-extraneous-class` が static だけのクラスを禁じるため）。repository が private field に 1 つ持つ。

| 関数 | 型 | 処理 |
| --- | --- | --- |
| `toItem(room, revision)` | `(Room, Revision) => RoomItem` | 上の表のとおり。`revision` は呼び出し側（repository）が決める（`room.revision.next()`）。「保存で改訂番号を 1 進める」は保存の規則なので mapper に置かない |
| `toRoom(item)` | `(unknown) => Room` | 形を確かめ（下記）、値を domain の factory で復元して `Room.restore` に渡す |

`toRoom` の復元:

1. **形の検査は型ガードで行い、`as` を使わない。** 各属性の型（string・number・配列・`"waiting" \| "started"`）だけを見る。外れたら、外れた属性名を返す小さな関数で属性名を得て、`getLogger().error("保存された部屋の項目の形が正しくありません", { roomCode, attribute })` を出してから `Error("Stored room item is invalid: <属性名>")` を throw する（`roomCode` は文字列なら値、でなければ `undefined`）
2. **値の規則は domain の factory に任せ、mapper で繰り返さない。** `RoomCode.create`・`Nickname.create`・`RoundCount.create` は Result を返すので、失敗なら 1 と同じ形（`attribute` に `roomCode`・`members.nickname`・`roundCount`）で log を出して throw する。`PlayerId.create`・`PlayerToken.create` は検証しない（1.3.1 の決定）。`Revision.restore` と `Room.restore` は自分で log を出して throw するので、mapper は包まずに通す
3. `lastUpdatedAt` は `new Date(文字列)` が `NaN` なら 1 と同じ形で throw する
4. `status` は `"started"` なら `RoomStatus.started()`、`"waiting"` なら `RoomStatus.waiting()`
5. `expiresAt` は読まない（形の検査にも含めない）。期限の判断はドメインが `lastUpdatedAt` から行うため
- **log にトークン・ニックネーム・項目全体を出さない。** 調べるのに要るのは部屋コードと外れた属性名だけで、トークンは本人の秘密のため
- 壊れた項目は利用者の操作で起きる失敗ではないので Result にせず throw する（`Room.restore`・`Revision.restore` と同じ扱い。use case が予期しない例外として変換する）

### 1-4. 部屋リポジトリ（`src/adapters/persistence/DynamoDbRoomRepository.ts`）

`implements RoomRepository`。constructor は `(client: DynamoDBDocumentClient, tableName: string)`。client の作り方（endpoint・認証情報）は知らない（composition root とテストが作る）。

| 関数 | 処理 |
| --- | --- |
| `findByCode(code)` | `GetCommand({ TableName, Key: { roomCode: code.value }, ConsistentRead: true })`。`Item` が無ければ `undefined`、あれば `mapper.toRoom(Item)` |
| `save(room)` | `PutCommand` で項目全体を書く（下記の条件付き）。成功なら `success(undefined)`、`ConditionalCheckFailedException` なら `failure("save_conflict")`、それ以外の例外は捕まえずに投げ直す |

保存の条件:

| 部屋 | `ConditionExpression` | 書く改訂番号 |
| --- | --- | --- |
| `room.revision.isInitial()` | `attribute_not_exists(#roomCode)` | `room.revision.next()`（= 1） |
| それ以外 | `#revision = :readRevision`（`:readRevision` = `room.revision.value`） | `room.revision.next()` |

- **属性名は `ExpressionAttributeNames`（`#roomCode`・`#revision`）で渡す。** DynamoDB の予約語と重なっても壊れないようにする
- **既存の部屋の条件に `attribute_exists` を足さない。** 項目が無い（TTL で消えた）と `#revision = :readRevision` は偽になり、衝突として返る。use case は読み直して「無い」と判断できる
- **`UpdateItem` ではなく `PutItem` で項目全体を置き換える。** 部屋は 1 項目 1 集約で、どの操作も集約全体を判断して書くため。差分の更新式を組むと、どの属性が変わったかを repository が知ることになる
- **強い整合性の読み込み（`ConsistentRead: true`）にする。** 衝突した use case は読み直して判断をやり直すが、結果整合の読み込みでは勝った側の書き込みが見えず、同じ改訂番号を読んで再び衝突しうる。やり直しの回数に上限を置く（1.6.1〜）と、それを使い切る原因になる
- **保存は渡された集約の改訂番号を変えない**（集約の `#revision` は readonly。1.4.1 の決定）。同じインスタンスをもう一度 `save` すると衝突になる。use case は保存した後の部屋を続けて書かない（5. を参照）
- 衝突の判定は `error instanceof ConditionalCheckFailedException`（`@aws-sdk/client-dynamodb` から import）。lib-dynamodb は client の例外をそのまま投げる
- repository の中でトランザクションも読み直しもしない（rules/development の「Repository / Use Case ルール」とモデル docs のとおり）

### 1-5. 暗号論的な乱数の源（`src/adapters/random/CryptoRandomSource.ts`）

`implements RandomSource`。`nextInt(bound)` は `node:crypto` の `randomInt(bound)` を返す。

- `randomInt` は棄却法で一様な整数を返す（剰余の偏りが無い）。`bound` が整数でない・1 未満・2^48 を超える場合は `RangeError` を投げる。port の契約（`bound` は 1 以上の整数）を守るのは呼び出し側（domain）なので、ここで検査を重ねない
- Web Crypto（`globalThis.crypto.getRandomValues`）で自前の棄却法を書く案は捨てた。偏りの無い範囲変換を自分で書いて検証することになり、本番は Node（Lambda）で動くため `node:crypto` で足りる

### 1-6. ローカルの DynamoDB と表の作成

#### `compose.yaml`

```yaml
services:
  dynamodb:
    image: amazon/dynamodb-local:2.5.2
    command: ["-jar", "DynamoDBLocal.jar", "-inMemory", "-sharedDb"]
    ports:
      - "8000:8000"
```

- **版を固定する**（`latest` にしない）。`2.5.2` は手元に取得済みの版
- **`-inMemory`** にする。テストが毎回新しい部屋コードを使うため（4. の「実 DB の分離」）項目が溜まり続けるが、コンテナを止めれば消える。volume の管理も要らない。代わりに起動し直すたびに表を作り直す（`db:up` が続けて作る）
- **`-sharedDb`** にする。付けないと DynamoDB Local は認証情報と region ごとに別の DB を持ち、スクリプトとテストと API（1.6.1）の設定が少しずれただけで「表が無い」になるため

#### `scripts/create-tables.ts`

1. endpoint は `process.env.DYNAMODB_ENDPOINT ?? "http://localhost:8000"`、region は `"ap-northeast-1"`、認証情報は固定の `{ accessKeyId: "local", secretAccessKey: "local" }`（DynamoDB Local 2.x はキーに英数字しか受け付けない）。固定の認証情報なので、誤って AWS の本物の表に向くことは無い
2. 起動直後の JVM を待つため、`ListTables` が通るまで 500 ミリ秒おきに最大 20 回試す。通らなければ「`docker compose up -d dynamodb` で起動したか」を案内して終了コード 1 で終わる
3. 表の定義の一覧（いまは `roomTable` だけ。1.8.1 が接続表を足す）について、既にあれば何もしない。無ければ `CreateTable`（`TableName` に `name`）と `UpdateTimeToLive`（`timeToLiveAttributeName`）を呼ぶ。何度実行しても同じ状態になる
4. `roomTable` は `@eshiritori/room` の公開入口から import する（`src/index.ts` に `export { roomTable } from "./adapters/persistence/roomTable";` を足す）。room の内部 path を直接 import しない

- **`tsx` で動かす。** Node 22.14 の型の除去（`--experimental-strip-types`）は、room の source の拡張子なしの import（`moduleResolution: Bundler`）を解決できないため
- この file は型検査（`npm run typecheck` は workspace だけ）と ESLint（対象は `packages/**/*.ts`）の対象外になる。手順だけの短い file に保ち、`npm run db:up` を実行して確かめる（要確認〔設計〕）

#### `package.json` の scripts

| 名前 | 中身 |
| --- | --- |
| `db:up` | `docker compose up -d dynamodb && npm run db:create-tables` |
| `db:create-tables` | `tsx scripts/create-tables.ts` |
| `db:down` | `docker compose down` |

- `check`・`check:fast` は DB を起動しない。起動していなければ repository のテストが手順を案内して落ちる（4.）。検証コマンドに docker の操作を混ぜると、CI と手元で前提が分かれるため

### 1-7. import 境界（`.dependency-cruiser.cjs`）

- `domain-is-pure` の `to.dependencyTypes` に `"core"` を足す。`@types/node` を入れたことで、domain が `node:crypto` などを import しても型検査が通るようになるため。いままでは型が無いことが偶然それを止めていた。1.3.1 のメモの「domain は実行環境の I/O 系 module に依存させない」を機械で守る
- adapter からの `node:crypto`・`@aws-sdk/*` は既存の規則に当たらない（`room-depends-only-on-shared-kernel` は `^packages/` だけ、`not-to-dev-dep` は `npm-dev` だけを見る）

### 1-8. 公開入口（`src/index.ts`）

- `roomTable` だけを足す（1-6 のスクリプトのため）。`DynamoDbRoomRepository`・`CryptoRandomSource` の公開は使う段（1.6.1 の composition root）が足す。この段ではテストから import されるので knip の未使用 file にならない

## 4. テスト計画

観測点は `DynamoDbRoomRepository.test.ts`（実 DB）。mapper と乱数の源は DB に触れない単体テスト。受け入れ基準 ID はテスト名に置かない（rules/testing）。`describe` は関数名。

### 共通

- log を確かめるテストは `MemoryLogger` を `setLogger` で差し替え、`afterEach` で戻す（`Revision.test.ts` と同じ形）
- 集約は共有 fixture（`packages/room/fixtures/roomFixtures.ts` の `roomWith`・`nicknameOf`・`roundCountOf`・`ROOM_CREATED_AT`）で作る。fixture は変えない

### `RoomItemMapper.test.ts`

`toItem`:

- 部屋の値を項目の属性に写す（部屋コード・ホストのプレイヤー識別子・周回数・メンバーの識別子とトークンとニックネーム）
- メンバーの並びを保つ（開始後の部屋で、描く順の並びのまま書く）
- 進行状態を待機中なら `"waiting"`、始まっていれば `"started"` で書く
- 最後に更新した時刻を UTC の ISO 8601（ミリ秒まで）で書く
- 渡された改訂番号を書く（集約の改訂番号ではなく引数の値）
- 期限の属性はドメインが期限切れと判断する時刻のエポック秒になる（`isExpiredAt(expiresAt 秒)` が `true`、その 1 秒前が `false`。最後に更新した時刻にミリ秒の端数がある場合も確かめる）
- 期限の属性名は表の定義（`roomTable.timeToLiveAttributeName`）と一致する

`toRoom`:

- `toItem` で書いた項目から、同じ部屋を復元する（部屋コード・メンバーの並びと 3 つの値・ホスト・周回数・進行状態・最後に更新した時刻のミリ秒・改訂番号が書いた値）
- 始まった部屋を始まった状態で復元する
- 形の誤り（属性の欠落・型の違い・メンバーが配列でない・メンバーの属性の欠落・未知の進行状態・日時として読めない時刻）を throw し、部屋コードと外れた属性名を log に出す（`it.each`）
- 値の誤り（書式の誤った部屋コード・空のニックネーム・範囲外の周回数）を throw し、外れた属性名を log に出す
- 改訂番号が 0 の項目は throw する（`Revision.restore` に任せる）
- ホストがメンバーにいない項目は throw する（`Room.restore` に任せる）
- log にトークンを出さない（形の誤り・値の誤りの log の context を文字列にして、トークンの値を含まないこと）

`save`:

- 新しい部屋を保存すると、部屋コードで読み出せ、改訂番号が 1 になる
- 同じ部屋コードの部屋が既にあると、新しい部屋の保存は衝突を返し、既にある部屋は変わらない（保存済みの部屋と同じ部屋コードで、別のホスト・`Revision.initial()` の部屋を `Room.restore` で作る。`Room.create` は部屋コードを乱数で作るので狙えない）
- 読み出した部屋にメンバーを加えて保存すると、加わったメンバーと進んだ改訂番号（2）で読み出せる
- 同じ改訂番号で読んだ 2 つの部屋に別々の人が入ると、先に保存した方だけが書き込まれ、後の保存は衝突を返す。読み直すと先の人だけがいる
- 7 人の部屋に 2 人がほぼ同時に入ると、後の保存は衝突し、読み直した部屋への参加は満員で拒否される（同時参加の判断部分。`join` の結果が `room_full`）
- 保存した後の同じ部屋（インスタンス）をもう一度保存すると衝突を返す（保存は集約の改訂番号を進めない）
- 項目が無い部屋コードの保存済みの部屋（新しい部屋コードで `Revision.restore(3)` を持たせて `Room.restore` した部屋）を保存すると衝突を返し、項目も作られない（TTL で消えた部屋への書き込み）
- 表が無いときは、衝突ではなく例外を投げる（存在しない表の名前で作った repository。衝突以外の例外を投げ直す分岐）

`findByCode`:

- 保存した部屋が無い部屋コードは `undefined` を返す
- 最後の更新から 24 時間以上たった部屋も返し、最後に更新した時刻をミリ秒まで保つ（`isExpiredAt` が `true`）
- 始まった部屋を、描く順の並びと始まった状態で返す
- 表が無いときは例外を投げる

### `CryptoRandomSource.test.ts`

`nextInt`:

- `bound` が 1 なら常に 0 を返す
- 返す値は 0 以上 `bound` 未満の整数（`bound` 2・36・64 でそれぞれ 2000 回）
- 範囲のすべての値が出る（`bound` 64 で 2000 回。1 つも出ない値がある確率は 64 × (63/64)^2000 ≒ 2 × 10^-12）

## 5. リスク・注意点

- **`npm run check` が DynamoDB Local を前提にする。** この段から、DB を起動していないと `coverage` が落ちる。rules/testing/project.md に手順を書き、テストの失敗の文言でも案内する。CI（まだ無い）を足す段は、DynamoDB Local を service container で起動して `db:create-tables` を実行する必要がある
- **DynamoDB Local の `UpdateTimeToLive`。** DynamoDB Local は TTL による削除を行わないが、設定の API は受け付ける想定。受け付けずにエラーになる版だった場合は、スクリプトでその呼び出しの失敗を「ローカルでは TTL を設定しない」と表示して続ける形に変え、実装の記録に残す
- **保存は集約の改訂番号を進めない。** 保存に成功した部屋のインスタンスで続けて判断・保存すると、常に衝突する。1.6.1〜1.7.2 の use case は、保存の後に同じインスタンスを保存しない。続けて書く必要が出たら読み直す
- **衝突のやり直しの上限は use case が決める**（1.4.1 から引き継ぎ）。この段の repository は 1 回の条件付き書き込みだけを行う
- **トークンを平文で保存する。** DB の中身が漏れると、メンバーになりすませる。ハッシュで保存するには、ドメインの比較（`PlayerToken.equals`）とトークンの復元の形を変えることになり、この段の範囲を超える。部屋は 24 時間で期限切れになり、トークンは部屋の中でしか意味を持たないため、このスライスでは平文のままにする。AWS にデプロイする要求で見直す
- **mapper の 24 時間とドメインの 24 時間。** 片方だけを変えると、TTL の削除がドメインの期限より早まる（部屋が突然消える）か、遅れる（無駄に残る）。mapper のテストが `isExpiredAt` と突き合わせて検出する
- **`@types/node` の影響。** すべての workspace の型環境に Node の型が入る。domain が `process`・`Buffer` などの global を使っても型検査では落ちない（import は 1-7 で塞ぐが、global は塞がない）。domain のレビューで見る
- **ポート 8000。** 手元で別の DynamoDB Local が 8000 を使っていると起動できない。`compose.yaml` の公開ポートを変えた場合は `DYNAMODB_ENDPOINT` を合わせる
- **`ConditionalCheckFailedException` の `instanceof`。** `@aws-sdk/client-dynamodb` が 2 つの版で入ると `instanceof` が外れる。room とルートの範囲を同じにして 1 つに揃える（`npm ls @aws-sdk/client-dynamodb` で確かめる）。外れた場合は衝突が例外として投げられ、同時参加のテストが落ちるので気付ける

## 6. 実装の記録

設計からの逸脱:

- **`packages/room/tsconfig.json` に `"types": ["node"]` を足した（影響ファイルに無かった変更）。** TypeScript 6.0 は `types` の既定が空で、`@types/node` を入れても型環境に入らない（1-1 の「どの workspace の型環境にも Node の型が入る」は成り立たない）。`node:crypto` と `process.env` を使う room にだけ明示した。shared-kernel には足さない。`.dependency-cruiser.cjs` の `domain-is-pure` への `core` の追加（1-7）は、room の domain が Node の型を見られるようになったので、設計のとおり必要
- **`UpdateTimeToLive` は DynamoDB Local 2.5.2 で受け付けられた。** スクリプトの失敗時の分岐は足していない
- **mapper の形の検査は 1 つの `readItem` 関数にまとめた。** 属性ごとの型ガードを並べ、`as` を使わずに項目として読む（設計の「型ガードで行い `as` を使わない」のとおり）。メンバーの形の誤りの属性名は `members.member`
- **repository テストの満員の拒否は、`RoomError` の code が `room.room_full` になる**（設計メモは `room_full` と略記していた）
