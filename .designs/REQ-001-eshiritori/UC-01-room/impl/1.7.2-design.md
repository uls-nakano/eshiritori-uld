## 1. 実装方針

ボトムアップで進める。順序は、application（`RoomSnapshotDto` の進行状態 → `StartGame`）、API 契約（OpenAPI と生成）、composition root（`apps/api`）、結合テスト（`tests/`）。domain の値と集約、adapter、エラーコードは変えない（`not_host`・`not_enough_members` は 1.2.1 で定義済み、`statusOf` も 403・409 に割り当て済み）。依存の追加も無い。

### 1-1. 部屋の写しに進行状態を足す（`packages/room/src/application/RoomSnapshotDto.ts`）

1.6.1・1.7.1 から送られてきたもの。

```ts
export interface RoomSnapshotDto {
  readonly code: string;
  readonly roundCount: number;
  readonly hostPlayerId: string;
  /** 進行状態。started のとき members の並びが描く順番。 */
  readonly status: "waiting" | "started";
  readonly members: readonly MemberDto[];
}
```

- `toRoomSnapshotDto` で `status: room.status.hasStarted() ? "started" : "waiting"` を詰める。`RoomStatus` は実値を外に出さず `hasStarted` で尋ねる値なので（docs/domain）、`RoomItemMapper` と同じ形で、境界の表現へ詰め替える
- 値の名前は DB の項目（`RoomItemMapper` の `status`）とそろえて `waiting`・`started` にする。型は inline の union にし、別名の型は作らない（使うのはこの DTO と契約の生成型だけのため）
- 「開始後は members の並びが描く順番」は domain の約束（docs/domain の「描く順番はメンバーの並びで表す」）。写しは並びを保つだけで、描く順番を別の配列にしない
- 既存の 3 つの use case のテスト（`CreateRoom.test.ts`・`JoinRoom.test.ts`・`GetRoom.test.ts`）は写しを `toEqual` で比べているので、期待に `status: "waiting"` を足す

### 1-2. application の `StartGame`（`packages/room/src/application/StartGame.ts`）

```ts
export interface StartGameInput { readonly roomCode: string; readonly playerToken: string }
export interface StartGameOutput { readonly room: RoomSnapshotDto }
export class StartGame {
  constructor(repository: RoomRepository, random: RandomSource, clock: Clock)
  execute(input: StartGameInput): Promise<Result<StartGameOutput, RoomError>>
}
```

処理の流れ:

1. `RoomCode.create(input.roomCode)` を呼ぶ。失敗（書式の誤り）は `room_not_found` のまま返す
2. `PlayerToken.create(input.playerToken)` を 1 回だけ作る（書式は検証しない。空のトークンは「持ち主のいないトークン」として集約が `not_host` にする）
3. `const now = this.#clock.now()` を 1 回だけ読む。期限の判断と開始の時刻に同じ値を使う
4. 最大 `MAX_START_ATTEMPTS = 10` 回、次を繰り返す
   - `repository.findByCode(code)` で部屋を読む。無いか、`room.isExpiredAt(now)` なら `failure(new RoomError("room_not_found", "Room was not found."))` を返す
   - `room.start(token, now, this.#random)` を呼ぶ。失敗（`not_host`・`not_enough_members`）は保存せずにそのまま返す
   - 結果が `false`（既に始まっていた）なら、**保存せずに** `success({ room: toRoomSnapshotDto(room) })` を返す
   - `repository.save(room)` を呼ぶ。成功なら `success({ room: toRoomSnapshotDto(room) })` を返す
   - `save_conflict` なら `getLogger().warn("ゲームの開始がほかの書き込みと重なったため読み直します", { roomCode, attempt })` を出して、次の回で読み直す
5. 上限まで衝突が続いたら、`getLogger().error("ゲームの開始が書き込みの重なりで決まりませんでした", { roomCode, attempts })` を出し、`Error("Could not start the game after repeated save conflicts.")` を throw する（API は 500）

判断:

- **検査の順は「部屋コードの書式 → 部屋の有無と期限 → 集約の判断（ホストか → 開始済みか → 人数）」にする。** 期限をホストかより先に見るのは `GetRoom` と同じ理由で、無い・期限切れの部屋にはトークンにかかわらず `room_not_found` を返すため。集約の中の順は 1.4.1 で決めたとおり
- **二度目の開始は 200 で、いまの部屋の写しを返す。** 応答は一度目と同じ形にし、「今回の要求で始まったか」を応答に出さない。UC-03 要件 6（エラーも表示されない）のとおり、ホストの画面は一度目と二度目を区別しなくてよい。use case も出力に `started` を持たない。1.9.1 で通知を足すときは、`StartGame` の中の「`start` が `true` を返して保存に成功した」分岐に publisher の呼び出しを入れる（出力の形は変えずに済む）
- **衝突したら読み直して、集約の判断からやり直す。** `JoinRoom` と同じ。ホストの二度押しが同時に届くと、負けた側は読み直した部屋（開始済み）で `false` になり、勝った側と同じ並びの写しを返す（UC-03 要件 6 の「通信の再送」）
- **上限は 10 回にする。** 待機中の部屋で開始と衝突しうる書き込みは、ほかの人の参加（この移行単位ではメンバーが抜けないので、部屋の一生で最大 7 件）と、別の開始（1 件。成功した後は開始済みになり、以後の開始・参加は保存しない）だけ。負け続けても 9 回目の読み直しまでに、始まるか開始済みで決着する。`JoinRoom` の `MAX_JOIN_ATTEMPTS` と値は同じだが、根拠になる「衝突しうる書き込み」が操作ごとに違うので、定数はファイルごとに持ち、根拠をそれぞれの doc comment に書く
- **「無い・期限切れ → `room_not_found`」は括り出さない（3 か所目）。** 1.7.1 から判断を引き継いだ。括り出さない理由は 2 つ。期限の判断そのもの（24 時間）は既に `Room.isExpiredAt` の 1 か所にあり、use case に重なっているのは「無いか期限切れなら見つからないと返す」という 1 行の条件とエラーの組み立てだけであること。括り出す（application の関数 1 ファイル＋ `JoinRoom.ts`・`GetRoom.ts` の書き換え）と影響ファイルが 3 件増えて 18 件になり、上限 15 を超えること。4 か所目が出る段（後続の移行単位の、部屋を扱う use case）で括り出す（要確認〔設計〕）
- トークンはログに出さない（部屋コードと回数だけ）

### 1-4. API 契約（`packages/api-contract/openapi.yaml`）

| 項目 | 内容 |
| --- | --- |
| `POST /rooms/{roomCode}/start`（`operationId: startGame`） | `summary: ゲームを始める`。`security: [{ playerToken: [] }]`。本文は無し。`200` は `StartGameResponse`。`403`・`404`・`409`・`500` は `ErrorResponse` |
| operation の description | 「ホストだけが始められる。描く順番をランダムに決め、members をその並びにする。既に始まった部屋への要求は何もせず、いまの部屋を 200 で返す（描く順番は決め直さない）」 |
| `403` の description | 「ホスト以外のメンバー、またはメンバーでない人からの要求（room.not_host）。トークンが無い・形が違う場合も同じ」 |
| `404` の description | 「部屋が無い、または期限切れ（room.room_not_found）」 |
| `409` の description | 「メンバーがホスト 1 人だけ（room.not_enough_members）」 |
| `StartGameResponse` | `room: RoomSnapshot`（required）。`GetRoomResponse` と違い `playerId` を持たない（要求できるのはホストだけで、ホストの識別子は `room.hostPlayerId` にある） |
| `RoomSnapshot.status` | `type: string`、`enum: [waiting, started]`、required に足す。description は「進行状態。waiting は待機中、started はゲームが始まった後」 |
| `RoomSnapshot.members` の description | 「開始前は部屋に入った順、開始後は描く順番」を足す |
| `ErrorResponse.code` の description | 値の列挙に `room.not_host`・`room.not_enough_members` を足す |

- **path は `POST /rooms/{roomCode}/start` にする。** 開始は「部屋の状態を書き換える」より「開始という操作を求める」もので、二度目が何もしない（同じ要求を何度送っても結果が同じ）ことを description に書く。`PUT /rooms/{roomCode}/status` のように状態を直接置く形にすると、`waiting` に戻す要求も契約上ありうる形になり、「一度始まったら待機中に戻らない」（docs/domain）と食い違う（要確認〔名前〕）
- **成功の status は 200 にする。** 何かを作る操作ではなく（201 にしない）、写しを返すので 204 にもしない。応答に写しを返すのは、ホストの画面が WebSocket の通知（1.9.1）を待たずに描く順番を出せるようにするため
- **非メンバー・トークン無しの開始は `room.not_host`（403）にする。** 1.4.1 の決定（`not_host` は「メンバーでない人を含めてホストでない」）と 1.7.1 の `RoomErrorCode` の注記のとおり。部屋の状態を取る要求の `room.not_member` とはコードが違うが、画面は開始の操作をホストにしか出さないので、`not_host` を受けて分岐する場面は無い
- `status` を enum にすると、生成型が `"waiting" | "started"` になり、`toRoomSnapshot` の `satisfies` が DTO との食い違いを型検査で止める
- 編集後に `npm run generate:api` で `src/generated/schema.ts` を作り直し、コミットに含める

### 1-5. HTTP の入口（`apps/api/src/createApp.ts`）

- `ApiUseCases` に `startGame: StartGame` を足す
- `toRoomSnapshot` に `status: dto.status` を足す
- route `POST /rooms/:roomCode/start` を足す
  1. `startGame.execute({ roomCode: c.req.param("roomCode"), playerToken: readBearerToken(c) })` を呼ぶ
  2. 失敗なら `roomErrorResponse` を返す。成功なら `200` で `{ room: toRoomSnapshot(result.value.room) } satisfies StartGameResponse` を返す
- **本文は読まない。** 契約に本文が無いので、送られてきても見ない（壊れた JSON が付いていても `request.invalid_json` にしない）
- `statusOf` は変えない。`not_host` → 403、`not_enough_members` → 409 の分岐は、この段の結合テストが初めて通す

### 1-6. composition root（`apps/api/src/composition.ts`）

`startGame: new StartGame(repository, random, clock)` を足す。時計と乱数の源は既存の 1 つずつを共有する。

### 1-7. 結合テストの土台（`tests/integration/support/startServer.ts`）

`postJson` に省略できる第 3 引数 `playerToken?: string` を足す。あれば `Authorization: Bearer <トークン>` を付ける（`getJson` と同じ形）。開始の要求は本文の無い契約なので、テストからは `undefined` を本文として渡し、`postJson` は本文が `undefined` のとき `body` と `content-type` を付けずに送る。新しい関数（`postWithToken` など）を別に足さないのは、キャストと eslint-disable の理由の注記を 1 か所に保つため。

`seedRoom` は変えない。`status: "started"` を指定すると、`nicknames` の並びがそのまま描く順番になった開始済みの部屋が書けるので、「順番が決め直されない」を乱数に左右されずに確かめられる（4 章）。

## 4. テスト計画

観測点は `tests/integration/uc-03-start-game.integration.test.ts` にする。application には単体テストを置き、カバレッジ 100% を満たす（`toRoomSnapshotDto` の `started` の分岐は `StartGame.test.ts`・`GetRoom.test.ts`、`waiting` の分岐は既存のテストが通す）。単体テストのテスト名に受け入れ基準 ID を置かない。

### `StartGame.test.ts`（application の単体テスト。fake で置き換える）

- fake はテストファイルの中に置く。部屋リポジトリは `JoinRoom.test.ts` と同じ形（渡された部屋の列を順に返し、尽きたら最後の部屋。受け取った部屋コードと保存した部屋を記録し、最初の N 回だけ `save_conflict` を返す）。`implements RoomRepository` にする
- 前提の部屋は `fixtures/roomFixtures.ts` の `roomWith` で作る。`roomWith` は毎回同じ `sequenceRandom` で作るので、読み直し用に何度作ってもホストのトークンは同じになる。開始済みの部屋は `roomWith` の後にホストのトークンで `start` する
- 並べ替えの結果を決めるため、`StartGame` に渡す乱数は `fixedRandom` を使う（例: 3 人の部屋に `[2, 0]` を渡すと「じろう → たろう → はなこ」）
- log の検査は `MemoryLogger` を `setLogger` で差し替え、`afterEach` で戻す（`JoinRoom.test.ts` と同じ）
- `describe("execute")` に置くテスト:
  - ホストのトークンで、2 人以上の待機中の部屋を始めるとき
    - ゲームが始まった部屋を保存する
    - メンバーを乱数で並べ替えた並びで保存する
    - 返す写しの進行状態が `started` で、並びが保存した部屋と一致し、トークンを含まない
    - 最後に更新した時刻を、時計の時刻にする
  - 部屋コードを、大文字小文字・前後の空白をそろえて探す（`" abc123 "` → `ABC123`）
  - 部屋コードの書式が誤りのとき、`room_not_found` を返して部屋を探さない
  - 部屋が無いとき、`room_not_found` を返して保存しない
  - 最後の更新から 24 時間たった部屋は `room_not_found` を返して保存しない。24 時間に 1 ミリ秒足りない部屋は始められる（境界）
  - 期限切れの部屋には、ホストのトークンでも、ホストでないトークンでも `room_not_found` を返す（ホストかより期限を先に見る）
  - ホストでないメンバーのトークン・どのメンバーのものでもないトークン・空のトークンのとき、`not_host` を返して保存しない（`it.each`）
  - メンバーがホスト 1 人だけのとき、`not_enough_members` を返して保存しない
  - 既に始まった部屋のとき
    - 保存しない（最後に更新した時刻も進めない）
    - 部屋の並びのまま、進行状態 `started` の写しを返す（並べ替えない。乱数を読まない `fixedRandom([])` を渡して確かめる）
    - ホストでないメンバーのトークンなら `not_host` を返す
  - 保存が 1 回衝突したとき
    - 部屋を読み直し、読み直した部屋で始めて保存する（`findByCode` 2 回・`save` 2 回）
    - 読み直した部屋が既に始まっていたら、保存せずに読み直した部屋の並びの写しを返す（二度押しが同時に届いた場合）
    - 部屋コードと回数を warn の log に出す
  - 衝突が上限まで続いたとき
    - error の log を出して throw する
    - 保存を 10 回で止める

  - `UC-03 要件 4: メンバーがホスト 1 人だけの部屋では開始できず、2 人以上で始められる旨が返る`
    - たろう 1 人の部屋で、たろうのトークンで開始する
    - 409 と `room.not_enough_members` が返る。部屋の状態の進行状態が `waiting` のまま
  - `UC-03 要件 4: メンバーが 2 人いれば開始でき、ゲームが始まった部屋が返る`
    - 「たろう」「はなこ」の部屋で、たろうのトークンで開始する
    - 200 が返る。進行状態が `started` で、members が同じ 2 人（並びは問わない）。はなこのトークンで取った部屋の状態も `started` になる
  - `UC-03 要件 5: ホスト以外のメンバーからの開始の要求は受け付けず、ゲームは始まらない`
    - 「たろう」「はなこ」「じろう」の部屋で、はなこのトークンで開始する
    - 403 と `room.not_host` が返る。進行状態が `waiting` のまま
  - `UC-03 要件 5: メンバーでない人からの開始の要求は受け付けず、ゲームは始まらない`
    - 別の部屋のメンバーのトークンと、トークン無しで試す（`it.each`）
    - 403 と `room.not_host` が返る。進行状態が `waiting` のまま
  - `UC-03 要件 6: 既にゲームが始まった部屋への開始の要求は無視され、描く順番は決め直されず、エラーも返らない`
    - `seedRoom` で `status: "started"`、8 人の部屋を書く（並びが描く順番）
    - ホストのトークンで開始する。200 が返り、members の並びが書いた並びのまま。部屋の状態の並びも同じ
  - `UC-03 要件 6: ホストが開始を 2 回続けて送っても、2 回目は一度目と同じ描く順番を返し、エラーも返らない`
    - 8 人の待機中の部屋で、ホストのトークンで 2 回続けて開始する
    - どちらも 200 で、2 回目の並びが 1 回目と同じ。部屋の状態の並びも同じ
  - `UC-03 要件 6: 開始の要求がほぼ同時に 2 回届いても、描く順番は 1 つに決まり、どちらにもエラーが返らない`
    - 8 人の待機中の部屋に、ホストのトークンで 2 つの開始を `Promise.all` で同時に送る
    - どちらも 200 で、2 つの応答の並びと部屋の状態の並びがすべて同じ
- 部屋が無い・期限切れ・部屋コードの書式誤りの 404 は、UC-03 に対応する基準が無いので結合テストを書かない（テスト名の先頭に置く ID が無い）。`StartGame.test.ts` が守り、route の 404 の詰め替え（`roomErrorResponse`）は uc-02 の結合テストが通している
- 500（衝突の使い切り）は、結合テストでは作らない。1.6.1 と同じ理由で、production の組み立てに故障を注入する口を開けない。単体テストが守る
- UC-03 要件 2・3（全員の画面の切り替え・同じ並びの表示）の ID はこの段のテストに置かない。通知は 1.9.1 で、ID を置くと `check:trace` が状態マークの不一致で止める

### apps/api

単体テストは置かない（1.6.1 と同じ理由）。新しい route の分岐（成功 200・403・409）は結合テストが HTTP 越しに通す。404 は単体テストと uc-02 の結合テストに任せる（上記）。

### 検証

周回中は、`npm run db:up` を済ませたうえで `npm run check:fast` を回す（結合テストを含む）。コミット前は `npm run check` を回す。E2E は含まない。

## 5. リスク・注意点

- **「決め直されない」を待機中の部屋から確かめるテストは、偶然の一致で通りうる。** 2 回目の開始が誤って並べ替えても、同じ並びになる確率は 8 人で 1/40320 残る（落ちるべきときに通る向きの揺れで、正しい実装が落ちることは無い）。乱数に左右されない確認は、開始済みの部屋を `seedRoom` で書くテストが受け持つ
- **同時の開始のテストの経路。** 2 つの要求が直列に届けば 2 つ目は読んだ時点で開始済み、並行に届けば負けた側が衝突して読み直す。どちらの経路でも結果（同じ並び・どちらも 200）は同じなので揺れない。衝突して読み直す経路は `StartGame.test.ts` と 1.5.1 の repository のテストが守る
- **`status` の enum の拡張。** 後続の移行単位で進行状態（ターン中・終了）が増えると、`RoomSnapshot.status` の enum に値が足される。画面（1.12.1〜）は `waiting` 以外を「始まった後」として扱う書き方にしておくと、値が増えても待機室に戻らない（docs/domain の「一度始まったら待機中に戻らない」）。1.11.1・1.12.1 の設計に引き継ぐ
- **進行状態の表現が 2 か所にある。** `RoomItemMapper`（DB の項目）と `toRoomSnapshotDto`（API の写し）が、それぞれ `hasStarted` から `"started" | "waiting"` を作る。境界ごとの表現なので共有しないが、値が増えるときは両方を直す
- **生成物の取り残し。** `openapi.yaml` を変えたら `npm run generate:api` を必ず回す（1.6.1・1.7.1 のリスクと同じ。`check` は気づかない）。`status` を足したのに生成物が古いと、`toRoomSnapshot` の `satisfies` が余分なプロパティとして型検査で止まるので、この段では気づける
- **「無い・期限切れ」の判断が 3 か所に入る。** 括り出しは見送った（1-2）。後続で同じ条件を書く use case が出たら、そこで括り出す
- **1.9.1 への引き継ぎ。** 開始の通知は「今回の要求で始まり、保存に成功した」ときだけ送る。`StartGame` のその分岐に publisher を入れ、二度目の開始（保存しない分岐）では送らない
