# 設計メモ: 1.8.1 WebSocket の接続の登録と送信（packages/realtime）

> タスクの範囲・変更ファイルの候補・束ね方は [tasks.md](../tasks.md) の 1.8.1 を正とし、ここには写さない。通知の経路と、ローカル・AWS の差を送信 adapter に閉じる方針は [docs/architecture/README.md](../../../../docs/architecture/README.md) の「操作と通知の経路を分ける」と「ローカルと AWS の構成の対応」を正とする。ここに書くのは、索引にも docs にも前の段のメモにも無い判断・確定した影響ファイル・テスト計画・リスク。

## 1. 実装方針

`packages/realtime` を新設する。**技術 module なので `domain` `application` `errors` を持たず、`src/` の直下に置く**（業務の判断を持たないため。依存方向は dependency-cruiser のルールで縛る。1-6）。room からは import しない。1.9.1 で `apps/api` が両方を組み立てる。

### 1-1. 依存の追加（`packages/realtime/package.json`）

| 依存 | 置き場 | 理由 |
| --- | --- | --- |
| `@aws-sdk/client-dynamodb`・`@aws-sdk/lib-dynamodb`（room と同じ `^3.1148.0`） | `dependencies` | 接続表への読み書き。room と同じく素の object で読み書きする |
| `ws`（`^8`。インストール時の最新） | `dependencies` | docs/architecture の「WebSocket（ローカル）」の選定 |
| `@types/ws`（`^8`） | `devDependencies` | `ws` の型。1-6 のとおり dependency-cruiser が `not-to-dev-dep` に当てた場合だけ `dependencies` へ移す |
| `@eshiritori/shared-kernel` | `dependencies` | `getLogger`（項目の形の誤り・送信の失敗の記録） |

- ルートの `package.json` は変えない。スクリプトが `@eshiritori/realtime` を import しても、1.5.1 の `@eshiritori/room` と同じく knip は報告しない見込み。報告された場合だけルートの `dependencies` に `"@eshiritori/realtime": "*"` を足す（1.5.1 のメモ 1-1 と同じ扱い）
- `tsconfig.json` は room と同じく `"types": ["node"]` を明示する（`node:http` `node:stream` `node:crypto` とテストの global の `WebSocket` を使う）

### 1-2. 接続表の定義（`src/connectionTable.ts`、新規）

`roomTable` と同じ形の定数 `connectionTable` を export し、`scripts/create-tables.ts` の `tables` に加える。

| 項目 | 値 | 理由 |
| --- | --- | --- |
| `name` | `eshiritori-connections` | 部屋の表と同じ接頭辞 |
| partition key | `roomCode`（S） | 通知は「部屋のメンバー全員へ」なので、部屋コードで一度に引く。GSI を使わないので、登録した直後の接続も強い整合の読み出しで必ず宛先に入る（1 秒以内の表示の前提） |
| sort key | `connectionId`（S） | 同じプレイヤーが複数のタブで開いても、接続ごとに 1 項目 |
| `timeToLiveAttributeName` | `expiresAt` | 切断の記録漏れ（プロセスの異常終了・AWS の `$disconnect` の取りこぼし）の掃除。`create-tables.ts` が全表に TTL を設定する作りなので、それにも合う |
| `BillingMode` | `PAY_PER_REQUEST` | 部屋の表と同じ |

- 定数にする理由と colocate テストを置かない理由は 1.5.1 の `roomTable` と同じ（振る舞いを持たない定義で、registry の実 DB テストがこの定義で作った表に対して通ることで確かめられる）
- AWS の `$disconnect` は接続 ID しか渡さないため、部屋コード無しで消すには `connectionId` の GSI が要る。**この段では足さない。** ローカルは接続を受けた時点で部屋コードを知っており（1-4 の `onClose` の closure）、送れなかった接続も部屋コード付きで消せるため。GSI は既存の表に後から足せるので、デプロイの要求で決める（要確認〔設計〕）

### 1-3. 接続の登録と検索（`src/DynamoDbConnectionRegistry.ts`、新規）

```ts
/** 部屋につながっている WebSocket の接続。 */
export interface RoomConnection {
  readonly roomCode: string;
  readonly connectionId: string;
  readonly playerId: string;
}

export class DynamoDbConnectionRegistry {
  constructor(client: DynamoDBDocumentClient, tableName: string);
  /** 接続を部屋に登録する。同じ接続をもう一度登録しても 1 件のまま（上書き）。 */
  register(connection: RoomConnection, connectedAt: Date): Promise<void>;
  /** 部屋に登録された接続をすべて返す。無ければ空配列。 */
  findByRoom(roomCode: string): Promise<RoomConnection[]>;
  /** 接続の登録を消す。無くても失敗しない。 */
  remove(roomCode: string, connectionId: string): Promise<void>;
}
```

- **識別子は `string` で受ける。** realtime は room に依存できない（1-6）ため `RoomCode` `PlayerId` を使えない。realtime にとって部屋コードとプレイヤー ID は「宛先をまとめる鍵」で、値の検証は room の側（1.9.1 の WebSocket の入口でトークンを確かめた後）で済んでいる。`RoomConnection` は domain object ではなく、表の 1 項目の形をそのまま表す記録（要確認〔設計〕）
- `playerId` は今の通知（全員に同じ内容）には要らないが、後続の「描き手だけにお題を送る」「接続が切れて戻る」で使うため、項目に持たせる。1 属性を足すだけで表の形は変わらない
- `register`: `PutCommand`（条件なし。同じ鍵なら上書きで冪等）。項目は `{ roomCode, connectionId, playerId, connectedAt: ISO 文字列, expiresAt: エポック秒 }`。`expiresAt = Math.ceil((connectedAt のミリ秒 + 24 時間) / 1000)`。24 時間は部屋の期限と同じ長さにする（期限切れの部屋への接続を残す意味が無いため）。モジュール内の定数 `CONNECTION_LIFETIME_MS` に置き、掃除のためだけの値で振る舞いの根拠にしないことをコメントに書く。時刻は引数で受ける（registry が時計を持たない。1.9.1 は composition の `clock` を渡す）
- `findByRoom`: `@aws-sdk/lib-dynamodb` の `paginateQuery` で `KeyConditionExpression: "#roomCode = :roomCode"`、`ConsistentRead: true`、`ProjectionExpression` で `roomCode` `connectionId` `playerId` だけを読む。ページ送りを自前の分岐で書かない（分岐が増えてもテストできないため。1 部屋は最大 8 人で 1 MB の上限に届かないが、ページ送りを省くと黙って宛先が欠ける）
- 読んだ項目は**型ガードを通してから** `RoomConnection` にする（[rules/development](../../../../rules/development/standard.md) の「外部入力を DTO として扱う前に runtime validation」）。3 属性のどれかが文字列でなければ `getLogger().error("保存された接続の項目の形が正しくありません", { roomCode, attribute })` を出して `throw new Error("Stored connection item is invalid: <attribute>")`。変換は 3 属性の取り出しだけなので、mapper の file は分けず registry の private 関数に置く（RoomItemMapper のような集約の復元を伴わないため）
- `remove`: `DeleteCommand`（条件なし。無い項目の削除も成功）
- 表が無いなど DynamoDB の例外は捕まえずに投げる（`DynamoDbRoomRepository` と同じ）

### 1-4. ローカルの送信と接続の受け入れ（`src/LocalWebSocketSender.ts`、新規）と送信の口（`src/WebSocketSender.ts`、新規）

**ローカルとの差を送信 adapter に閉じるため、送信の口を interface に切り出す。** AWS 版（Management API の `PostToConnection`）はデプロイの要求で同じ口に足す。1.9.1 の publisher はこの口だけを知る。

```ts
// src/WebSocketSender.ts
/** 送った結果。gone は接続がもう無い（切れた・知らない接続 ID）ことを表し、呼び出し側は登録を消す。 */
export type SendOutcome = "sent" | "gone";

/** 接続 ID を宛先に WebSocket で文字列を送る口。ローカルと AWS で実装を差し替える。 */
export interface WebSocketSender {
  send(connectionId: string, message: string): Promise<SendOutcome>;
}
```

```ts
// src/LocalWebSocketSender.ts
export class LocalWebSocketSender implements WebSocketSender {
  /** HTTP の upgrade 要求を WebSocket の接続として受け入れ、新しい接続 ID を返す。接続が切れたら onClose を 1 回呼ぶ。
   *  ハンドシェイクが成り立たずに socket が閉じたら reject する。 */
  accept(request: IncomingMessage, socket: Duplex, head: Buffer, onClose: (connectionId: string) => void): Promise<string>;
  send(connectionId: string, message: string): Promise<SendOutcome>;
  /** 受け入れたすべての接続を閉じる（サーバーの停止・テストの後始末）。 */
  closeAll(): Promise<void>;
}
```

- **realtime が公開する「ローカルの WebSocket サーバーの口」は `accept` にする**（1.9.1 への引き継ぎ）。`ws` の `WebSocketServer({ noServer: true })` を内部に 1 つ持ち、`handleUpgrade` を包む。HTTP サーバーの生成・`upgrade` イベントの購読・URL の解釈・トークンの確認・拒否の応答（`HTTP/1.1 401` を socket に書いて閉じる）は 1.9.1 の `apps/api/src/webSocketEndpoint.ts` が持つ。これで `apps/api` は `ws` を import せず、AWS では `accept` の代わりに API Gateway が接続を受ける。受け入れ（`accept`）は AWS 版に無いローカルだけの責務なので、interface には入れず `LocalWebSocketSender` の公開メソッドにする（要確認〔設計〕〔名前〕）
- 接続 ID は `node:crypto` の `randomUUID()`（AWS の接続 ID と同じく不透明な文字列）。`Map<string, WebSocket>` に持つ
- `onClose` は接続ごとに受ける。1.9.1 は `accept(..., (id) => registry.remove(roomCode, id))` のように部屋コードを closure に閉じ込めて渡す。`ws` の `close` を購読し、Map から外してから `onClose` を呼ぶ
- `accept` の reject: `ws` は不正な upgrade 要求（`Sec-WebSocket-Key` が無いなど）に 400 を書いて socket を壊し、コールバックを呼ばない。そのままだと Promise が永久に解決しないため、`handleUpgrade` の前に `socket.once("close", ...)` で reject を仕掛け、コールバックで外す
- `send`: Map に無い、または `readyState !== WebSocket.OPEN` なら `"gone"`。送れたら `"sent"`。`ws` の送信コールバックがエラーを返したら `getLogger().warn("WebSocket の送信に失敗しました", { connectionId, error })` を出して `"gone"`（呼び出し側が登録を消す。切断と同じ扱いでよい。DomainError ではなく通知の取りこぼしなので throw しない）
- `closeAll`: Map のすべての socket を `close()` し、`WebSocketServer` を閉じる

## 5. リスク・注意点

- **登録と切断の順序（1.9.1 への引き継ぎ）**: `accept` が解決してから `register` が終わるまでの間にクライアントが閉じると、`onClose` の `remove` が `register` より先に走り、登録が残る。残った登録は次の送信で `"gone"` になって消え（publisher が消す）、最悪でも TTL で消えるため、通知の誤配にはならない。1.9.1 で `onClose` の中で登録の完了を待ってから消すなどの手当てを判断する
- **ローカルは 1 プロセス前提**: `LocalWebSocketSender` の Map はプロセス内にしかない。`npm run start:api` を 2 つ立てると、片方のプロセスが受けた接続にもう片方からは送れず `"gone"` になり、登録が消される。ローカルの運用は 1 プロセス（docs/architecture の「Node 1 プロセス」）なので手当てしない
- **DynamoDB Local を起動し直した直後**: `-inMemory` なので接続表も消える。`npm run db:up` で作り直す（既存の手順どおり）
- **`ws` の `handleUpgrade` の挙動への依存**: 不正な要求でコールバックを呼ばない挙動は `ws` 8 の実装に依る。4-2 の reject のテストで固定する
- **global の `WebSocket` の型**: `@types/node` 22.20.5 の `web-globals/fetch.d.ts` が `var WebSocket` を宣言している（`lib` に DOM が無くても undici の型になる）ことを確かめた。テストの型検査は `types: ["node"]` で通る見込み
- **dependency-cruiser の型 package の扱い**: 1-6 のとおり、`@types/ws` を dev に置いて当たった場合は `dependencies` へ移す。ルールを緩めない

## 実装の記録

設計からの逸脱（理由付き）。

- **送信コールバックの成否の見分け方**: 設計は「コールバックがエラーを返したら `gone`」としたが、`ws` は成功時に `undefined` ではなく `null` を渡す。`error === undefined` では成功を失敗と取り違えるため、`error instanceof Error` で失敗を見分ける実装にした
- **「届かない」テストの組み立て**: 一方にだけ送ったとき、もう一方に届かないことを確かめるため、もう一方へは別の文字列を後から送り、受け取った最初のメッセージがその文字列であること（先の文字列が混ざっていないこと）で確かめた。固定の sleep を使わないための形
- `@types/ws` は `devDependencies` のまま `not-to-dev-dep` に当たらなかったので、移していない。ルートの `package.json` も変えていない（knip は報告しなかった）
- 上記以外は設計どおり（影響ファイルは設計メモの 15 件）
