## 1. 実装方針

### 1-2. `WaitingRoom`（`apps/web/src/components/WaitingRoom.tsx`、新規）

```ts
type RoomSnapshot = components["schemas"]["RoomSnapshot"];
/** 待機室の表示。開始の API 呼び出し・招待 URL のコピーは呼び出し側（1.12.1 のページ）が持つ。 */
export interface WaitingRoomProps {
  /** 最後に届いた部屋の写し（応答または通知）。 */
  room: RoomSnapshot;
  /** この画面を見ている本人のプレイヤー識別子。メンバー一覧の「あなた」と、ホストかどうかを決める。 */
  viewerPlayerId: string;
  /** 配信元のオリジン（例: https://eshiritori.example）。招待 URL を組み立てる。 */
  appOrigin: string;
  /** ホストが「開始」を押したとき。 */
  onStart: () => void;
  /** 「招待 URL をコピー」を押したとき。組み立てた招待 URL を渡す。 */
  onCopyInviteUrl: (inviteUrl: string) => void;
  /** 直前の開始の要求が返した ErrorResponse の code。無ければ誤りを出さない。 */
  startErrorCode?: string | undefined;
  /** 開始の要求中。ボタンを押せなくする。 */
  starting?: boolean | undefined;
}
export function WaitingRoom(props: WaitingRoomProps): ReactElement;
```

表示（上から）

1. 「部屋コード: K7Q2XM」（`room.code` をそのまま。全員）
2. ホストの画面だけ: 招待 URL の文字と、ボタン「招待 URL をコピー」
3. 「周回数: 1 周」（全員）
4. 見出し「メンバー（3/8）」と、`room.members` の並びのままの一覧（`<ul>`。見出しと `aria-labelledby` で結ぶ）。各行はニックネームに印を付ける: ホストかつ本人「たろう（ホスト・あなた）」、ホスト「たろう（ホスト）」、本人「じろう（あなた）」、それ以外は印なし
5. ホストの画面: 開始の誤り（`role="alert"`）とボタン「開始」。ホスト以外の画面: 「たろうさんが開始するのを待っています…」（ボタンは出さない）

判断

- **ホストかどうかは `room.hostPlayerId === viewerPlayerId` だけで決める。** 判断の再実装ではなく、写しの値の表示の出し分け。サーバーも開始を `room.not_host` で拒むので、出し分けが崩れても始まらない（UC-03 要件 5）
- **招待 URL は部品が `appOrigin` と `room.code` から組み立てる（`new URL(`/r/${room.code}`, appOrigin).href`）。** 招待 URL を props で受けると、story は渡した文字列が出ることしか確かめられず、「その部屋に直接入れる URL」（UC-01 要件 2）を観測できない。オリジンを受けて組み立てれば、story が部屋コードと URL の対応を確かめられ、`window.location` を読まないので story の結果が実行環境に左右されない。`/r/` の形は 1.12.1 のページの URL の読み取りと 2 か所になる（要確認〔設計〕）
- **招待 URL とコピーはホストの画面にだけ出す。** `room.html`・`room-design.html` とも、ホスト以外の待機室は部屋コードだけを描いている（要確認〔仕様〕）
- **コピーは呼び出し側に任せる（`onCopyInviteUrl`）。** `navigator.clipboard` は安全な配信元でしか使えず、jsdom にも無い。部品から外すと story が呼び出しを `fn()` で確かめられる。コピーできたことの表示（「コピーしました」）はシナリオにも見た目の正にも無いので作らない
- **「開始」はメンバーが 1 人でも押せる。** 押すとサーバーが `room.not_enough_members` を返し、「2 人以上で始められます」を出す（`room-design.html`「押すと『2 人以上で始められます』」）。見た目の正はこのときボタンを灰色に描いているが、灰色にするには画面が「2 人以上か」を数えることになり、判断の再実装に当たるので付けない。全体のスタイルは 1.12.1 以降（要確認〔設計〕）
- **「メンバー（3/8）」の 8 は表示の定数として部品に持つ（`ROOM_CAPACITY = 8`）。** 写しに上限は無く、見た目の正が描いているため。満員の判断はサーバーが持ち、画面は数を出すだけ（1.10.1 の周回数の選択肢 `ROUND_COUNT_CHOICES` と同じ扱い。要確認〔仕様〕）
- **ホスト以外の待つ表示は、ホストのニックネームを入れる**（`room-design.html` の「たろうさんが開始するのを待っています…」。シナリオフェーズの `room.html` は「ホストが開始するのを待っています…」で、詰めた方に合わせる）。`room.members` にホストが見つからない写しは契約上起きないが、型の上では起こりうるので「ホストが開始するのを待っています…」に寄せる
- 状態は持たない（`useState` を使わない）。誤りを消すのは、開始を押し直すときの呼び出し側
- 誤りの色は 1.10.1 と同じく `crimson` だけを当てる

## 5. リスク・注意点

- **`check:trace` の状態マーク。** story に ID を書く変更と「（未実装）」を外す変更は同じ段で入れる。片方だけだと `check:trace` が落ちる。UC-02 要件 1・10、UC-03 要件 2 の ID はコメントにも書かない
- **`new URL` とオリジンの末尾。** `appOrigin` に末尾のスラッシュやパスが付いていても `new URL("/r/K7Q2XM", origin)` はオリジン直下に組み立てる。文字列の連結にすると `//r/` になりうるので使わない
- **一覧の見出しの文字で list を引く。** 見出しの文字に人数が入るので、story ごとに `name` が変わる。`aria-labelledby` の付け忘れは `getByRole("list", { name })` が見つからずに落ちる（意図どおり）
- **非ホストの待つ表示の「…」は 1 文字の三点リーダー（U+2026）。** 見た目の正と同じ文字を story に書く
- **古い写しが後から届く件（1.9.1 で先送り）。** 部品は渡された写しをそのまま出すだけなので、この段では影響しない
- **1.12.1 への引き継ぎ:** (1) `status` が `waiting` なら `WaitingRoom`、それ以外は `DrawingOrderView` を出す、(2) `appOrigin` は `window.location.origin` を渡す、`/r/{部屋コード}` の読み取りは `WaitingRoom` の組み立てと同じ形にする、(3) `onCopyInviteUrl` で `navigator.clipboard.writeText` を呼ぶ（失敗の扱いはそこで決める）、(4) 開始を押し直す前・メンバーが増えたときに `startErrorCode` を消すのは呼び出し側、(5) `viewerPlayerId` は応答の `player.playerId` または `GetRoomResponse.playerId`
