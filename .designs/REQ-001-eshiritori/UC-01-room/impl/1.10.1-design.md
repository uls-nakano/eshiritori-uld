> この段の範囲・観測点・束ね方は [tasks.md](../tasks.md) の 1.10.1 に従い、ここには写さない。受け入れ基準は [UC-01](../../../../docs/usecases/UC-01-部屋を作って仲間を招く.md) 要件 3（と既に効いている要件 4・5）、[UC-02](../../../../docs/usecases/UC-02-招待された部屋に入る.md) 要件 4・6〜9 の誤りの表示に従う。見た目は [mockups/room-design.html](../mockups/room-design.html) の「トップ」「参加画面」、技術は [docs/architecture/README.md](../../../../docs/architecture/README.md) の「技術の選定」に従う。API 契約（`CreateRoomRequest`・`JoinRoomRequest`・`ErrorResponse`）は [1.6.1](1.6.1-design.md)・[1.7.1](1.7.1-design.md) のメモに従う。ここに書くのは、それらに無い判断、確定した影響ファイル、テスト計画、リスク。

## 1. 実装方針

順序は ワークスペースの立ち上げ（package・tsconfig・Storybook・story を走らせるテスト）→ 検証の配線（ESLint・knip・dependency-cruiser・ルートの scripts）→ 誤りの文言の対応 → `CreateRoomForm` と story → `JoinRoomForm` と story → 生き資料。各 component は story（play 関数）を先に書いて落ちることを確かめてから実装する。

domain・application・adapter・API 契約は変えない。`apps/web` は表示だけを持ち、業務の判断（ニックネームの長さ・周回数の範囲・部屋コードの正規化）を再実装しない。

### 1-2. story の play 関数を `npm run check` で走らせる（`apps/web/src/stories.test.ts`、新規）

**Storybook の portable stories（`composeStories`）を Vitest の jsdom で走らせる。** `@storybook/addon-vitest`（Vitest の browser mode と Playwright の Chromium）は採らない。

- 採らない理由: (1) `npm run check` にブラウザの起動が入り、検証が重くなる（規約は E2E を重いという理由で `check` から外している）、(2) 新しい環境ではブラウザの取得（`playwright install`）が `check` の前提に加わる、(3) 1.13.1 で `tests/` に入る `@playwright/test` と Playwright の版をそろえる必要が生まれ、段をまたいだ結合ができる
- 捨てる性質: 実ブラウザでの描画差は確かめられない。この段のフォームはラベル・入力・選択・ボタン・誤りの文言だけで、jsdom で表示の基準を判定できる。実ブラウザの経路は 1.13.1 の E2E が持つ

```ts
// apps/web/src/stories.test.ts の形
const annotations = setProjectAnnotations([previewAnnotations]);
beforeAll(annotations.beforeAll);
const storyFiles = import.meta.glob<StoryFile>("./**/*.stories.tsx", { eager: true });
for (const [path, storyFile] of Object.entries(storyFiles)) {
  describe(path, () => {
    for (const story of Object.values(composeStories(storyFile))) {
      it(story.storyName, async () => { await story.run(); });
    }
  });
}
```

- story を足すたびにテストを書かなくてよいように、glob で全 story を拾う。1.11.1・1.12.1 の story も同じテストで走る
- `describe` は対象の関数が無いので story ファイルのパスにする（[rules/testing](../../../../rules/testing/standard.md) の「対象となる関数が存在しない場合は例外」）。`it` 名は story の `name`（日本語）
- 受け入れ基準 ID はこのファイルには置かない（各 story の play 関数のコメントに置く）

### 1-3. 検証の配線

- **ルートの `package.json`**
  - scripts に `test:stories`（`npm run test:stories -w @eshiritori/web`）と `storybook`（`npm run storybook -w @eshiritori/web`）を足す
  - `check` と `check:fast` の 2 段目（`lint` `typecheck` などの並列の段）に `test:stories` を足す。DB を使わないので `check:db` のレーンには入れない
  - `typecheck` は `--workspaces --if-present` で `apps/web` の `typecheck` を拾うので変えない
  - knip の `apps/*` の `project` を `src/**/*.{ts,tsx}` にする（`.tsx` を対象に入れないと、component と story が検査から漏れる）。entry は knip の Storybook・Vitest・Vite の plugin が `apps/web` の依存から有効になり、story・`.storybook/*`・`*.test.ts`・`vite.config.ts` を拾う想定。拾えなければ `apps/web` 専用の `entry` を足す
  - devDependencies に `eslint-plugin-react-hooks`（^7.1）を足す
- **`eslint.config.js`**
  - 型付きの対象の `files` に `apps/**/*.tsx` を足す（今は `apps/**/*.ts` だけで、`.tsx` が lint されない）
  - `apps/**/*.tsx` に `eslint-plugin-react-hooks` の推奨設定を当てる（hooks の呼び出し順の誤りを検出する）
  - default export が要るファイル（`apps/web/**/*.stories.tsx` の meta、`apps/web/.storybook/*.ts`、`apps/web/vite.config.ts`）だけ `no-restricted-exports` を切る override を足す。component は named export のまま
- **`.dependency-cruiser.cjs`**
  - `web-depends-only-on-api-contract` を足す: `from: ^apps/web/` → `to: ^(packages|apps)/`、`pathNot: ^(apps/web|packages/api-contract)/`。画面が `room` の domain や `apps/api` を import して判断を再実装する経路を塞ぐ（[docs/architecture](../../../../docs/architecture/README.md) の「package と境界」の `apps/web` の行）
  - `not-to-dev-dep` の `pathNot` を `TEST` から、テストに加えて story・`.storybook/`・`apps/web/vite.config.ts` も除く正規表現（定数 `DEV_ONLY` を新設）に替える。`TEST` は shared kernel と domain の規則でも使うので書き換えない。component（`CreateRoomForm.tsx` など）は devDependencies を import できないままにする

### 1-4. 誤りの文言の対応（`apps/web/src/components/formErrorMessages.ts`、新規）

```ts
/** 誤りを表示する場所。field は入力欄の下、form はボタンの上。 */
export type FormErrorPlace = "nickname" | "roundCount" | "roomCode" | "form";
/** API の ErrorResponse.code を、表示する文言と場所に対応させる。 */
export function describeFormError(code: ErrorResponse["code"]): { place: FormErrorPlace; message: string };
```

| code | 場所 | 文言 |
| --- | --- | --- |
| `room.nickname_empty` | nickname | ニックネームを入れてください |
| `room.nickname_too_long` | nickname | ニックネームは 10 文字までです |
| `room.round_count_out_of_range` | roundCount | 周回数は 1〜5 の間で指定してください |
| `room.room_not_found` | roomCode | 部屋が見つかりません |
| `room.room_full` | form | 満員のため入れません |
| `room.game_already_started` | form | ゲーム中のため入れません |
| `room.nickname_taken` | nickname | 同じニックネームの人がいます。別のニックネームにしてください |
| 上記以外（`request.invalid_body`・`server.internal_error`・未知の code） | form | うまくいきませんでした。時間をおいてもう一度試してください |

- 文言はシナリオと `room-design.html` のとおり。最後の行（想定外の誤り）だけはどこにも書かれていない新しい文言（要確認〔仕様〕）
- **2 つのフォームで 1 つの対応表を共有する。** ニックネームの誤りは両方に出るため、フォームごとに持つと文言が食い違いうる
- `ErrorResponse["code"]` は契約上ただの `string` なので、`switch` の `default` で未知の code を受ける。code を列挙型にする契約の変更はしない（新しい code が増えても画面が落ちず、想定外の文言に寄るだけで済む）
- 単体テストは置かない。対応表の各行は 2 つの story の play 関数が文言を直接書いて確かめる（文言をこのファイルから import して期待値にしない。実装の写しのテストになるため）

### 1-5. `CreateRoomForm`（`apps/web/src/components/CreateRoomForm.tsx`、新規）

```ts
type CreateRoomRequest = components["schemas"]["CreateRoomRequest"];
/** トップの「部屋を作る」欄。送信と API の呼び出しは呼び出し側（1.12.1 のページ）が持つ。 */
export interface CreateRoomFormProps {
  /** 入力を送るとき。nickname は入力のまま（前後の空白を除かない）、roundCount は数値。 */
  onSubmit: (request: CreateRoomRequest) => void;
  /** 直前の送信が返した ErrorResponse の code。無ければ誤りを出さない。 */
  errorCode?: string | undefined;
  /** 送信中。ボタンを押せなくし、二重に部屋を作らないようにする。 */
  submitting?: boolean | undefined;
}
export function CreateRoomForm(props: CreateRoomFormProps): ReactElement;
```

- 見出し「部屋を作る」、ラベル付きのニックネームの入力欄（補足「10 文字まで」）、周回数の選択欄（ラベル「周回数」、選択肢 1〜5 を「1 周」〜「5 周」で、最初は 1）、ボタン「部屋を作る」
- `<form>` の submit（Enter キーを含む）で `preventDefault` して `onSubmit` を呼ぶ。入力欄と選択欄の値は component の state に持つ（誤りが出ても入力は消さない）
- **画面では入力を検査しない。** ニックネームの空・長さは送ってサーバーの code で表示する。`maxLength` 属性も付けない（`maxLength` は UTF-16 の単位で数え、絵文字 1 つを 1 文字と数えるサーバーの判断（1.2.1）と食い違う。食い違うと、サーバーなら通る名前を画面が切り詰める）。要確認〔設計〕
- 周回数の選択肢 1〜5 は UC-01 要件 3 の表示の仕様として component に定数で持つ（`ROUND_COUNT_CHOICES`）。範囲外の誤りの判断はサーバーが持ち、画面は code を表示するだけ
- 誤りは `describeFormError` の場所に応じて、該当の入力欄の下（`aria-invalid` と `aria-describedby` で欄と結ぶ）か、ボタンの上に `role="alert"` で出す
- id は `useId()` で作る。1.12.1 でトップに 2 つのフォームが並んでも、ラベルと入力欄の結び付きが重ならないようにするため
- 見た目は意味を持つところ（誤りの色）だけに当て、レイアウトの作り込みはしない（要確認〔設計〕）

- 単体テスト: 置かない。component と対応表は表示の振る舞いだけを持ち、story が観測点を兼ねる。`apps/web` はカバレッジの計測対象（ルートの `vitest.config.ts` は `packages/*` だけ）に入れない。presentation は 100% の必須対象ではない（[rules/testing](../../../../rules/testing/standard.md) の「カバレッジ」）
- 機械チェック: `check:trace`（UC-01 要件 3 の状態マークとテストの一致）、`check:boundaries`（新しい規則）、`lint`（`.tsx`）、`lint:unused`、`typecheck`、`format:check`
- 手で 1 回: `npm run storybook` で起動し、2 つの component の story が開けることを確かめる（`.storybook/main.ts` は jsdom のテストでは読まれないため）

## 5. リスク・注意点

- **規模が上限 15 を超える（18 件）。** 実装に入る前に人の判断が要る。分ける場合の案は、`JoinRoomForm` とその story を 1.11.1 へ移す（この段 16 件・1.11.1 は 6 件）。それでもこの段は 15 を 1 件超えるため、推奨は分けずに進めること（増えた分は生成物・写し・1 語の削除と、検証の配線で、読む量は 11 ファイル）
- **TypeScript の `include` に `.storybook` を明示する。** ドットで始まるフォルダはワイルドカードでは拾われないため、`"src"` だけだと `.storybook/*.ts` が型付き lint で「project service に見つからない」と落ちる
- **dependency-cruiser の `combinedDependencies: true`。** ルートと `apps/web` の devDependencies は story・設定ファイル以外から import できない。component が `storybook/test` などを誤って import すると `not-to-dev-dep` で落ちる（意図どおり）
- **knip の plugin の検出。** `apps/web` の `vitest`・`storybook`・`vite` の plugin が有効にならないと、`stories.test.ts`・story・`.storybook/*` が「使われていないファイル」、`jsdom` が「使われていない依存」と出る。出たら `apps/web` の `entry` を明示するか `ignoreDependencies` に理由付きで足す
- **portable stories の後片付け。** `story.run()` は story ごとに描画先を作る。play 関数は `within(canvasElement)` で引くので前の story の DOM が残っても取り違えないが、`screen` は使わない
- **jsdom の `<select>` と `userEvent.selectOptions`。** `value` は文字列で返るので、`onSubmit` の前に数値にする（`Number`）。story が `roundCount: 3`（数値）で確かめるので、文字列のまま渡す誤りは落ちる
- **1.12.1 への引き継ぎ:** (1) `index.html` はこの段に無い（`src/main.tsx` と一緒に作る）、(2) 部屋コードが空のまま送られたときの扱い（API を呼ばずに `room.room_not_found` の文言を出すのが自然。`/rooms//members` を呼ぶと契約外の 404 になる）、(3) 通信そのものの失敗は `errorCode` に `server.internal_error` などを渡せば想定外の文言になる、(4) 再送の前に `errorCode` を消すのは呼び出し側、(5) 参加画面の story に UC-02 要件 1 の ID を置き、そこで「（未実装）」を外す
- **`scenarios.md` の「結合テストへの対応」は更新しない。** S-01-01・02・15〜17 は結合テストで「実装済み」になっており、この段の story は表示の側の追加検証にあたる

## 実装の記録

設計からの逸脱（数字は書かない）。

- `apps/web/tsconfig.json` の `include` を `.storybook`（ディレクトリ）でなく `.storybook/*.ts` にした。ディレクトリ指定だと `main.ts` が型付き lint の project service に見つからなかったため

- `apps/web/index.html` は設計どおり作らず 1.12.1 へ移した
