# 設計メモ: 1.6.1 部屋を作る API

> この段の範囲、変更ファイルの候補、束ね方は [tasks.md](../tasks.md) の 1.6.1 に従い、ここには写さない。受け入れ基準は [docs/usecases/UC-01-部屋を作って仲間を招く.md](../../../../docs/usecases/UC-01-部屋を作って仲間を招く.md)、層と技術の当てはめは [docs/architecture/README.md](../../../../docs/architecture/README.md) に従う。ここには、索引にもモデル docs にも前の段のメモにも無いものだけを書く。具体的には、判断、確定した影響ファイル、テスト計画、リスク。

## 1. 実装方針

ボトムアップで進める。順序は application（`CreateRoom`）、API 契約（OpenAPI と生成）、composition root（`apps/api`）、結合テスト（`tests/`）。domain と adapter の中身は変えない。

### 1-1. 依存の追加

| 依存 | 置き場 | 理由 |
| --- | --- | --- |
| `hono`（^4） | `apps/api` の `dependencies` | HTTP のルーティング。docs/architecture の選定どおり |
| `@hono/node-server`（^2） | `apps/api` と `tests` の `dependencies` | ローカルで Node の HTTP サーバーとして待ち受けるため。`tests` はポート 0 で待ち受けるのに使う（1-6） |
| `@aws-sdk/client-dynamodb`、`@aws-sdk/lib-dynamodb`（room と同じ範囲） | `apps/api` の `dependencies` | composition が client を作り、`DynamoDbRoomRepository` に渡すため |
| `@aws-sdk/client-dynamodb` | `tests` の `dependencies` | DB の起動を確かめる `DescribeTable` に使う（1-6） |
| `openapi-typescript`（^7） | ルートの `devDependencies` | 型の生成。実行時には import しない |
| `overrides: { "openapi-typescript": { "typescript": "$typescript" } }` | ルートの `package.json` | openapi-typescript 7.13 の peer は `typescript@^5.x` で、`~6.0.3` だと `npm install` が ERESOLVE で止まる。`/tmp` で試して確かめた。overrides を付けると入り、TS 6.0.3 の下で生成も型検査も通った |

- `apps/api` が import する npm package は、ルートの `devDependencies` に置かない。1.5.1 と同じ理由で、`combinedDependencies` によって `not-to-dev-dep` に当たる
- workspace 内の依存は `"*"` で宣言する。内訳は次のとおり。
  - `apps/api`: `@eshiritori/room`、`@eshiritori/shared-kernel`、`@eshiritori/api-contract`
  - `tests`: `@eshiritori/api`、`@eshiritori/api-contract`

### 1-2. application（`packages/room/src/application/`）

#### `Clock.ts`

```ts
/** 時計。use case が「いま」を受け取る port。 */
export interface Clock {
  /** 現在時刻。 */
  now(): Date;
}
```

- domain の `RandomSource` とは違い、`Clock` は domain に置かない。domain は時刻を引数で受け取るので（`Room.create(…, now, …)`）、時刻を読むのは use case だけになる。rules/architecture の「port は application に置く」に従う
- 実装は composition root のオブジェクトリテラル `{ now: () => new Date() }` にする。1 行の adapter のためにファイルとテストを増やさない

#### `RoomSnapshotDto.ts`

API に返す部屋の写しの DTO と、集約から DTO への変換を置く。

```ts
export interface MemberDto { readonly playerId: string; readonly nickname: string }
export interface RoomSnapshotDto {
  readonly code: string;
  readonly roundCount: number;
  readonly hostPlayerId: string;
  readonly members: readonly MemberDto[];
}
export function toRoomSnapshotDto(room: Room): RoomSnapshotDto
```

- **メンバーのトークンを入れない。** トークンは本人だけが持つ秘密で、メンバー一覧は全員に配るため（1.4.1 のリスク）
- **ホストの印は `hostPlayerId` で表し、メンバーごとの `isHost` は持たない。** 集約と同じ表し方にそろえる。画面は ID を比べて印を付けるだけで、業務の判断ではない
- **進行状態（`status`）はこの段では持たない。** 作った直後の部屋は必ず待機中なので、`started` の分岐は use case のテストから到達できない。入れると application のカバレッジ 100% のためだけにテストファイルが 1 件増える。進行状態を返す必要が出る段（1.7.1 の `GetRoom`、1.7.2）で、OpenAPI と一緒に足す（要確認〔設計〕）
- メンバーの並びは集約の並びを保つ（開始前は入った順）

#### `CreateRoom.ts`

```ts
export interface CreateRoomInput { readonly nickname: string; readonly roundCount: number }
export interface CreateRoomOutput {
  readonly room: RoomSnapshotDto;
  readonly playerId: string;     // 作った人（ホスト）のプレイヤー識別子
  readonly playerToken: string;  // 作った人のプレイヤートークン。この応答でだけ返す
}
export class CreateRoom {
  constructor(repository: RoomRepository, random: RandomSource, clock: Clock)
  execute(input: CreateRoomInput): Promise<Result<CreateRoomOutput, RoomError>>
}
```

処理の流れ:

1. `Nickname.create(input.nickname)` を呼ぶ。失敗はそのまま `failure` で返す
2. `RoundCount.create(input.roundCount)` を呼ぶ。失敗はそのまま返す。両方とも誤りのときは、ニックネームの誤りを返す（画面の入力欄の並びの順）
3. 最大 `MAX_CREATE_ATTEMPTS = 3` 回、次を繰り返す
   - `Room.create(nickname, roundCount, clock.now(), random)` で部屋を作る
   - `repository.save(room)` で保存する
   - 成功なら `success({ room: toRoomSnapshotDto(room), playerId: room.host.playerId.value, playerToken: room.host.token.value })` を返す
   - `save_conflict` なら `getLogger().warn("部屋コードが既にある部屋と重なったため作り直します", { roomCode, attempt })` を出して、次の回へ進む
4. 3 回とも衝突した場合は、`getLogger().error("部屋コードが重なり続けたため部屋を作れませんでした", { attempts })` を出し、`Error("Could not allocate a unique room code.")` を throw する

- **新しい部屋の保存の衝突は、部屋コードの重なりとみなす。** 新しい部屋の改訂番号は必ず initial で、repository の条件は「同じ部屋コードが無いこと」だけなので、`revision.isInitial()` で見分けるまでもない
- **作り直すときは、部屋ごと作り直す。** 部屋コードだけを差し替える口は集約に無い。メンバーの識別子とトークンも作り直されるが、まだ誰にも返していないので問題ない
- **上限は 3 回にする。** 部屋コードは 36^6 ≒ 21.8 億通りある。生きている部屋の数を考えると 1 回重なるのも稀で、3 回続けて重なるのは乱数の源の故障とみなしてよい。上限を置かないと、故障したときに要求が終わらない
- **使い切ったときは業務の失敗（`RoomError`）にせず throw する。** 利用者が入力を直しても解消しない失敗で、`RoomErrorCode` に足すと画面の文言の対応表にも残り続けるため。API は 500 を返す（1-4）
- **repository が投げる例外（DB に接続できないなど）は捕まえない。** rules/development の変換の規則は「捕捉する場合」が対象で、ここでは捕捉しない。composition root の共通のエラー処理が 500 にする
- トークンをログに出さない

### 1-3. API 契約（`packages/api-contract`）

#### `openapi.yaml`（OpenAPI 3.1）

| 項目 | 内容 |
| --- | --- |
| `POST /rooms`（`operationId: createRoom`） | 本文は `CreateRoomRequest`（必須）。`201` は `CreateRoomResponse`、`400` と `500` は `ErrorResponse` |
| `CreateRoomRequest` | `nickname: string`、`roundCount: integer`。どちらも required |
| `CreateRoomResponse` | `room: RoomSnapshot`、`player: PlayerCredential` |
| `RoomSnapshot` | `code: string`、`roundCount: integer`、`hostPlayerId: string`、`members: RoomMember[]` |
| `RoomMember` | `playerId: string`、`nickname: string` |
| `PlayerCredential` | `playerId: string`、`playerToken: string`（応答を受けた本人だけが持つ） |
| `ErrorResponse` | `code: string`、`detail: string` |

- **値の制約（`minLength`・`maxLength`・`minimum`・`maximum`）は schema に書かない。** 規則の正は domain にある。schema に書くと 2 か所に分かれる。さらに `maxLength` はコードポイントで数えるので、domain が書記素で数える 10 文字とずれる（絵文字で食い違う）。制約は `description` に文章で書き、domain の誤りの `code` で返すことを明記する
- **`ErrorResponse.code` は enum にせず `string` にする。** enum にすると `RoomErrorCode` を契約にも手で写すことになり、同期の手段が無い。取りうる値は `description` に列挙する（`room.<…>` と、1-4 の要求の誤りの 3 件）。画面の対応表（1.10.1）を作るときに enum にする必要が出たら、そこで見直す
- 招待 URL は応答に入れない（要確認〔設計〕）。招待 URL は画面の URL の構成（`/r/{部屋コード}`。1.12.1）と配信元のオリジンで決まり、API はどちらも知らない。画面が部屋コードから組み立てる

#### 生成と公開

- `packages/api-contract/package.json` に次を置く。
  - `"scripts"`: `"generate": "openapi-typescript openapi.yaml -o src/generated/schema.ts && prettier --write src/generated/schema.ts"` と `"typecheck": "tsc --noEmit"`
  - `"exports"`: `{ ".": "./src/index.ts" }`
- ルートの `package.json` に `"generate:api": "npm run generate -w @eshiritori/api-contract"` を置く
- **生成の後に Prettier をかける。** openapi-typescript の出力は 4 スペースのインデントで、`format:check`（対象は `**/*.ts`）に当たる。`.prettierignore` を足すより、生成のコマンドで整える方が変更するファイルが少ない。ESLint はもともと `**/generated/**` を除外しているので変えない
- `src/index.ts` は `export type { components, paths } from "./generated/schema";` だけにする。各 schema の別名（`CreateRoomRequest` など）は、使う側が `components["schemas"]["…"]` で引く。別名を契約の package に並べると、schema を足すたびに手で書き足す場所が増える
- 生成物はコミットする（ビルドしない方針。1.1.1）

### 1-4. composition root（`apps/api`）

`package.json` は次の内容にする。

- `name`: `@eshiritori/api`
- `exports`: `{ ".": "./src/composition.ts" }`
- `scripts`: `"start": "tsx src/main.ts"` と `"typecheck": "tsc --noEmit"`

`tsconfig.json` は room と同じ形にする（`types: ["node"]`）。Hono と `@hono/node-server` は、`lib: ES2022` と `types: ["node"]` だけで型検査が通る。`/tmp` で TS 6.0.3 を使って確かめた。

#### `createApp.ts`

```ts
export interface ApiUseCases { readonly createRoom: CreateRoom }
export function createApp(useCases: ApiUseCases): Hono
```

`POST /rooms` の処理:

1. `await c.req.json()` で本文を読む。例外が出たら `400 { code: "request.invalid_json", detail: "Request body must be valid JSON." }` を返す
2. 型ガード `isCreateRoomRequest(body: unknown): body is components["schemas"]["CreateRoomRequest"]` を通す。オブジェクトであること、`nickname` が string、`roundCount` が number であることを確かめる。外れたら `400 { code: "request.invalid_body", detail: "…" }` を返す。値の範囲は見ない（domain の仕事）
3. `createRoom.execute({ nickname, roundCount })` を呼ぶ。失敗なら `statusOf(error)` の status と `{ code: error.code, detail: error.detail }` を返す
4. 成功なら、DTO を `CreateRoomResponse` に詰め替えて `201` で返す。応答は `satisfies components["schemas"]["CreateRoomResponse"]` で契約と突き合わせる

- **`statusOf(error: RoomError)` は `RoomErrorCode` の 9 件すべてを網羅する `switch` にする。** 対応は次のとおり。
  - 400: 入力の誤り 3 件
  - 404: `room_not_found`
  - 409: `room_full`・`game_already_started`・`nickname_taken`・`not_enough_members`
  - 403: `not_host`

  全件を網羅しないと、`switch` の戻り値の型が閉じない。1.7.x はこの関数を使い回す
- **要求の形の誤りと値の誤りを分ける**（rules/development の「JSON parse error と値の validation error を混ぜない」）。周回数が数でない（`"3"`）場合や、`roundCount` が無い場合は `request.invalid_body` にする。`room.round_count_out_of_range` は、数として届いた値が 1〜5 の整数でない場合だけにする（要確認〔仕様〕）
- **`app.onError` で予期しない例外を 500 にする。** `getLogger().error("API の処理中に予期しない例外が起きました", { method, path, errorName, stack })` を出し、`500 { code: "server.internal_error", detail: "Internal server error." }` を返す。context の `stack` には、例外が持つ stack を渡す（logger が自分の frame で上書きしないため）。本文やトークンは log に出さない

#### `composition.ts`

```ts
export interface ApiConfig {
  readonly port: number;
  readonly dynamoDbEndpoint: string;
  readonly roomTableName: string;
}
export function readApiConfig(env: Readonly<Record<string, string | undefined>>): ApiConfig
export function createDynamoDbClient(config: ApiConfig): DynamoDBClient
export function composeApp(config: ApiConfig): Hono
```

- `readApiConfig` は環境変数を読む。`PORT` の既定は `3000`、`DYNAMODB_ENDPOINT` の既定は `http://localhost:8000`。後者は 1.5.1 のスクリプトやテストと同じ名前と既定値にする。`roomTableName` は環境変数にせず、`roomTable.name` で固定する（AWS の環境ごとに変える口は、デプロイの要求で足す）
- `PORT` が整数でないときは、`getLogger().error` で値を出してから throw する（起動の時点で落とす）
- `createDynamoDbClient` の設定は次のとおり。認証情報が固定なので、誤って AWS の表に向くことは無い。AWS 向けは別の要求で足す
  - endpoint は設定から取る
  - region は `ap-northeast-1`
  - 認証情報は `local`/`local`（DynamoDB Local は英数字のキーしか受け付けない）
- `composeApp` の手順:
  1. `DynamoDBDocumentClient.from(createDynamoDbClient(config))` を作る
  2. それを使って `new DynamoDbRoomRepository(client, config.roomTableName)` を作る
  3. `new CryptoRandomSource()` と、時計 `{ now: () => new Date() }` を用意する
  4. `new CreateRoom(…)` を作る
  5. `createApp({ createRoom })` を返す
- 結合テストは `readApiConfig(process.env)` と `composeApp` をそのまま使う（rules/acceptance-testing の「composition root の production と同じ手順」）

#### `main.ts`

`const config = readApiConfig(process.env)` のあと `serve({ fetch: composeApp(config).fetch, port: config.port }, …)` を呼ぶ。待ち受けを始めたら `getLogger().info("API サーバーを起動しました", { port })` を出す。何も export しない。

- ローカル起動は `npm run start:api` にする。中身は、ルートの `package.json` の `"start:api": "npm run start -w @eshiritori/api"`。tsx は 1.5.1 でルートの devDependencies に入っている。room の source は拡張子なしで import するので、Node の型の除去では動かない（1.5.1 と同じ理由）
- Lambda 用の起動口は、デプロイの要求で足す（docs/architecture の「ローカルと AWS の構成の対応」の右の列）

### 1-6. `tests/` ワークスペース

- `tests/package.json` の内容:
  - `name`: `@eshiritori/tests`
  - `private`
  - `type: module`
  - `scripts`: `"test:integration": "vitest run"` と `"typecheck": "tsc --noEmit"`
- `tests/tsconfig.json` を新しく作る。room と同じ形で、`include: ["**/*.ts"]` にする。型検査と ESLint の projectService に要る（tasks.md に無い）
- `tests/vitest.config.ts` の設定:
  - `include: ["integration/**/*.integration.test.ts"]`
  - 待ち受けの起動と DB を含むので、`testTimeout` は既定より長くする（10 秒）
  - ルートの `vitest.config.ts` は `packages/*/src` だけを拾うので、ルートの `npm test` と `coverage` には入らない
- `tests/integration/support/startServer.ts` の関数:

  ```ts
  export interface TestServer {
    readonly baseUrl: string;
    postJson<TBody>(path: string, body: unknown): Promise<{ status: number; body: TBody }>;
    close(): Promise<void>;
  }
  export async function startServer(): Promise<TestServer>
  ```

  手順は次のとおり。
  1. `readApiConfig(process.env)` を呼ぶ
  2. `createDynamoDbClient(config)` で `DescribeTable(config.roomTableName)` を試す。表の名前は設定から取り、tests を `@eshiritori/room` に依存させない。失敗したら、「DynamoDB Local に接続できないか、部屋の表がありません。`npm run db:up` を実行してください」と元の例外の名前を含めた `Error` を投げる（rules/testing/project.md）
  3. `composeApp(config)` を作る
  4. `serve({ fetch, port: 0 }, (info) => …)` で空いているポートに待ち受ける
  5. `close` で `server.close()` を Promise にして返す。keep-alive の接続が残ると止まらないので、先に `closeAllConnections()` を呼ぶ

  `postJson` は `fetch` の結果を `as TBody` で受ける。これは唯一のキャストで、テストのハーネスが、生成型を指定して応答を受けるためのもの。理由をコメントに残す。Node の型では `Response.json()` が `unknown` を返すため、キャストが要る。

- **結合テストは前提を DB に直書きしない。** この段のテストは部屋の無い状態から始まる
- **検証は HTTP の応答だけで行う。** rules/acceptance-testing に従う。部屋の状態を読む API は 1.7.1 で足す

## 4. テスト計画

観測点は `tests/integration/uc-01-create-room.integration.test.ts` にする。application には単体テストを置き、カバレッジ 100% を満たす。

### `CreateRoom.test.ts`（application の単体テスト。fake で置き換える）

- 依存の置き換えは test file の中に置く。共有の fixture にはしない
  - 部屋リポジトリ: 保存した部屋を記録し、最初の N 回だけ `save_conflict` を返す小さな fake。`implements RoomRepository` にする。`findByCode` は使わないので、呼ばれたら throw する
  - 時計: `{ now: () => ROOM_CREATED_AT }` を使う
  - 乱数: `sequenceRandom()` を使う
- log の検査は `MemoryLogger` を `setLogger` で差し替え、`afterEach` で戻す
- `describe("execute")` には次のテストを置く
  - 有効なニックネームと周回数のとき
    - 作った人だけがメンバーにいて、その人がホストの部屋を保存する
    - 返す写しの部屋コード・周回数・ホスト・メンバー一覧が、保存した部屋と一致する
  - 返すプレイヤー識別子とプレイヤートークンが、保存した部屋のホストのものになる
  - 前後の空白を除いたニックネームで作る
  - 部屋の写しにトークンを含めない（写しを文字列にして、トークンの値を含まない）
  - 最後に更新した時刻を時計の時刻にする（保存した部屋の `lastUpdatedAt`）
  - 周回数の境界の 1 と 5 で作れる（`it.each`）
  - ニックネームが空・空白だけ・11 文字のとき、`nickname_empty`・`nickname_too_long` を返して保存しない（`it.each`）
  - 周回数が 0・6・2.5 のとき、`round_count_out_of_range` を返して保存しない（`it.each`）
  - ニックネームと周回数がどちらも誤りのとき、ニックネームの誤りを返す
  - 保存が 1 回衝突したとき
    - 別の部屋コードの部屋を作り直して保存し、それを返す
    - 重なった部屋コードを warn の log に出す
  - 3 回続けて衝突したとき
    - error の log を出して throw する
    - 保存を 3 回で止める

### `uc-01-create-room.integration.test.ts`（HTTP 結合テスト。実 DB）

- 進め方
  - `beforeAll` で `startServer()` を呼び、`afterAll` で `close()` を呼ぶ。1 ファイルで 1 本のサーバーを共有する
  - 応答は生成型で受ける。`components["schemas"]["CreateRoomResponse"]` と `["ErrorResponse"]` を使う
  - 本文には「前提・操作・期待」の節コメントを置く
- 分離: 部屋コードは乱数で毎回変わる。前提の書き込みも無いので、テスト同士は同じ項目を触らない
- テスト名と期待（ID はテスト名の先頭に置き、シナリオ ID は書かない）:
  - `UC-01 要件 1: ニックネームと周回数を入れて部屋を作ると、作った人がホストとしてただ 1 人のメンバーになった部屋ができる`
    - 周回数 1 と 3 で試す（`it.each`）
    - 201 が返る
    - 部屋コードが英大文字と数字 6 文字になる
    - 周回数が指定した値になる
    - メンバーは「たろう」1 人で、`hostPlayerId` と応答の `player.playerId` がその人になる
    - `player.playerToken` が空でない
    - トークンが `room` の中に現れない
  - `UC-01 要件 1: 部屋を作るたびに別の部屋コードの部屋ができる`（2 回作り、部屋コードが違う）
  - `UC-01 要件 4: ニックネームが空・空白だけのときは入力の誤りが返り、部屋は作られない`
    - 400 と `room.nickname_empty` が返る
  - `UC-01 要件 4: ニックネームが前後の空白を除いて 10 文字を超えるときは入力の誤りが返り、部屋は作られない`
    - 「じゅげむじゅげむごこう」で試す
    - 400 と `room.nickname_too_long` が返る
  - `UC-01 要件 4: 前後の空白を除いて 10 文字のニックネームなら部屋を作れる`
    - 境界の値で試す。前後に空白を付けた 10 文字を送る
    - 201 が返り、空白を除いた名前になる
  - `UC-01 要件 5: 周回数が 1〜5 の整数でないときは入力の誤りが返り、部屋は作られない`
    - 0・6・2.5 で試す（`it.each`）
    - 400 と `room.round_count_out_of_range` が返る
  - `UC-01 要件 5: 周回数の境界の 1 と 5 なら部屋を作れる`
  - `UC-01 要件 5: 周回数が数でない・無い要求は要求の形の誤りが返り、部屋は作られない`
    - `"3"` と、欠落で試す
    - 400 と `request.invalid_body` が返る
  - `UC-01 要件 4 / UC-01 要件 5: 本文が JSON として読めない要求は要求の形の誤りが返り、部屋は作られない`
    - 400 と `request.invalid_json` が返る
- 「部屋は作られない」は、この段では HTTP で観測できない。部屋の状態を読む API が無く、誤りのときは部屋コードも返らないためで、期待の節コメントにそのことを書く。保存しないことは `CreateRoom.test.ts` が確かめる。1.7.1 で `GetRoom` ができても、部屋コードの無い要求の「作られていない」は確かめようがない（5. を参照）
- 500（`server.internal_error`）と部屋コードの使い切りは、結合テストでは作らない。production の組み立てに、故障を注入する口を開けないため（rules/acceptance-testing）

### apps/api の単体テストを置かない理由

- `createApp.ts` は、生成型と DTO の詰め替え、および要求の形の検査だけを持つ。その分岐（JSON の誤り・形の誤り・値の誤り・成功）は、結合テストがすべて HTTP 越しに通る
- `composition.ts` と `main.ts` は組み立てだけで、振る舞いを持たない
- カバレッジの計測対象（ルートの `vitest.config.ts` の `packages/*/src`）に apps は入らない。rules/testing の「composition root は除外してよい」に当たる
- `statusOf` の 404・409・403 の分岐は、この段ではどのテストも通らない。1.7.1・1.7.2 の結合テストが通す

### 検証

周回中は、`npm run db:up` を済ませたうえで `npm run check:fast` を回す（1-7 で結合テストが入る）。コミット前は `npm run check` を回す。E2E は含まない。

## 5. リスク・注意点

- **openapi-typescript と TypeScript 6 の peer。** overrides で入れる（1-1）。openapi-typescript が TS 6 で壊れる変更を受けた場合、生成が失敗するか、生成物の型検査が落ちて気づける
- **生成物の取り残し。** `openapi.yaml` を変えて `generate:api` を忘れても、`check` は気づかない（生成と差分の検査は無い）。1.7.x で OpenAPI を足すときも同じなので、後続の段でも生成を手順に入れる。必要になったら、差分の検査を検証の入口に足すことを検討する
- **DB が無いときの結合テスト。** `startServer` が起動の手順を案内して落ちる（1-6）。`check` は DB を起動しないので、`npm run db:up` を済ませていないと落ちる（rules/testing/project.md のとおり）
- **サーバーが止まらない。** fetch（undici）の keep-alive の接続が残ると、`server.close()` が終わらず、Vitest が待ち続ける。`closeAllConnections()` を先に呼ぶ
- **knip の設定。** apps と tests の entry の判定は、knip の版によって既定が違う。1-7 の設定で未使用・未宣言の報告が出たら、報告に合わせて entry や依存を直す。ルートの devDependencies の `tsx`・`vitest` を workspace の scripts と import から使っている点も、報告の対象になりうる
- **`check:fast` が重くなる。** 結合テストが加わり、周回ごとにサーバーの起動とおよそ 10 件の HTTP 要求が増える。秒単位の増え方の見込みで、遅すぎるようなら `check:fast` から外す（要確認〔設計〕）
- **トークンの漏れ。** トークンを返すのは `CreateRoomResponse.player` だけにする。`RoomSnapshot` と log にはトークンを入れないことを、単体テストと結合テストの両方で確かめる
- **「部屋は作られない」の観測。** UC-01 要件 4・5 の「部屋は作られない」は、API 境界では「誤りが返り、部屋コードが返らない」までしか観測できない。保存しないことは application の単体テストが守る
- **`ConsoleLogger.ts` の `declare const console`。** 1.2.2 から「不要なら消してよい」と引き継いだが、この段の範囲外なので触らない
