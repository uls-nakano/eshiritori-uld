# 設計メモ: 1.2.2 共通の Logger

> タスクの範囲・変更ファイルの候補・束ね方は [tasks.md](../tasks.md) の 1.2.2 を正とし、ここには写さない。ここに書くのは、索引に無い判断・確定した影響ファイル・テスト計画・リスク。

## 1. 実装方針

前提として、shared kernel の型環境には `console` の宣言が無い（`tsconfig.base.json` の `lib` は `ES2022` だけで、`@types/node` も入っていない。`console` を宣言するのは `lib.dom.d.ts` と `lib.webworker.d.ts` だけ）。`ConsoleLogger` の設計はこの制約から決める（1-3）。

### 1-1. `Logger`（`src/Logger.ts`）— 公開契約

型だけを置き、実行時のコードを持たない。

- `export type LogContext = Readonly<Record<string, unknown>>` — 調査のための変数値。rules/development の「context には原因の変数値だけを入れる」を型では縛らず、呼び出し側の規約に任せる
- `export type LogLevel = "info" | "warn" | "error"`
- `export interface Logger`
  - `info(message: string, context?: LogContext): void`
  - `warn(message: string, context?: LogContext): void`
  - `error(message: string, context?: LogContext): void`
- **レベルは `info` `warn` `error` の 3 つにする。** `error` は throw 直前の原因の記録（1.6.1 以降の use case）、`info` はサーバーの起動（1.6.1 の `main.ts`）で使う見込みがある。`warn` は使う段が決まっていないが、`error` と `info` の間の段階が無いと「失敗ではないが調べたい」記録が `error` に寄るため最初から置く。`debug` は使う段が見えないので置かない。要確認〔設計〕
- 戻り値は `void`。ログ出力は失敗しても処理を止めない（throw しない）前提で、呼び出し側は結果を見ない

### 1-2. `getLogger`（`src/getLogger.ts`）— 共通の取得口

- module の中に `let current: Logger = new ConsoleLogger();` を持つ
- `export function getLogger(): Logger` — `current` を返す。処理側は `getLogger().error(...)` と書く
- `export function setLogger(logger: Logger): void` — `current` を差し替える。テストで `MemoryLogger` に差し替えるための口。composition root が出力先を変える場合もこれを使う。要確認〔名前〕
- **差し替えた logger をそのまま返し、包み込む facade オブジェクトは作らない。** 包むと stack の除外対象に facade の frame が加わり、1-3 の「先頭の固定数の frame を落とす」が実装の組み合わせに依存するようになるため
- 既定へ戻す `resetLogger` は作らない。Vitest は既定でテストファイルごとに module を分けて読み込む（`isolate: true`）ため、あるファイルでの差し替えは別のファイルに漏れない。同じファイル内では各テストの `beforeEach` で `setLogger(new MemoryLogger())` を呼び直せば足りる

### 1-3. `ConsoleLogger`（`src/ConsoleLogger.ts`）— console への出力

- `export class ConsoleLogger implements Logger`
- **出力先を constructor で受け取る。** ファイル内に `interface ConsoleOutput { info(...data: unknown[]): void; warn(...): void; error(...): void }`（export しない）を定義し、`constructor(private readonly output: ConsoleOutput = console)` とする。テストは `vi.fn()` で作った出力先を渡して検証する（グローバルの `console` を spy しない。テストファイルでも `console` の型が無いため）
- **既定値の `console` は、ファイル内の `declare const console: ConsoleOutput;` で型を与える。** Node と browser のどちらにも実行時の `console` はあり、宣言は出力に何も残さない。`@types/node` を足す案は、`package.json`・`package-lock.json`・tsconfig を変える（このタスクの 8 件を超える）うえ、shared kernel を Node 専用の型環境にするため採らない。tsconfig の `lib` に `DOM` を足す案は、shared kernel に DOM の大域を持ち込むため採らない。要確認〔設計〕
- 各メソッドはレベルに対応する `console` のメソッドへ委ねる（`info` → `output.info`、`warn` → `output.warn`、`error` → `output.error`）。引数は `(message, context)`。context が無ければ `(message)` だけを渡す（`undefined` が出力に表示されるのを避ける）
- **整形は自前でせず、`console` に任せる。** `JSON.stringify` で 1 行にする案は、context に `bigint`・循環参照があると throw し、`Error` が `{}` になる。`console` は Node の `util.inspect` で安全に整形し、AWS Lambda のログ形式を JSON にした場合は `console` のメソッドからレベルが付く。要確認〔設計〕
- **`error` は stack trace を補う**（rules/development の Logger ルール）
  - `error` のメソッド本体で `new Error().stack` を取り、改行で分けて先頭 2 行（見出しの `Error` と `ConsoleLogger.error` 自身の frame）を落とした残りを `stack` にする。stack を取る処理を private メソッドに切り出さない（切り出すと落とす frame の数が変わるため、メソッド本体に置く理由をコメントに書く）
  - `context?.stack !== undefined` なら上書きしない（呼び出し側が捕捉した例外の stack を渡した場合）。それ以外は `{ ...context, stack }` を出力する。context 無しの `error` でも `{ stack }` を出力する
  - `new Error().stack` が `undefined` になるのは V8 以外の実行環境だけで、テストからは到達できない。`?? ""` などの分岐には `/* v8 ignore next -- defensive: ... */` を理由付きで付け、shared kernel のカバレッジ 100% を保つ
- `info` と `warn` には stack を足さない

### 1-4. `MemoryLogger`（`src/MemoryLogger.ts`）— テスト用のメモリ蓄積

- 同じファイルに `export interface LogEntry { readonly level: LogLevel; readonly message: string; readonly context: LogContext | undefined }`（`MemoryLogger` が記録する 1 件。蓄積の形なので `Logger.ts` ではなくこちらに置く）
- `export class MemoryLogger implements Logger`
  - private の配列に、呼ばれた順に `LogEntry` を積む
  - `get entries(): readonly LogEntry[]` — 記録した全件を呼ばれた順で返す
- **stack を補わない。** stack は出力先（console）での調査のための情報で、`MemoryLogger` の役割は「処理側が渡した message と context」をテストで確かめること。補うと、use case のテストが context を `toEqual` で比べられなくなる。rules/development の「stack は logger 内部で補う」は、実際に出力する `ConsoleLogger` で満たす。要確認〔設計〕
- `clear()` や、レベルで絞る補助は足さない（使う段が出るまで）。テストごとに新しい `MemoryLogger` を作る

### 1-5. `src/index.ts`

- 追加: `export type { LogContext, Logger, LogLevel } from "./Logger";`、`export { getLogger, setLogger } from "./getLogger";`、`export type { LogEntry } from "./MemoryLogger";`、`export { MemoryLogger } from "./MemoryLogger";`
- **`ConsoleLogger` は公開しない。** 既定の出力先として `getLogger` の内側で使うだけで、他 package が実装クラスへ直接依存する箇所を作らない（rules/development の「実装クラスへ直接依存する箇所を増やさない」）。出力先を変えたい段が出たら、その段で公開を判断する
- 並びは `simple-import-sort/exports` に従う（`npm run lint:fix` で揃える）

## 4. テスト計画

受け入れ基準 ID: なし（土台）。単体テストのテスト名に ID を置かない。テスト名は日本語、トップレベルの `describe` は関数名・メソッド名（rules/testing の記述スタイル）。

### `ConsoleLogger.test.ts`（観測点）

出力先は各テストで `{ info: vi.fn(), warn: vi.fn(), error: vi.fn() }` を作って constructor に渡す。

- `describe("info")`
  - message と context を console の info に渡す
  - context が無ければ message だけを渡す
  - stack を足さない
- `describe("warn")`
  - message と context を console の warn に渡す
  - context が無ければ message だけを渡す
- `describe("error")`
  - message と、context に stack を足したものを console の error に渡す（元の context の値はそのまま残る）
  - stack の先頭の frame は呼び出し元で、logger 内部の frame を含まない（テスト内の名前付き関数から `error` を呼び、`stack` の最初の行がその関数名を含み、`ConsoleLogger` を含まないことを確かめる）
  - context に stack があれば上書きしない
  - context が無くても stack だけの context を渡す
- `describe("constructor")`
  - 出力先を省くと既定の出力先を使う（`new ConsoleLogger()` が `Logger` として生成でき、既定値の分岐を通る。グローバルの `console` への実出力は確かめない）

### `MemoryLogger.test.ts`（観測点）

- `describe("info")` / `describe("warn")` / `describe("error")` — それぞれのレベルと message・context を 1 件記録する
- `describe("error")` — stack を補わない（渡した context がそのまま記録される）
- `describe("entries")`
  - 何も記録していなければ空になる
  - 呼ばれた順に記録を返す
  - context を省いた記録は context が undefined になる
  - 別のインスタンスとは記録を共有しない

### `getLogger.test.ts`（観測点）

module の状態を持つため、`beforeEach` で `vi.resetModules()` を呼び、`getLogger` と `ConsoleLogger` を動的 import で読み直す（テストの順番に依存させない）。

- `describe("getLogger")`
  - 差し替えていなければ `ConsoleLogger` を返す
  - 何度呼んでも同じ logger を返す
- `describe("setLogger")`
  - 差し替えた後は、差し替えた logger を返す（`MemoryLogger` を設定し、`getLogger().error(...)` の記録が `MemoryLogger` に残ることまで確かめる。処理側の書き方 `getLogger().error(...)` がテストで観測できることの確認）

### カバレッジ

`packages/shared-kernel/src/**` が 4 指標 100%（`index.ts` は除外）。`Logger.ts` は型だけで計測対象の文を持たない。v8 ignore は 1-3 の到達できない分岐の 1 か所だけ。

## 5. リスク・注意点

- **`declare const console` と後の `@types/node`。** 1.6.1 で `apps/api` が `@types/node` を入れると、ルートの `node_modules/@types/node` に巻き上げられ、`types` を指定していない shared kernel の tsconfig にも自動で読み込まれる。そのときは大域の `console` が宣言される。module 内の `declare const console` は大域の宣言を隠すだけで衝突しないので型検査は通るが、宣言が冗長になる。1.6.1 で冗長になったら消してよい（この段で先回りしない）
- **stack の frame を数で落とす前提。** 先頭 2 行（見出しと `error` 自身）を落とす実装は、V8 の stack の形式（Node 22・Lambda）に依存する。Firefox・Safari は見出し行を持たず、呼び出し元の frame を 1 つ落とす。画面（`apps/web`）が shared kernel の `ConsoleLogger` を使う段が出たら見直す。Vitest の変換（Vite）は関数名を保つので、テストの「先頭の frame が呼び出し元」は観測できる見込み。保たれない場合は、テストを関数名ではなくテストファイル名で確かめる形に変える
- **`Error.stackTraceLimit`（既定 10）。** 自身の frame を 1 つ落とすので、呼び出し元から 9 frame が残る。足りなければ上げる判断は運用（1.6.1 以降）に回す
- **`getLogger` の module 状態。** Vitest の `isolate` を `false` にすると、テストファイル間で差し替えが漏れる。設定を変える段が出たら、`setLogger` の呼び直しを各テストの `beforeEach` に置く規約が要る
- **knip。** `ConsoleOutput` は export しないので未使用 export の対象にならない。`LogEntry` などの型は公開入口（`index.ts`）から export するので報告されない

## 6. 実装の記録

- 「stack の先頭の frame が呼び出し元」のテストは、`ConsoleLogger` を文字列で除外できなかった。テストファイル名（`ConsoleLogger.test.ts`）自体が呼び出し元の frame に含まれるため。実装ファイルの frame（`ConsoleLogger.ts:`）と `ConsoleLogger.error` を含まないことで確かめる形に変えた（設計の想定内の調整。実装は設計どおり）。
- lint（`no-unsafe-assignment`）対策で、テストの `expect.any(String)` に `as string` を付けた。
