## 1. 実装方針

### 1-1. メンバー（`src/domain/room/Member.ts`）

- 状態: `#playerId: PlayerId`、`#token: PlayerToken`、`#nickname: Nickname`。すべて不変（メンバーを書き換える操作はこのスライスに無い）
- `static create(nickname: Nickname, random: RandomSource): Member` — `PlayerId.generate(random)` → `PlayerToken.generate(random)` の順に発行する。入力はすでに検証済みの VO なので Result を返さない
- `static restore(playerId: PlayerId, token: PlayerToken, nickname: Nickname): Member` — mapper（1.5.1）が使う
- `isHeldBy(token: PlayerToken): boolean` — `this.#token.equals(token)`（定数時間の比較は `PlayerToken.equals` が持つ）
- `isNamed(nickname: Nickname): boolean` — `this.#nickname.equals(nickname)`（同じニックネームとは何かは `Nickname` が知る）
- getter `playerId`・`token`・`nickname`（DTO と mapper のデータ変換用。図には描かない。VO の `value` と同じ扱い）

### 1-2. 部屋（`src/domain/room/Room.ts`）

#### 状態と復元の入力

- 状態は図の属性どおり: `#code`、`#members: readonly Member[]`、`#hostPlayerId`、`#roundCount`、`#status`、`#lastUpdatedAt: Date`、`#revision`
- **メンバーの配列は変更のたびに新しい readonly 配列に差し替える**（`join` は `[...members, member]`、`start` は並べ替えた写し）。getter `members` は内部の配列をそのまま返せる
- **時刻は受け取るときと返すときに写しを作る**（`new Date(now.getTime())`）。`Date` は可変で、呼び出し側が後から書き換えると期限の判断が変わるため
- 復元の入力型 `RoomSnapshot`（interface）を **`Room.ts` の中に** export して置く。フィールドは状態と同じ 7 つで、すべて domain の型（`RoomCode`・`readonly Member[]`・`PlayerId`・`RoundCount`・`RoomStatus`・`Date`・`Revision`）。別ファイルにしないのは、`src/domain/` の `.ts` が 1 つずつモデル図のクラスと突き合わせられ（`check:model-trace` の「図に無いクラス」）、図に `RoomSnapshot` を足すほどの概念ではないため

#### 関数

| 関数 | 型 | 処理 |
| --- | --- | --- |
| `static create(hostNickname, roundCount, now, random)` | `(Nickname, RoundCount, Date, RandomSource) => Room` | `RoomCode.generate(random)` → `Member.create(hostNickname, random)` の順に作る。ホストは作ったメンバーの `playerId`、状態は `RoomStatus.waiting()`、最後に更新した時刻は `now`、改訂番号は `Revision.initial()` |
| `static restore(snapshot)` | `(RoomSnapshot) => Room` | 渡された値で作る（メンバーの配列は写す）。**ホストがメンバーの 1 人でなければ throw する**（下記） |
| `join(nickname, now, random)` | `=> Result<Member, RoomError>` | 判断の順序は 1-3。通れば `Member.create(nickname, random)` を末尾に加え、最後に更新した時刻を `now` にし、加わったメンバーを返す |
| `findMember(token)` | `(PlayerToken) => Member \| undefined` | `members.find((m) => m.isHeldBy(token))` |
| `start(requesterToken, now, random)` | `=> Result<boolean, RoomError>` | 判断の順序は 1-4。今回の要求で始めたら `success(true)`、既に始まっていたら何もせず `success(false)` |
| `isExpiredAt(now)` | `(Date) => boolean` | `now - lastUpdatedAt >= 24 時間`（ミリ秒で比べる。定数 `ROOM_LIFETIME_MILLISECONDS = 24 * 60 * 60 * 1000` を非公開で置く） |

- 業務の数（`MAX_MEMBERS = 8`、`MIN_MEMBERS_TO_START = 2`）はファイル内の非公開の定数にする（1.2.1 と同じ）
- **改訂番号は `join`・`start` で変えない。** 集約は読んだときの改訂番号を持ったまま判断し、保存（1.5.1 の adapter）がそれを条件にして `revision.next()` を書く。集約が判断のたびに進めると、保存の条件（読んだときの値）を別に持つことになるため。`create` した部屋が `isInitial()` のままなのも、この取り決めで「まだ保存されていない」と一致する
- **最後に更新した時刻を進めるのは、状態を変えた操作だけ**（`create`、`join` の成功、`start` で始めたとき）。拒否した `join`、何もしなかった二度目の `start` では変えない。変えない操作は保存されない（use case が保存しない）ので、時刻だけ進めても残らないため。部屋の状態を読むだけの操作（1.7.1 の `GetRoom`）も期限を延ばさない（要確認〔仕様〕）

#### getter（データ変換用。図には描かない）

- `code`・`members`・`hostPlayerId`・`roundCount`・`status`・`lastUpdatedAt`（写しを返す）・`revision` — mapper（1.5.1）が保存に、DTO（1.6.1〜）がメンバー一覧・描く順番に使う。ユビキタス言語の `Room.members`・`Room.hostPlayerId` と名前をそろえる
- **`host`（ホストのメンバー）** — 部屋を作った人にトークンを返す（1.6.1 の `CreateRoom`）ために要る。`members.find((m) => m.playerId.equals(this.#hostPlayerId))` で求める。見つからない分岐は `create` と `restore` の検証で到達しないため、`/* v8 ignore next -- defensive: create と restore が「ホストはメンバーの 1 人」を保証する */` を付けて `Error` を throw する（要確認〔設計〕）
  - use case が `members` からホストを探すと、「ホストとは誰か」の判断が application に漏れるため、部屋に持たせる

#### 復元の検証

- `restore` は「ホストがメンバーの 1 人である」だけを確かめる。外れたら `getLogger().error("復元する部屋のホストがメンバーにいません", { roomCode: snapshot.code.value, hostPlayerId: snapshot.hostPlayerId.value })` を出してから `Error("Room host must be one of the members.")` を throw する。保存データの破損で、利用者の操作で起きる失敗ではないため Result にせず、`RoomErrorCode` にも足さない（1.3.1 の `Revision.restore` と同じ扱い）
- メンバーの人数（1〜8）とニックネームの重複は検証しない。破れていても `join` が拒否する方向に倒れるだけで、壊れた判断（例外・別人の取り違え）にはならないため。**トークンをログに出さない**

### 1-3. `join` の判断の順序

1. ゲームが一度でも始まっている（`status.hasStarted()`）→ `room.game_already_started`
2. メンバーが 8 人以上 → `room.room_full`
3. 同じニックネームのメンバーがいる（`members.some((m) => m.isNamed(nickname))`）→ `room.nickname_taken`

- 開始済みを満員より先にするのは、開始済みの部屋は人数が減っても入れないため（UC-02 要件 7）。満員と伝えると、空くのを待てば入れると受け取られる
- 満員をニックネームの重複より先にするのは、満員の部屋ではニックネームを変えても入れないため
- 期限切れは `join` で見ない。use case が `findByCode` の後に `isExpiredAt` で尋ね、`room_not_found` にする（モデル docs の部屋リポジトリの章のとおり）
- メンバーの再参加（UC-02 要件 10）は `join` の責務ではない。トークンを持つブラウザは `join` を呼ばずに部屋の状態を取る（1.7.1・1.12.1）

### 1-4. `start` の判断の順序と並べ替え

1. 要求したトークンの持ち主がいない、または持ち主がホストでない → `room.not_host`（書式の誤ったトークンも 1.3.1 の決定どおりここに落ちる）
2. 既に始まっている → 何もせず `success(false)`（並べ替えない・乱数の源に尋ねない・時刻を変えない）
3. メンバーが 2 人未満 → `room.not_enough_members`
4. メンバーを並べ替え、状態を `RoomStatus.started()`、最後に更新した時刻を `now` にして `success(true)`

- **ホストかどうかを開始済みより先に確かめる。** 二度目の開始を黙って成功にする（UC-03 要件 6）のはホストの二度押しと再送のためで、ホスト以外の要求は始まっていても受け付けない（UC-03 要件 5）。逆の順にすると、メンバーでない人の要求に「成功」を返すことになる
- 並べ替えは「残りから 1 人ずつ引く」形（Fisher–Yates と同じ分布）: 残りのメンバーの写し `remaining` が 2 人以上ある間、`random.nextInt(remaining.length)` で選んだ 1 人を `remaining.splice(index, 1)` で取り出して並びの末尾に足し、最後の 1 人をそのまま足す。乱数の源に尋ねる回数は `n - 1`、渡す `bound` は `n, n - 1, …, 2`。どの並びも同じ確率になる（`RandomSource` の契約が一様であれば）
  - 添字で入れ替える書き方（`[a[i], a[j]] = [a[j], a[i]]`）にしないのは、`noUncheckedIndexedAccess` の下で読み出しが `Member | undefined` になり、non-null assertion（lint で禁止）か到達しない分岐（カバレッジ 100% と両立しない）が要るため。`push(...remaining.splice(index, 1))` なら `undefined` が出ない

### 1-5. 部屋リポジトリの port（`src/domain/room/RoomRepository.ts`）

```ts
/** 保存の条件が満たされず、書き込まなかったことを表す印。利用者に返す失敗ではなく、use case がやり直す合図。 */
export type RoomSaveConflict = "save_conflict";

export interface RoomRepository {
  /** 部屋コードの部屋を復元する。無ければ undefined。期限切れの部屋も返す。 */
  findByCode(code: RoomCode): Promise<Room | undefined>;
  /** 読んだときの改訂番号を条件に保存する（新しい部屋は同じ部屋コードが無いときだけ）。条件が外れたら書き込まず RoomSaveConflict を返す。 */
  save(room: Room): Promise<Result<void, RoomSaveConflict>>;
}
```

- **衝突は例外でも `RoomError` でもなく、Result の失敗で返す。** 同時の参加・部屋コードの重なりは通常の流れで起き、use case が読み直し（`join`・`start`）か部屋コードの作り直し（`create`）でやり直すため。`RoomError` にすると応答のエラーコードと混ざる。shared kernel の `Result` が `E extends DomainError` の制約を持たないのは、この使い方を見込んだもの（`Result.ts` の JSDoc）
- 衝突の種類（改訂番号の不一致か、部屋コードの重なりか）を分けない。use case は自分が保存した部屋の `revision.isInitial()` で見分けられるため
- `RoomSaveConflict` も `RoomRepository.ts` の中に置く（別ファイルは「図に無いクラス」になる）
- 図の `save(room) void` は変えない（Result を図に書かない取り決め）

### 1-6. 公開入口（`src/index.ts`）

- `export type { RoomRepository, RoomSaveConflict } from "./domain/room/RoomRepository";` を足す。`Room`・`Member`・`RoomSnapshot` と値オブジェクトは公開しない（1.2.1 の方針）
- **公開する理由は knip。** この段では `RoomRepository.ts` をどのファイルも import しない（実装は 1.5.1、利用は 1.6.1）ため、そのままでは knip が「Unused files」として報告し `npm run check` が落ちる（`/tmp` に複製したリポジトリで確かめた）。公開入口は knip の entry なので、そこから辿れれば報告されない。port の型は composition root（1.6.1）が adapter を use case に渡すときの型注釈にも使える（要確認〔予定外〕）

### 1-7. fixture（`packages/room/fixtures/roomFixtures.ts`）

- **置き場を tasks.md の `src/domain/room/fixtures/` から package 直下の `fixtures/` に変える。** `check:model-trace` は `src/domain/` 下の `.test.ts` 以外の `.ts` をすべてモデル図のクラスと突き合わせ、`fixtures/` を除外しない（kit 所有の script で直せない）ため、`roomFixtures` が「図に無いクラス」になる（1.3.1 のメモのリスクで予告済み）。この fixture は `Room.test.ts`・`Member.test.ts` に加えて後続の use case のテスト（1.6.1〜1.7.2）と mapper のテスト（1.5.1）でも使うので、rules/testing の「複数テストで共有する fixture は package 直下の `fixtures/`」にも合う（要確認〔予定外〕）
  - tsconfig の `include` は変えない。テストから import されるので `tsc` の検査に入り、ESLint の型付きの規則も効く（複製したリポジトリで確かめた）。knip の project（`src/**/*.ts`）の外なので未使用の export は報告されないが、使うものだけを export する
- **vitest を import しない。** `not-to-dev-dep`（`packages/` の `.test.ts` 以外から dev 依存への import を禁止）に当たるため。失敗は素の `throw new Error(...)` にする
- export する関数（公開の関数には戻り値の型を明示する）:
  - `sequenceRandom(): RandomSource` — 呼ぶたびに 0, 1, 2, … を `bound` で割った余りを返す。続けて作った識別子・トークンが互いに違う値になる

  - `nicknameOf(value: string): Nickname`、`roundCountOf(value: number): RoundCount` — Result が成功でなければ throw して値を取り出す
  - `ROOM_CREATED_AT: Date` — テストの基準時刻（`2026-10-09T09:00:00.000Z`）。共有するので、テストは写して使うか、変更しない
  - `roomWith(nicknames: readonly string[], now?: Date): Room` — 先頭の名前で `Room.create`（周回数 1、`sequenceRandom()`）し、残りを順に `join` する。`join` が失敗したら throw

## 4. テスト計画

受け入れ基準 ID: なし（単体テストのテスト名に ID を置かない）。判断部分が対応するシナリオは S-01-01〜S-01-06、S-01-12〜S-01-14、S-01-18 と差分確認の 3 件（下の各項目に注記。注記はこのメモだけで、テスト名には入れない）。受け入れ基準を外すのは 1.6.1・1.7.1・1.7.2 の結合テスト。

### 共通

- `describe` は図の公開メソッド名だけにする。**入れ子の `describe` にも英数字の識別子の名前を付けない**（`check:model-trace` は入れ子も拾い、図に無い識別子を「図に無い関数」として報告する）。入れ子が要るときは日本語の名前にする。getter（`host`・`members` など）の `describe` は作らず、各関数の `describe` の中で確かめる
- 失敗は `isFailure` で絞り込んでから `error.code`（`room.room_full` など）を見る
- ログを確かめるテストは `beforeEach` で `setLogger(new MemoryLogger())`、`afterEach` で退避した元の Logger に戻す（1.3.1 の `Revision.test.ts` と同じ）
- 部屋・メンバーは fixture（1-7）で作る。時刻は `ROOM_CREATED_AT` から `new Date(ROOM_CREATED_AT.getTime() + ms)` で作る

  - 待機中で、まだ保存されていない（`status.hasStarted()` が false、`revision.isInitial()` が true）
  - 作った時刻が最後に更新した時刻になる
  - ホストのトークンで `findMember` するとホストが見つかる
- `describe("restore")`
  - 渡した値をそのまま持つ（7 つの値、メンバーの並び）
  - 渡したメンバーの配列や時刻を後から変えても、部屋の値は変わらない
  - ホストがメンバーにいないスナップショットは `Error` を throw する
  - throw する前に、部屋コードとホストの識別子を context に入れた error のログを 1 件出す（トークンを含まない）
- `describe("join")`
  - 入れる部屋なら、新しいメンバーが末尾に加わり、加わったメンバーを返す（S-01-03・S-01-04）
  - 加わったメンバーのトークンで `findMember` できる
  - 最後に更新した時刻が入った時刻になり、改訂番号は変えない
  - 7 人の部屋には入れて 8 人になる（境界）
  - 8 人の部屋は `room.room_full` で拒否し、メンバーは 8 人のまま（S-01-12。差分確認の同時参加は、読み直した部屋が 8 人になっている場面としてこの判断に落ちる）
  - ゲームが始まった部屋は `room.game_already_started` で拒否する（S-01-13）
  - 同じニックネームのメンバーがいれば `room.nickname_taken` で拒否する（S-01-14）
  - ひらがなとカタカナの違いは別のニックネームとして入れる（S-01-14）
  - 判断の順序（入れ子 `describe("判断の順序")`）: 始まった 8 人の部屋は `game_already_started`（`restore` で作る）／8 人の部屋に同じニックネームで入ると `room_full`
  - 拒否したときは、メンバーも最後に更新した時刻も変わらない
- `describe("findMember")`: メンバーのトークンならそのメンバー／どのメンバーのトークンでもなければ undefined／書式の誤ったトークンなら undefined
- `describe("start")`（S-01-05・S-01-18・差分確認の二重の開始）
  - ホストが 2 人以上の部屋で始めると true を返し、始まった状態になる
  - メンバーを並べ替え、その並びが描く順番になる: 「たろう（ホスト）・はなこ・じろう」に `fixedRandom([1, 1])` → 記録した `bound` が `[3, 2]`、並びが「はなこ・じろう・たろう」
  - 乱数が毎回残りの先頭を指せば並びは変わらない: `fixedRandom([0, 0])` → 「たろう・はなこ・じろう」
  - 乱数が毎回残りの末尾を指せば逆順になる: `fixedRandom([2, 1])` → 「じろう・はなこ・たろう」
  - 最後に更新した時刻が開始の時刻になり、改訂番号は変えない
  - ホスト以外のメンバーのトークンは `room.not_host` で拒否し、始まらない
  - メンバーでないトークン・書式の誤ったトークンは `room.not_host` で拒否する
  - ホスト 1 人だけの部屋は `room.not_enough_members` で拒否し、始まらない（S-01-18）
  - 既に始まった部屋にホストがもう一度要求すると false を返し、並び・最後に更新した時刻は変わらず、乱数の源にも尋ねない（`fixedRandom([])` を渡して throw しないこと）
  - 既に始まった部屋への、ホスト以外のメンバーの要求は `room.not_host`（判断の順序）
- `describe("isExpiredAt")`（S-01-06）
  - 最後に更新してから 24 時間に 1 ミリ秒足りなければ false
  - ちょうど 24 時間たっていれば true／それより後も true
  - メンバーが入ると、入った時刻から測り直す（作ってから 24 時間後でも、23 時間後に入っていれば false）
  - 開始すると、開始の時刻から測り直す

### カバレッジ

- `packages/room/src/domain/**` が 4 指標 100%。分岐は `join` の 3 つの拒否と成功、`start` の 4 つの経路、並べ替えのループ、`isExpiredAt` の境界、`restore` の検証の可否で、すべて上のテストが両側を通る。`host` の見つからない分岐だけを理由付きの `v8 ignore` で外す
- `RoomRepository.ts` は型だけで実行時の文を持たない。`fixtures/` は `src/` の外で、カバレッジの計測に入らない

## 5. リスク・注意点

- **`roomFixtures` の置き場。** 1-7 の変更を戻して `src/domain/room/fixtures/` に置くと `check:model-trace` が落ちる。`src/` の下の別の場所（例: `src/fixtures/`）でも model-trace は通るが、knip の project に入り、後続の段で使う予定の export が「未使用」として報告される
- **knip と `RoomRepository.ts`。** 1-6 の公開をやめる場合は、`RoomRepository.ts` を 1.5.1 へ移す必要がある（1.5.1 の変更ファイルが 1 件増える）
- **`RoomSaveConflict` の使い方は 1.5.1 と 1.6.1〜1.7.2 が決める。** やり直しの上限（何回読み直すか）は use case の判断で、この段では決めない。上限が無いと、衝突が続いたときに要求が終わらない
- **トークンの漏れ。** `Member` に `token` の getter があるため、メンバー一覧の DTO（1.6.1〜）に入れないこと。トークンを返してよいのは本人（部屋を作った人・入った人）への応答だけ。`restore` のログにもトークンを入れない
- **時刻の基準。** `isExpiredAt` と最後に更新した時刻は、use case が受け取る時計（1.6.1 の `Clock`）の値で決まる。DynamoDB の TTL（1.5.1）は同じ `lastUpdatedAt + 24 時間` から計算し、ドメインの判断と揃える
- **並べ替えの偏り。** 一様な並びは `RandomSource` が一様であることに依存する。単体テストは決まった値での並びだけを確かめ、確率の偏りは検証しない（1.5.1 の `CryptoRandomSource` のテストが範囲を守る）
- **`start` と `join` の同時。** ホストの開始と誰かの参加が同時に届いた場合は、改訂番号の条件で片方が衝突し、読み直して判断し直す。開始が先なら参加者は `game_already_started`、参加が先なら参加者を含めて並べ替える。どちらもこの段の判断のままで正しく、追加の対応は要らない
