# 設計メモ: 1.13.1 E2E-01-01（招待 URL で 1 人を誘って始める）

> この段の範囲・観測点・束ね方は [tasks.md](../tasks.md) の 1.13.1 に従い、ここには写さない。ジャーニーの筋は [docs/journeys/E2E-01](../../../../docs/journeys/E2E-01-仲間と部屋に集まってゲームを始める.md) に、E2E の書き方は [rules/acceptance-testing](../../../../rules/acceptance-testing/standard.md) の「E2E テスト」に従う。画面と API の配線は [1.12.1](1.12.1-design.md) のメモと実装に従う。ここに書くのは、それらに無い判断、確定した影響ファイル、テスト計画、リスク。

## 1. 実装方針

順序は 依存の追加（`@playwright/test`・`vite`）→ 起動のコマンド（`start`・`start:web`）→ DB の確認の共有化 → Playwright の設定と globalSetup → E2E のテスト → `npm run test:e2e` で通ることを確かめる → ジャーニーの（未実装）を外す → lint・knip・型の設定 → 生き資料と記録。

domain・application・adapter・`apps/api`・API 契約・`apps/web/src` は変えない。E2E は本物の画面と API を外から操作するだけで、テストのための注入口を production に作らない。

### 1-1. 画面の起動のコマンド（1.12.1 から送られた分）

- `apps/web/package.json`: `scripts.start` を `vite`、`devDependencies` に `vite`（インストール済みの 8.3.4 に合わせ `^8.3.4`）。いまは Storybook と `@vitejs/plugin-react` の推移的な依存として入っているだけで、`start` から呼ぶなら直接の依存にする（knip がスクリプトの binary を未登録として止めるため）
- ルートの `package.json`: `start:web` を `npm run start -w @eshiritori/web`（`start:api` と対にする）
- `vite.config.ts` は変えない。中継先は既存の `API_ORIGIN`、ポートは CLI の `--port` で渡す

### 1-2. E2E で画面を立てるのは Vite の開発サーバー

規約の「UI と API は production と同じ起動コマンドで、別プロセスとして起動する」の「production と同じ起動コマンド」を、**ローカルの配信の構成**（[docs/architecture](../../../../docs/architecture/README.md) の「ローカルと AWS の構成の対応」の「画面の配信」= Vite の開発サーバーが `/rooms` と `/ws` を中継）を立てるコマンド `apps/web` の `start`（`vite`）と読む。

- 捨てた案: `vite build` → `vite preview`。静的ファイルを配る点で AWS（S3 + CloudFront）に近いが、中継は `server.proxy` にしか無く、`preview.proxy` に同じ設定を二重に持つことになる。AWS 側の API・WebSocket への振り分けはデプロイの要求で決める（docs/architecture）ので、いま production の配信を真似ても正にならない（要確認〔仕様〕）
- `webServer` のコマンドは `npm run start -w @eshiritori/web -- --port 5273 --strictPort`。ルートの `start:web` を経由すると、npm の 2 段の引数渡しで `--port` が npm の設定として食われるため、ワークスペースの `start` を直接呼ぶ（中身は同じ `vite`）

### 1-3. Playwright の設定（`tests/e2e/playwright.config.ts`、新規）

```ts
export default defineConfig({
  testDir: ".",
  testMatch: "**/*.e2e.test.ts",
  globalSetup: "./globalSetup.ts",
  timeout: 60_000,          // 初回は Vite が画面を変換するため既定より長く
  forbidOnly: !!process.env["CI"],
  retries: 0,
  workers: 1,
  reporter: "list",
  use: { baseURL: WEB_ORIGIN, trace: "retain-on-failure" },
  projects: [{ name: "chromium", use: { ...devices["Desktop Chrome"] } }],
  webServer: [
    { command: "npm run start:api", port: API_PORT, env: { PORT: String(API_PORT) }, cwd: REPO_ROOT, reuseExistingServer: false, timeout: 60_000 },
    { command: "npm run start -w @eshiritori/web -- --port 5273 --strictPort", url: WEB_ORIGIN, env: { API_ORIGIN: `http://localhost:${API_PORT}` }, cwd: REPO_ROOT, reuseExistingServer: false, timeout: 60_000 },
  ],
});
```

- **ポートは API 3100・画面 5273 に固定する。** 開発サーバー（API 3000・画面 5173）と別番号にし、開発中のまま E2E を走らせられるようにする（規約）。`reuseExistingServer: false` と `--strictPort` で、前の実行が残っていたら古いサーバーを相手にせず起動の失敗で止める
- API の待ち合わせは `port`（接続を受けるまで待つ）。`url` は 2xx〜403 を返す path が要るが、API には DB に触れずにそれを返す path が無い（`/` は 404）
- `webServer` の `env` は `process.env` に重ねて渡るので、`DYNAMODB_ENDPOINT` を上書きした環境でも API と globalSetup が同じ DB を見る
- `cwd` はリポジトリのルート（`fileURLToPath(new URL("../../", import.meta.url))`）。`tests/e2e` から `npm run start:api` を呼ぶと `tests/package.json` の scripts を探してしまうため
- 出力（`test-results/`）は既定のまま `tests/e2e/test-results/` に出る。`.gitignore` に `test-results/` と `playwright-report/` が既にあり、Prettier 3 は `.gitignore` を読むので `format:check` にも混ざらない。HTML レポートは作らない（`reporter: "list"`）
- ブラウザは Chromium だけ。複数ブラウザでの差は、この段の確かめること（つながって動くこと）に入らない

### 1-4. 実行ごとに一意な識別子

規約の「テストが書き込む対象の識別子は実行ごとに一意にし、実行環境の組み立てが 1 回だけ決めて全プロセスへ配る」は、この E2E では**組み立てが値を配らない**。書き込む対象（部屋）の識別子は部屋コードで、サーバーが実行ごとに乱数で発行し、重なりは改訂番号を条件にした保存で避ける（1.5.1）。ニックネーム「たろう」「はなこ」は部屋の中だけで重なりを判断するので、毎回の新しい部屋で固定値のまま使える。外部システムのスタブも無いので、globalSetup は値を配らない（1-5）

### 1-5. globalSetup と DB の確認の共有（`tests/e2e/globalSetup.ts`、`tests/support/assertTablesReady.ts`、新規）

- globalSetup は **DB の表が使えることを確かめるだけ**。使えなければ `npm run db:up` を案内して throw する。DB が無いまま走らせると、画面に「想定外の誤り」が出て待機室の待ち合わせが時間切れになり、原因が読めないため
- 確認の実装は結合テストの `tests/integration/support/startServer.ts` の `assertTableReady` と同じなので、`tests/support/assertTablesReady.ts` に移して両方から使う（規約の「結合テストと E2E で共有するものは `tests/support/` に置き、1 つの実装を使う」）。関数の形は `assertTablesReady(config: ApiConfig): Promise<void>`（`ApiConfig` は `@eshiritori/api` の composition が公開する型。名前は複数の表を確かめるので複数形にする）。`startServer.ts` は import に置き換えるだけで、案内の文言は変えない
- globalSetup は `readApiConfig(process.env)` で設定を読む（API と同じ設定の読み方。`tests/` から import してよいのは composition root だけという境界に収まる）
- Playwright は `webServer` を globalSetup より先に起動する。API は DB が無くても起動するので、順序の問題は無い
- Playwright の globalSetup は default export の関数が要る。戻り値の型 `Promise<void>` を明記する（`explicit-module-boundary-types`）

### 1-6. E2E のテスト（`tests/e2e/e2e-01-gather-and-start.e2e.test.ts`、新規）

テスト名は `E2E-01-01: 部屋を作り、招待 URL で誘った仲間が入り、ホストが始めると、全員の画面が同じ描く順番のゲーム画面になる`。受け入れ基準 ID とシナリオ ID は書かない（`check:trace` の配置違反）。

冒頭コメント（規約の `前提:` `期待:`）:

- 前提: 外部システムのスタブは使わない。DynamoDB Local が起動して表がある。部屋はテストの中で作るので、前の実行の部屋とは部屋コードで分かれる
- 期待: たろう（ホスト）とはなこの 2 人の部屋になり、開始後は 2 人の画面に同じ並びの描く順番（たろう・はなこの 2 人）が出る。並びはサーバーが決めるので、名前の並びそのものではなく「2 人の画面で同じ」ことを確かめる

**2 つの端末は 2 つのブラウザコンテキストで表す。** たろうはテストの `page`（設定の `baseURL` を引き継ぐ）、はなこは `browser.newContext()` で作った別のコンテキスト（`localStorage` が分かれる = トークンを共有しない）。はなこは画面から読んだ招待 URL（絶対 URL）を開くので `baseURL` に頼らない。はなこのコンテキストは `try` / `finally` で閉じる。

手順（`test.step`。手順名はジャーニーのストーリーの言葉）:

| 手順名 | 操作 | 確かめること |
| --- | --- | --- |
| たろうがトップ画面でニックネームを入れて部屋を作る | `/` を開き、見出し「部屋を作る」のフォーム内の「ニックネーム」に「たろう」、ボタン「部屋を作る」 | 見出し「待機室」。メンバー一覧（名前「メンバー（1/8）」の list）の項目が「たろう（ホスト・あなた）」だけ。「部屋コード: 〇〇」と招待 URL が出る |
| たろうが招待 URL をはなこに送る | 画面の招待 URL の文字（`/r/` を含む文）を読む | 招待 URL が `<画面のオリジン>/r/<表示の部屋コード>` |
| はなこが招待 URL を開き、ニックネームを入れて部屋に入る | はなこのコンテキストで招待 URL を開き、「ニックネーム」に「はなこ」、ボタン「入る」 | 開いた直後に「部屋コード: 〇〇」（入力欄でなく固定の表示）。入った後は見出し「待機室」と「たろうさんが開始するのを待っています…」 |
| たろうの待機室に、開き直すことなくはなこが加わる | （操作なし。たろうの画面を再読み込みしない） | たろうのメンバー一覧が「たろう（ホスト・あなた）」「はなこ」の 2 件、見出し「メンバー（2/8）」 |
| たろうが開始を押すと、2 人の画面がゲーム画面に切り替わる | たろうのボタン「開始」 | 2 人とも見出し「ゲームが始まりました」。「描く順番」の list の項目から「（あなた）」を除いた並びが 2 人で一致し、たろう・はなこの 2 人を含む |

- 部品の探し方は role とラベル（`getByRole("heading")`・`getByRole("list", { name })`・`getByLabel`・`getByRole("button")`）。トップは 2 つのフォームが同じラベル「ニックネーム」を持つので、`page.locator("form", { has: page.getByRole("heading", { name: "部屋を作る" }) })` の中で探す。`data-testid` は足さない（`apps/web` を変えない）
- 待ち合わせは Playwright の自動待機（`expect(...).toHaveText` など）に任せ、`waitForTimeout` を使わない。はなこの画面の切り替えは通知（WebSocket）、たろうの切り替えは開始の応答で起きる
- 描く順番の比較は、たろうの画面で `allTextContents()` を読んで「（あなた）」を除き、はなこの画面の list に `toHaveText` で同じ並び（はなこの行は「（あなた）」付き）を求める形にする。片方を読んでもう片方を自動待機で比べ、読み取りの瞬間のずれで落ちないようにする
- `tests/tsconfig.json` は `lib: ES2022`（DOM なし）なので、`page.evaluate` でブラウザの値を読まない。読むのはロケーターの文字だけ

### 1-7. 実行のコマンド

## 4. テスト計画

| 観測点 | レベル | 対応する ID |
| --- | --- | --- |
| `tests/e2e/e2e-01-gather-and-start.e2e.test.ts` | E2E（Playwright・Chromium、本物の画面と API と DynamoDB Local） | E2E-01-01 |

- 進め方: テストを書く → ジャーニーの「（未実装）」を残したまま `npm run check:trace` が「未実装の ID にテストがある」で落ちることを確かめる（トレースの Red）→ `npm run db:up` の後 `npm run test:e2e` を通す → 「（未実装）」を外して `check:trace` を通す

- 落ちることの確かめ: 一度だけ、はなこの期待を「メンバー（3/8）」など誤った値にして `npm run test:e2e` が落ちること（自動待機が時間切れで失敗を報告すること）を手元で確かめ、戻す
- 結合テストの回帰: `startServer.ts` の確認を移すので、`npm run test:integration`（`check` に含む）で既存の結合テストが通ることを確かめる。DB を止めた状態で案内の文言が出ることも 1 度確かめる
- コミット前: `npm run check` と `npm run test:e2e` の両方（rules/testing の「観測点が E2E の子タスクは」）
- カバレッジ: domain・application を変えないので 100% 要件に影響しない。`tests/` と `apps/web` の起動設定は計測の対象外（ルートの `vitest.config.ts` は `packages/*` だけを計測）

## 5. リスク・注意点

- **Vite の依存の最適化による再読み込み**: 開発サーバーは、初めて見る依存を見つけるとページを再読み込みすることがある。入口（`index.html` → `main.tsx`）から辿れる依存は起動時に先に最適化されるので通常は起きないが、起きると入力の途中で画面が戻って不安定になる。起きたら `vite.config.ts` の `optimizeDeps.include` で先に指定する（変更ファイルが 1 件増える）
- **キャッシュの共有**: 開発サーバー（5173）と E2E の画面（5273）を同時に動かすと、同じ `apps/web/node_modules/.vite` を使う。最適化の結果が食い違うと片方が再読み込みする。同時に動かしても動くことを手元で 1 回確かめる。食い違うなら E2E 側だけ `--force` を付ける
- **固定のポート**: 3100・5273 が他で使われていると起動で失敗する（`reuseExistingServer: false`・`--strictPort` による意図した失敗）。環境変数での上書きは、必要になるまで作らない
- **ブラウザの版**: `@playwright/test` を固定しても、別の機械では `npx playwright install chromium` が要る。CI のワークフローはまだ無い（`.github/workflows/` が無い）ので、規約の「CI の専用ジョブ」はこの段では作らない。CI を作る段で、ブラウザの取得と DB の起動をジョブに入れる
- **通知の届く時刻**: はなこが入った後のたろうのメンバー一覧と、開始後のはなこの画面は WebSocket の通知で変わる。たろうの接続が `connected` を受ける前にはなこが入っても、たろうは `connected` で最新の写しを受け取るので取りこぼしは無い（1.9.1・1.12.1 の設計）。期待は自動待機（既定 5 秒）で待つ
- **トークンの保存キーと URL の部屋コード**（1.12.1 のリスクを引き継ぐ）: 招待 URL は `room.code`（大文字）で組み立てられるので、この E2E の経路では一致する。小文字の URL を開く経路はこの E2E の範囲に入らない
- **React の StrictMode**: 開発サーバーでは effect が 2 回走り、WebSocket の接続が一度開いて閉じる。サーバーは閉じた接続への送信に失敗したら登録を消す（docs/architecture）ので、通知は残った接続に届く。E2E がこの経路を本物のブラウザで通す初めての段なので、落ちたらまずここを疑う
