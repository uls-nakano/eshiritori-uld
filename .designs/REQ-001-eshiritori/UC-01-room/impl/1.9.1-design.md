## 1. 実装方針

順序は application（port → `JoinRoom` / `StartGame`）→ API 契約 → composition root（publisher → WebSocket の入口 → 起動）→ 結合テスト。domain・adapter（room の永続化）・`packages/realtime` は変えない。

### 1-1. 通知の port（`packages/room/src/application/RoomEventPublisher.ts`、新規）

```ts
/** 部屋の変化を、部屋につながっている全員に知らせる口。実装は composition root が注入する。 */
export interface RoomEventPublisher {
  /** メンバーが加わった後の部屋を知らせる。 */
  publishMemberJoined(room: RoomSnapshotDto): Promise<void>;
  /** ゲームが始まった後の部屋（members が描く順番）を知らせる。 */
  publishGameStarted(room: RoomSnapshotDto): Promise<void>;
}
```

- **通知は部屋の写し（`RoomSnapshotDto`）をまるごと運ぶ。** 差分（加わった 1 人だけ）を送ると、画面が一覧を組み立て直す判断を持つことになり、取りこぼした通知を後から回復できない。写しなら最後に届いたものを表示するだけで済む（presentation は API が返した値を表示する。[rules/architecture](../../../../rules/architecture/standard.md)）。写しはトークンを持たない型なので、通知にトークンが混ざらない
- メソッドを出来事ごとに 2 つに分ける（`publish(event)` の 1 つにしない）。use case が「何が起きたか」を言い、送り方（形・宛先）は実装が決める
- port は `application/` に置く（tasks.md のとおり）。domain の判断を持たない出口なので domain には置かない。モデル図の対象外

### 1-2. use case から通知する（`JoinRoom.ts`・`StartGame.ts`）

- コンストラクタの末尾に `publisher: RoomEventPublisher` を足す（`#publisher`）
- `JoinRoom`: 保存が成功した分岐でだけ、返す写しで `publishMemberJoined` を 1 回呼ぶ。入れなかった（Result の失敗）・衝突して読み直した回では呼ばない
- `StartGame`: `started.value === true` で保存が成功した分岐でだけ `publishGameStarted` を 1 回呼ぶ。既に始まっていた（保存しない）分岐では呼ばない（UC-03 要件 6: 二度目は何も変わらないので知らせない）
- **通知を待ってから応答を返す（`await`）。** AWS の Lambda は応答を返した後の処理を続けられないため、投げっぱなしにすると通知が落ちる。待つことで「応答が返った時点で全員に送り終えている」が成り立ち、1 秒以内（UC-02 要件 3、UC-03 要件 2）の根拠になる
- **通知の失敗は操作の失敗にしない。** 保存は済んでいるので、ここで throw すると「入れなかった」と見えて、入り直すと `nickname_taken` になる。use case が `try/catch` で受け、`getLogger().warn("メンバーが加わったことの通知に失敗しました", { roomCode, error })`（開始は「ゲームが始まったことの通知に失敗しました」）を出して、成功の Result をそのまま返す。warn にするのは Logger の約束（`error` は throw 直前の記録）に合わせるため。この方針は送り方ではなく「操作の成否と通知の成否を分ける」application の判断なので、adapter ではなく use case に置く（単体テストで固定できる）
- try/catch は 2 つの use case に 3 行ずつ書く。共通の関数に括り出さない（2 箇所で、ログの文言が違うため）

### 1-3. 公開入口（`packages/room/src/index.ts`）

`export type { RoomEventPublisher } from "./application/RoomEventPublisher";` を足す。

### 1-4. 通知の形の契約（`packages/api-contract/openapi.yaml` と生成物）

`components.schemas` に 1 つ足し、`npm run generate:api` で `schema.ts` を作り直す。

```yaml
RoomNotification:
  type: object
  description: WebSocket で部屋のメンバーに送る通知。...（接続の URL と 3 つの type の意味を書く）
  required: [type, room]
  properties:
    type:
      type: string
      enum: [connected, member_joined, game_started]
      description: connected は接続直後のいまの部屋、member_joined はメンバーが加わった、game_started はゲームが始まった。
    room:
      $ref: "#/components/schemas/RoomSnapshot"
```

- 3 つの type はどれも `room` だけを運ぶので、`oneOf` に分けず 1 つの schema にする（生成型も union の判別が要らない）。後続の移行単位で中身の違う通知（お題など）が増えたら、そのとき `oneOf` に分ける
- OpenAPI は WebSocket の経路を表せないので、接続の仕方（1-6 の URL と拒否の status）は schema の `description` に書く。`paths` には足さない
- `connected` は 1-6 の「接続直後にいまの部屋を送る」ためのもの

### 1-5. publisher の実装（`apps/api/src/RealtimeRoomEventPublisher.ts`、新規）

```ts
export class RealtimeRoomEventPublisher implements RoomEventPublisher {
  constructor(registry: DynamoDbConnectionRegistry, sender: WebSocketSender);
  publishMemberJoined(room: RoomSnapshotDto): Promise<void>; // type "member_joined"
  publishGameStarted(room: RoomSnapshotDto): Promise<void>;  // type "game_started"
}
/** 通知の本文（JSON 文字列）を作る。webSocketEndpoint の connected も同じ形で作る。 */
export function roomNotificationMessage(type: RoomNotification["type"], room: RoomSnapshotDto): string;
```

- 流れ: `registry.findByRoom(room.code)` → 全接続へ `sender.send` を `Promise.all` で並べる → `"gone"` の接続は `registry.remove(roomCode, connectionId)`。宛先は部屋の全接続（加わった本人・開始したホストの接続も含む。本人の別タブにも届き、害が無い）
- 本文は `JSON.stringify({ type, room: toRoomSnapshot(room) } satisfies RoomNotification)`。**`toRoomSnapshot` は `createApp.ts` の既存の関数を export して使う。** DTO を spread で流用すると、DTO に後から属性が増えたとき契約に無い値（トークンなど）が黙って通知に乗るため、明示の詰め替えを 1 つに保つ
- 宛先を部屋コードで引くので、registry に登録する部屋コードは**正規化済みの写しの `code`** にする（1-6）。URL のまま（小文字など）登録すると、publisher が引く `room.code` と食い違い届かない
- `sender` は `WebSocketSender`（interface）で受ける。AWS 版の送信は同じ口に差し替わる

### 1-6. WebSocket の入口（`apps/api/src/webSocketEndpoint.ts`、新規）

```ts
export interface WebSocketEndpointDependencies {
  readonly getRoom: GetRoom;
  readonly registry: DynamoDbConnectionRegistry;
  readonly sender: LocalWebSocketSender;
  readonly clock: Clock;
}
/** HTTP サーバーの upgrade イベントに渡すハンドラを作る。 */
export function createWebSocketUpgradeHandler(
  deps: WebSocketEndpointDependencies,
): (request: IncomingMessage, socket: Duplex, head: Buffer) => void;
```

- **URL は `GET /ws?roomCode=<部屋コード>&playerToken=<トークン>`。** 本人の確かめ方を HTTP の `Authorization` ヘッダーにしないのは、ブラウザの WebSocket API がヘッダーを付けられないため。部屋コードを path に入れないのは、AWS の API Gateway WebSocket がステージごとに 1 つの URL で path を持てず、クエリなら同じ形で `$connect` に渡せるため（画面は接続先のベース URL だけを差し替える）
- 流れ:
  1. path が `/ws` でなければ 404 で拒否
  2. `getRoom.execute({ roomCode, playerToken })` でメンバーかを確かめる（クエリが無ければ空文字。既存の use case がそのまま `room_not_found` / `not_member` にする）。失敗は `room_not_found` → 404、それ以外（`not_member`）→ 403 で拒否。新しい use case は作らない（GetRoom の判断と同じ: 部屋がある・期限内・メンバー）
  3. `sender.accept(request, socket, head, onClose)` で受け入れる
  4. `registry.register({ roomCode: 写しの code, connectionId, playerId }, clock.now())`
  5. **登録の後に `getRoom` をもう一度呼び、その写しを `connected` で本人の接続にだけ送る**（`"gone"` なら登録を消す）。登録の前に読んだ写しを送ると、読んでから登録までの間に入った人を一覧からも通知からも取りこぼす。登録の後に読めば、それより後の保存はその publisher の `findByRoom`（強い整合）がこの接続を見つけ、それより前の保存は写しに入っている
- 拒否は `socket.end("HTTP/1.1 <status> <reason>\r\nConnection: close\r\nContent-Length: 0\r\n\r\n")`（`@hono/node-server` の `rejectUpgradeRequest` と同じ形）。本文は付けない（ブラウザの WebSocket は拒否の本文を読めない）
- 予期しない例外（DB が無いなど）は handler の中で受け、`getLogger().error("WebSocket の接続の受け付けに失敗しました", { path, errorName, stack })` を出し、受け入れ前なら 500 で拒否する。**ログにクエリ（トークン）を出さない**（`request.url` ではなく path だけ）
- **登録と切断の順序（1.8.1 から引き継いだリスク）**: `onClose` は登録の Promise を待ってから `registry.remove` を呼ぶ。登録が終わる前に閉じられても登録が残らない。`remove` の失敗は warn のログにして捨てる
- `@hono/node-server` 2 の `upgradeWebSocket`（Hono の route で受ける仕組み）は使わない。`ws` の `WebSocketServer` を `apps/api` が持つことになり、受け入れを `LocalWebSocketSender` に閉じた 1.8.1 の設計と食い違うため。`serve` に `websocket` を渡さなければ node-server は `upgrade` を購読しない（2.1.4 の実装で確認）

### 1-7. 組み立てと起動（`composition.ts`・`main.ts`）

- `ApiConfig` に `connectionTableName`（`connectionTable.name`）を足す
- **`composeApp(config): Hono` を `startApi(config): Promise<RunningApi>` に置き換える。** `RunningApi = { readonly port: number; close(): Promise<void> }`。中で DynamoDB client・repository・registry・`LocalWebSocketSender`・publisher・use case を組み、`serve` で待ち受け、`server.on("upgrade", createWebSocketUpgradeHandler(...))` をつなぐ。`close` は `sender.closeAll()` → `server.closeAllConnections()` → `server.close()` → DynamoDB client の `destroy()`
  - 起動の手順を composition に 1 つだけ置き、`main.ts` と結合テストの `startServer.ts` の両方がこれを呼ぶ。upgrade のつなぎ込みを各自で書くと、production と違う組み立てを結合テストが検証しうるため（[rules/acceptance-testing](../../../../rules/acceptance-testing/standard.md)）。`tests/` が import できるのは `composition.ts` だけ（dependency-cruiser の `tests-use-composition-root-only`）なので、ここに置くことで規約にも合う
  - `serve` の戻り値を `node:http` の `Server` に絞る確認（`startServer.ts` の `instanceof`）は composition に移す
- `main.ts`: `const api = await startApi(readApiConfig(process.env));` の後に起動のログ
- `apps/api/package.json` の `dependencies` に `"@eshiritori/realtime": "*"` を足す（`package-lock.json` が追随）

### 1-8. 結合テストの土台（`tests/integration/support/`）

- `startServer.ts`: `startApi({ ...readApiConfig(process.env), port: 0 })` を使う形に書き換える。`TestServer` に変更は無い（`baseUrl`・`postJson`・`getJson`・`close`）。`close` は `RunningApi.close` に委ねる。`@hono/node-server` を import しなくなるので、`tests/package.json` の依存から外す（knip が未使用の依存として報告するため）
- `connectWebSocket.ts`（新規）: Node 22 の標準の `WebSocket` で `ws://…/ws?roomCode&playerToken` につなぐ

  ```ts
  export interface RoomSocket {
    /** 接続直後に届いた connected の通知。 */
    readonly connected: RoomNotification;
    /** 次の通知を待つ。timeoutMs 以内に届かなければ reject する。 */
    next(timeoutMs: number): Promise<RoomNotification>;
    close(): void;
  }
  /** 部屋のメンバーとして通知の接続を開き、connected が届くまで待つ。拒否されたら reject する。 */
  export function connectWebSocket(baseUrl: string, roomCode: string, playerToken: string): Promise<RoomSocket>;
  ```

  - 受信は接続した時点から配列に溜め、`next` は溜まった先頭を取る（`await` の合間に届いた通知を落とさない）。JSON の解釈は `postJson` と同じく生成型へのキャストをハーネスの中だけで行う
  - **`connected` を待ってから返す。** サーバーは登録の後に `connected` を送るので、受け取った時点で以後の通知の宛先に入っていることが保証される。`open` だけで返すと、登録前に操作を走らせて通知を取りこぼし、テストが不安定になる
  - 拒否（`open` の前の `error` / `close`）は reject。標準の WebSocket は拒否の status を読めないので、テストは「つながらない」ことだけを確かめる

### 1-10. 生き資料の同期（`docs/architecture/README.md`）

「操作と通知の経路を分ける」に、この段で決めた次の 4 点を足す。全体図・表は変わらない。

- 接続は `?roomCode=&playerToken=` のクエリで本人を確かめる（ヘッダーを使わない理由と、AWS でも同じ形で渡せること）

- 通知は応答の前に送り終える。通知に失敗しても、保存が済んだ操作は成功のまま返す

`uc-02-join-room.integration.test.ts`（新しい `describe("WebSocket の通知")`。既存の describe の中の GET のテスト（1.7.1 の minor 指摘）は動かさない）:

## 5. リスク・注意点

- **規模が上限 15 を超える（24 件）。** 分割案: (a) 入口の段 = 契約・`webSocketEndpoint`・`startApi`・`startServer`・`connectWebSocket`・`apps/api/package.json`・`tests/package.json`・lock・`docs/architecture`（約 11 件）、(b) 通知の段 = port・use case と単体テスト・publisher・`createApp`・結合テスト 2・状態マーク 2・`scenarios.md`（約 13 件）。ただし (a) は受け入れ基準 ID を付けられる観測点を持てない（接続できる・`connected` が届くことは UC-02 要件 3 の一部で、要件 3 が（未実装）のうちは ID をテストに書けない。`check:trace`）。設計フェーズの「受け渡しだけなので結合テストまで束ねる」と同じ理由で、**割らずに進めることを推す**。増えた 10 件のうち 5 件はテスト・生成物・状態マークで、読む量は 14 件の見積もりと大きく変わらない
- **通知の追い越し**: ほぼ同時に 2 人が入ると、2 つの publisher の送信が並び、先に保存された方の写し（人数の少ない一覧）が後に届きうる。画面は最後に届いた写しを表示するので、一覧から 1 人欠けたまま止まる。ローカル 1 プロセスでも起こりうるが、間隔は数ミリ秒の競り合いに限る。対策は写しに改訂番号を載せて古い写しを捨てること（契約への追加で後方互換）だが、保存後の改訂番号を use case が知る口が repository に無く、この段では足さない（要確認〔設計〕）
- **トークンがクエリに乗る**: プロキシ・API Gateway のアクセスログに URL が残りうる。入口のログには path だけを出す。トークンは部屋限り・24 時間で、なりすませるのはその部屋のそのメンバーだけ。AWS のアクセスログの設定はデプロイの要求で扱う
- **受け入れ後に登録が失敗した接続**: DB の障害で `register` が失敗すると、開いたまま宛先に入らない接続が残る（`LocalWebSocketSender` に 1 接続だけを閉じる口が無い）。`connected` が届かないことで画面は異常に気づける。再接続の扱いは 1.12.1 で決める
- **応答の遅れ**: 参加と開始の応答は、接続表の Query と最大 8 接続への送信を待ってから返る。ローカルでは数ミリ秒〜十数ミリ秒の見込み
- **1 秒の判定と CI の負荷**: 結合テストは 1 秒の上限で待つ。負荷の高い機械で揺れたら、上限を緩めず原因（DB の起動直後など）を先に見る
- **`composeApp` の置き換え**: `startServer.ts` 以外の利用者は無い（`seedRoom.ts` は `readApiConfig` と `createDynamoDbClient` だけを使う）ことを確認済み
- **1.12.1 への引き継ぎ**: 画面は `connected` を受けてから待機室を出す。通知は `type` を問わず `room` を表示に使えばよく、`status` が `waiting` 以外ならゲーム画面へ（1.7.2 の約束）。接続の URL は API の HTTP のベースとは別に設定できるようにする（AWS では別の URL）
