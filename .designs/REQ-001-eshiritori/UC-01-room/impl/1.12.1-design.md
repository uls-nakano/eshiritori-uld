# 設計メモ: 1.12.1 ページの配線、API と WebSocket の呼び出し、プレイヤートークンの保存

> この段の範囲・観測点・束ね方は [tasks.md](../tasks.md) の 1.12.1 に従い、ここには写さない。受け入れ基準は [UC-02](../../../../docs/usecases/UC-02-招待された部屋に入る.md) 要件 1・10（と既に効いている UC-02 要件 3・5、[UC-03](../../../../docs/usecases/UC-03-ゲームを始める.md) 要件 2 の画面の側）に従う。画面と URL の対応は [mockups/room-design.html](../mockups/room-design.html) の「画面と URL」に従う。表示部品の口（props）は [1.10.1](1.10.1-design.md)・[1.11.1](1.11.1-design.md) のメモと実装、API と通知の形は `packages/api-contract/openapi.yaml`（[1.9.1](1.9.1-design.md) まで）に従う。ここに書くのは、それらに無い判断、確定した影響ファイル、テスト計画、リスク。

## 1. 実装方針

順序は トークンの保存（テスト → 実装）→ API の呼び出し（テスト → 実装）→ WebSocket の接続 → `RoomPage` の story（落ちることを確かめる）→ `RoomPage` → `TopPage` → `App` → `main.tsx`・`index.html` → 開発サーバーの中継（`vite.config.ts`）→ 生き資料。

domain・application・adapter・`apps/api`・API 契約・表示部品（`components/`）は変えない。ページは表示部品に値を渡し、API の応答と通知の写しをそのまま表示する。業務の判断（満員・重複・開始できるか・部屋コードの正規化）を再実装しない。`apps/web` は `api-contract` 以外の package を import しない（`check:boundaries` の既存の規則）。

### 1-1. ブラウザの外とのやりとりは、ページに引数で渡す

**ページは `fetch`・`WebSocket`・`localStorage`・`navigator.clipboard`・`history` に直接触らない。** 3 つの口（API の呼び出し・通知の接続・トークンの保存）とコピーの関数を `main.tsx` が組み立て、`App` を経てページに props で渡す。

- 理由: story をグローバルの差し替え（`fetch` の上書き、`WebSocket` の偽クラス、`localStorage` の事前書き込み）で書くと、jsdom のテストと実ブラウザの Storybook の両方で後片付けが要り、story 同士が汚し合う。props なら story は偽物を渡すだけで済み、偽の通知を任意の時点で流せる
- 捨てる性質: story は本物の `apiClient`・`roomSocket` を通らない。`apiClient` と `playerTokenStore` は隣の単体テストが、全体のつながりは 1.13.1 の E2E が持つ
- トークンの保存の偽物は、`createPlayerTokenStore` に記憶域の偽物（`Map` を包んだもの）を渡して作る。story でも本物の保存の規則（キーの組み立て）を通す

### 1-2. トークンの保存（`apps/web/src/storage/playerTokenStore.ts`、新規）

```ts
/** 部屋ごとに、このブラウザのプレイヤートークンを覚えておく口。 */
export interface PlayerTokenStore {
  /** その部屋のトークン。無ければ undefined。 */
  load(roomCode: string): string | undefined;
  save(roomCode: string, playerToken: string): void;
  remove(roomCode: string): void;
}
/** 記憶域（既定は localStorage）に、部屋コードごとのキーで保存する。 */
export function createPlayerTokenStore(
  storage: Pick<Storage, "getItem" | "setItem" | "removeItem">,
): PlayerTokenStore;
```

- **保存するのはトークンだけ。** `playerId` は `GET /rooms/{roomCode}` の応答が毎回返すので持たない（持つと、サーバーの値と食い違ったときにどちらを信じるかの判断が増える）
- **キーは `eshiritori.playerToken.<部屋コード>`。** 部屋コードはサーバーが返した `room.code`（正規化済み）で保存し、読むときは URL の部屋コードをそのまま使う（画面は正規化しない）。招待 URL は `WaitingRoom` が `room.code` で組み立てるので、通常の経路では一致する（リスクに記す）
- **`localStorage` が使えないとき（プライベートブラウズでの例外など）は、読めば `undefined`、書いても何もしない。** 例外をページに漏らさない。保存できないブラウザでは、開き直したときに参加画面が出る（UC-02 要件 10 は満たせないが、二重に加わることはサーバーのニックネームの重複で止まる）
- 部屋ごとにキーを分けるのは、別の部屋の招待 URL を開いたときに前の部屋のトークンを送らないため。1 部屋 1 キーなので、期限切れの部屋のキーは残り続ける（リスクに記す）

### 1-3. API の呼び出し（`apps/web/src/api/apiClient.ts`、新規）

```ts
type ErrorCode = components["schemas"]["ErrorResponse"]["code"];
/** 呼び出しの結果。失敗は ErrorResponse.code（表示は describeFormError が決める）。 */
export type ApiResult<T> = { ok: true; value: T } | { ok: false; code: ErrorCode };
export interface ApiClient {
  createRoom(request: CreateRoomRequest): Promise<ApiResult<CreateRoomResponse>>;
  joinRoom(roomCode: string, request: JoinRoomRequest): Promise<ApiResult<JoinRoomResponse>>;
  getRoom(roomCode: string, playerToken: string): Promise<ApiResult<GetRoomResponse>>;
  startGame(roomCode: string, playerToken: string): Promise<ApiResult<StartGameResponse>>;
}
/** baseUrl（例: 画面と同じオリジン）に向けて fetch で呼ぶ。 */
export function createApiClient(baseUrl: string, fetchFn: typeof fetch): ApiClient;
```

- 型はすべて `@eshiritori/api-contract` の生成型（`components["schemas"][...]`）。手書きの型を作らない
- path の部屋コードは `encodeURIComponent` して埋める（入力のまま送る。正規化はサーバー）。トークンは `Authorization: Bearer <トークン>`
- 応答の扱い: 2xx は本文を成功の値にする。2xx 以外は本文の `code` を失敗にする。本文が JSON でない・`code` が無いときは `server.internal_error`。`fetch` そのものが失敗した（通信できない）ときは `network.unreachable`（新しい名前。要確認〔名前〕）。どちらも `describeFormError` の想定外の文言になる
- **`joinRoom` は部屋コードが空文字なら呼ばずに `room.room_not_found` を返す。** 空の path は `/rooms//members` になり、契約に無い 404（本文が JSON でない）が返って「想定外の誤り」になるため（1.10.1 からの引き継ぎ）。空白だけの部屋コードは送る（空白の除去はサーバーの正規化）。判断を API の呼び出しに置くのは、単体テストで確かめられる場所にするため（要確認〔設計〕）
- 応答の本文の形は検査しない（契約の生成型として受ける）。サーバーと画面は同じ契約から型を作っており、形の食い違いは型と結合テストで止まる

### 1-4. 通知の接続（`apps/web/src/api/roomSocket.ts`、新規）

```ts
export type RoomNotification = components["schemas"]["RoomNotification"];
/** 開いた接続。ページを離れるときに閉じる。 */
export interface RoomSocket { close(): void; }
/** 部屋の通知を受ける接続を開く口。ページはこの型だけを知る。 */
export type ConnectRoomSocket = (params: {
  roomCode: string;
  playerToken: string;
  onNotification: (notification: RoomNotification) => void;
}) => RoomSocket;
/** socketUrl（例: ws://localhost:5173/ws）にブラウザ標準の WebSocket で接続する口を作る。 */
export function createRoomSocketConnector(socketUrl: string): ConnectRoomSocket;
```

- URL は `socketUrl` に `roomCode`・`playerToken` のクエリを `URLSearchParams` で付ける（契約の `GET /ws?roomCode=&playerToken=`）
- 受けたメッセージは `JSON.parse` して `RoomNotification` として `onNotification` に渡す。JSON でないメッセージは捨てる（例外をページに漏らさない）
- **接続の URL は API の URL と別に受ける。** AWS では WebSocket が別の URL になる（1.9.1 からの引き継ぎ）。この段では `main.tsx` が両方とも画面と同じオリジンから作る（`http(s)` を `ws(s)` に替えて `/ws`）
- **切れた接続はつなぎ直さない。** 切断からの復帰は後続の「接続が切れて戻る」の範囲（[docs/architecture](../../../../docs/architecture/README.md) の「プレイヤーの識別」）。開き直せば待機室に戻る（UC-02 要件 10 の経路）
- 単体テストは置かない。ブラウザの `WebSocket` を包むだけで、判断は URL の組み立てと JSON の読み取りに限られる。ページの story は偽物を渡し、本物の経路は 1.13.1 の E2E が通る（理由を PR に書く。[rules/testing](../../../../rules/testing/standard.md) の「テスト配置ルール」）

### 1-5. 部屋のページ（`apps/web/src/pages/RoomPage.tsx`、新規）

```ts
export interface RoomPageProps {
  /** URL の /r/{部屋コード} の部屋コード（入力のまま）。 */
  roomCode: string;
  api: ApiClient;
  tokenStore: PlayerTokenStore;
  connectSocket: ConnectRoomSocket;
  /** 招待 URL を組み立てるオリジン（WaitingRoom に渡す）。 */
  appOrigin: string;
  /** 招待 URL をコピーする。失敗は reject で返し、ページが無視する。 */
  copyText: (text: string) => Promise<void>;
}
```

ページの状態は 4 つ。最初の状態は描画の前に `tokenStore.load(roomCode)` で決める（トークンが無ければ最初の描画から参加画面）。

| 状態 | 表示 | 移る先 |
| --- | --- | --- |
| 読み込み中（トークンあり、`getRoom` の応答待ち） | 「読み込み中…」 | 成功 → メンバー。`room.room_not_found` → トークンを消して参加画面（誤り `room.room_not_found` 付き）。`room.not_member` → トークンを消して参加画面（誤りなし）。それ以外 → 読み込めない |
| 参加画面 | `JoinRoomForm`（`invitedRoomCode` に URL の部屋コード） | `joinRoom` 成功 → トークンを `room.code` で保存してメンバー。失敗 → 誤りを `errorCode` に渡して留まる |
| メンバー | `room.status` が `waiting` なら `WaitingRoom`、それ以外は `DrawingOrderView` | — |
| 読み込めない | `describeFormError` の想定外の文言（`role="alert"`）だけ。参加画面は出さない | 再読み込みでやり直す |

- **UC-02 要件 10 の判断はここ。** トークンがあれば参加画面を出さず、`getRoom` で同じメンバーとして待機室を出す。通信の失敗（`network.unreachable` など）で参加画面に落とすと、メンバーなのに別人として入り直せてしまうので、「読み込めない」で止める
- **期限切れ・部屋が無いとき（UC-02 要件 5）は、参加画面に「部屋が見つかりません」を出す。** 招待 URL の参加画面と同じ表示（`JoinRoomForm` は `invitedRoomCode` があるとき `room.room_not_found` をボタンの上に出す）。トークンを保存していないブラウザでは、入るを押したときに同じ表示になる
- **メンバーになったら通知の接続を開く。** `useEffect` で `connectSocket` を呼び、片付けで `close` する（StrictMode の二重実行でも接続が 1 本に戻る）。通知は `type` を問わず `room` で写しを置き換える（最後に届いた写しを表示）。`member_joined` を受けたら `startErrorCode` を消す（人数が変わり、「2 人以上で始められます」が古くなるため）
- **待機室は `getRoom` の応答で出し、`connected` を待たない。** 1.9.1 は「`connected` を受けてから待機室を出す」と引き継いだが、サーバーは登録の後に読み直した写しを `connected` で送るので、先に出しても取りこぼしは無い。`connected` を待つと、WebSocket がつながらない環境では待機室すら出なくなる（要確認〔設計〕）
- `viewerPlayerId` は `getRoom` の `playerId`、または `joinRoom` の `player.playerId`
- 開始: `startGame(roomCode, token)`。押した時点で `startErrorCode` を消し `starting` にする。成功の写しで置き換える（`started` なので `DrawingOrderView` に切り替わる。`game_started` の通知も同じ写しで届く）。失敗は `startErrorCode`
- 参加の送信: 送る前に `errorCode` を消し `submitting` にする。部屋コードは `JoinRoomForm` が渡す値（= URL の部屋コード）
- コピー: `copyText(url)` の失敗は無視する。招待 URL は画面に文字で出ているので手で写せる。「コピーしました」の表示は仕様に無いので作らない（要確認〔仕様〕）
- 参加画面の見出しは `JoinRoomForm` の「部屋に入る」をそのまま使い、ページで見出しを足さない（見た目の正の「参加画面」は画面の呼び名で、画面上の文言ではない）
- メンバー以外の状態で `connectSocket` を呼ばない（トークンが確かめられる前に接続しない）

### 1-6. トップのページ（`apps/web/src/pages/TopPage.tsx`、新規）

```ts
export interface TopPageProps {
  api: ApiClient;
  tokenStore: PlayerTokenStore;
  /** 部屋に入った（作った）後、その部屋の URL へ移る。 */
  onEnterRoom: (roomCode: string) => void;
}
```

- `CreateRoomForm` と `JoinRoomForm`（`invitedRoomCode` なし）を並べる。誤りと送信中はフォームごとに持つ
- どちらも成功したら、応答の `room.code` でトークンを保存し、`onEnterRoom(room.code)` で `/r/{room.code}` へ移る。移った先の `RoomPage` が保存したトークンで `getRoom` を呼んで待機室を出す（応答の写しをページ間で受け渡す口を作らない。1 回の読み直しで済み、開き直しと同じ経路を通る）
- 部屋コードを小文字で入れても、移る先はサーバーが正規化した `room.code` の URL になる

### 1-7. URL の切り替え（`apps/web/src/App.tsx`、新規）

- `location.pathname` が `/r/<部屋コード>`（末尾の `/` は許す）なら `RoomPage`（部屋コードは `decodeURIComponent`）、それ以外はすべて `TopPage`。`/r/` の形は `WaitingRoom` の招待 URL の組み立て（`new URL(`/r/${code}`, appOrigin)`）と揃える。読み取りは `App.tsx` 内の関数 1 つにまとめる
- 移るときは `history.pushState` して表示の状態を更新する。`popstate` を受けて戻る・進むに追従する
- `RoomPage` には `key={roomCode}` を付け、別の部屋へ移ったときに状態を作り直す
- 共通の見出し「絵しりとり」を `h1` で出す。ルーターのライブラリは使わない（画面は 2 つの URL だけ）
- `App` は `main.tsx` が作った口（`api`・`tokenStore`・`connectSocket`・`copyText`・`appOrigin`）を受けて下へ渡すだけ

### 1-8. 入口（`apps/web/src/main.tsx`、`apps/web/index.html`、新規）

- `main.tsx`: `createApiClient(location.origin, fetch.bind(globalThis))`、`createRoomSocketConnector(<origin の http(s) を ws(s) に替えた /ws>)`、`createPlayerTokenStore(localStorage)`（`localStorage` の参照そのものが例外になる環境では、何も覚えない記憶域に寄せる）、`copyText` は `navigator.clipboard.writeText` を `async` 関数で包む（安全でないオリジンでは `navigator.clipboard` が無く、同期の例外にしないため）。`createRoot(document.getElementById("root"))` に `<StrictMode><App … /></StrictMode>` を描く。`#root` が無ければ例外で止める
- `index.html`: `lang="ja"`、`<meta name="viewport" content="width=device-width, initial-scale=1">`、`<title>絵しりとり</title>`、`<div id="root">`、`<script type="module" src="/src/main.tsx">`。全体のスタイルは `<style>` に最小限（本文の最大幅とフォントの大きさ）だけ置き、CSS ファイルは作らない

### 1-9. 開発サーバーの中継（`apps/web/vite.config.ts`、変更）

- **画面は API と WebSocket を同じオリジンへ要求し、Vite の開発サーバーが `apps/api` へ中継する。** `server.proxy` に `/rooms`（HTTP）と `/ws`（`ws: true`）を足し、向き先は `http://localhost:3000`（`apps/api` の既定のポート）。環境変数 `API_ORIGIN` があればそれを使う（1.13.1 の E2E が開発サーバーと別のポートで API を立てるため）
- 捨てた案: 画面が API の URL（`VITE_API_ORIGIN` など）を直接呼び、`apps/api` に CORS を足す。`apps/api` の変更と、画面とサーバーの両方に設定項目が増える。同じオリジンにしておけば AWS でも CloudFront の振り分けで同じ形にでき、別の URL にする場合も `main.tsx` の 2 つの URL の作り方を替えるだけで済む（要確認〔設計〕）
- Vite は SPA の履歴の戻し（知らない path に `index.html` を返す）を既定で持つので、`/r/K7Q2XM` を直接開ける。`/rooms` の中継は `/r/` と前方一致しない
- `test` の設定（jsdom・`src/**/*.test.ts`）は変えない。新しい単体テスト 2 つも `npm run test:stories` で走る

## 5. リスク・注意点

- **`check:trace` の状態マーク。** UC-02 要件 1・10 の ID を story に書く変更と「（未実装）」を外す変更は同じ段で入れる。E2E-01-01 の ID はどこにも書かない（1.13.1）
- **story の中の状態の更新と `act`。** 偽の通知を play 関数から流すと、React の状態の更新が `act` の外で起きて警告が出ることがある。期待は `findBy…` / `waitFor` で待つ。警告で落ちる設定ではないが、出るなら通知を流す処理を `act` で包む
- **jsdom の `history` と `location`。** `RoomPage` の story は URL を読まない（部屋コードは props）。URL の読み取りは `App.tsx` にだけあり、story を持たないので、`/r/` の形の誤りは手の確認と 1.13.1 の E2E で見つかる
- **小文字の部屋コードの URL。** 手で `/r/k7q2xm` を開くと、`K7Q2XM` で保存したトークンが見つからず参加画面が出る。同じニックネームで入ればサーバーの重複で止まるが、別のニックネームなら別のメンバーとして加われる。招待 URL は常に `room.code`（大文字）で組み立てられるので通常の経路では起きない。画面で大文字にすると正規化の再実装になるので、この段では扱わない
- **`localStorage` に期限切れの部屋のキーが残る。** トークンは 24 時間で無効になるが、キーは消さない（開き直して `room.room_not_found` か `room.not_member` が返ったときだけ消す）。1 部屋 1 キーで数十バイトなので、遊んだ回数ぶん増えても問題にならない
- **StrictMode の二重実行。** 開発時は `useEffect` が 2 回走り、`getRoom` が 2 回、WebSocket が開いて閉じてまた開く。片付けで `close` を必ず呼ぶ。`getRoom` の応答が片付けの後に届いたときに状態を更新しないよう、効果の中で打ち切りの印を持つ
- **WebSocket がつながらなくても待機室は出る。** 1-5 のとおり `connected` を待たないので、中継の設定漏れなどでつながらないと一覧が更新されないまま気づきにくい。手の確認で、2 つ目のブラウザが入ったときに 1 つ目の一覧が変わることを必ず見る
- **古い写しが後から届く件（1.9.1 で先送り）。** ページは最後に届いた写しを表示するので、追い越しが起きると一覧から 1 人欠けたまま止まりうる。この段では扱わない
- **開発サーバーの中継と AWS。** AWS では画面（CloudFront）と API・WebSocket（API Gateway）の振り分けをデプロイの要求で決める。同じオリジンにできない場合は `main.tsx` の URL の作り方だけを替える
- **knip の入口。** `index.html` から `src/main.tsx` を拾えないと、`main.tsx`・`App.tsx`・ページ・口が「使われていないファイル」と出る。出たら `package.json` の knip の設定に `apps/web` 専用の `entry: ["src/main.tsx"]` を足す（`apps/*` の共通設定には足さない。`apps/api` に無いファイルを指すため）
- **1.13.1 への引き継ぎ:** (1) 画面の起動のコマンド（`apps/web` の `start`、ルートの `start:web`、`vite` の devDependency、`CLAUDE.md` / `AGENTS.md` の「構成」）はこの段に無い、(2) 中継の向き先は `API_ORIGIN` で替えられる、(3) 待機室は `getRoom` の応答で出るので、E2E が「待機室が出た」を確かめた時点では通知の接続がまだ登録されていないことがある（その間に入ったメンバーも `connected` の写しに含まれるので、一覧の期待は `expect(...).toHaveText` の自動の待ちで書く）

## 実装の記録

- 設計どおりに実装した。`package.json` の knip 設定は変更不要（`index.html` から `src/main.tsx` が入口として拾われた）。
- 逸脱（軽微）: `ApiClient` の各操作をメソッド記法でなく関数型のプロパティで宣言した。story が `args.api.getRoom` を `expect` に渡すとき `@typescript-eslint/unbound-method` に引っかかるため。呼び出し側の使い方は変わらない。
- 逸脱（軽微）: story「ページを離れると接続を閉じる」は、play から描画を外す手段が無いため置かなかった（設計に「省き、リスクに残す」とある）。接続の `close` は effect の片付けで呼ぶ。
- `RoomSocket` は `roomSocket.ts` の外から使われないため export しない（knip）。
- 逸脱（軽微）: 通知は JSON.parse に加えて isRoomNotification で形を確かめ、違う形のメッセージは捨てる（rules/development の外部入力の型ガード）。
- 成功応答の本文は検査せず型変換する。理由はコードのコメントに残した。エラー本文の `code` は `unknown` から typeof で絞る。
