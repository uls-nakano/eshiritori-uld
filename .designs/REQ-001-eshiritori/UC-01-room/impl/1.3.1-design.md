## 1. 実装方針

### 1-1. 乱数の源（`src/domain/random/RandomSource.ts`）

- `export interface RandomSource { nextInt(bound: number): number }` だけを置く。JSDoc に契約を書く: `bound` は 1 以上の整数、戻り値は 0 以上 `bound` 未満の整数。契約を守るのは実装（1.5.1 の `CryptoRandomSource`）の責務で、ドメインは戻り値を検査しない（検査の分岐はテストで到達できず、domain のカバレッジ 100% と両立しないため）
- 実装クラス・テスト用の実装はこの段では作らない（下の 4. のとおり、テストの決まった値の源は各テストファイルの中に置く）

### 1-2. 生成の組み立て（3 つの識別子に共通）

- `generate(random)` は「文字の並び（非公開の定数）から `random.nextInt(並びの長さ)` で 1 文字ずつ選ぶ」を、決めた文字数だけ繰り返して連結する。添字の読み出しは `ALPHABET.charAt(index)`（`noUncheckedIndexedAccess` で `ALPHABET[index]` は `string | undefined` になるため）
- 組み立ての関数は各ファイルの非公開の関数にし、共通のファイルに切り出さない。`src/domain/` の非テストファイルは 1 つずつモデル図のクラスと突き合わせられ（`check:model-trace` の「図に無いクラス」）、図に無いヘルパーのファイルは置けないため。重複は 3 行程度
- 文字の並びと文字数:

| 値 | 文字の並び | 文字数 | 組み合わせ | 根拠 |
| --- | --- | --- | --- | --- |
| `RoomCode` | `A`〜`Z` と `0`〜`9`（36 文字、この順） | 6 | 36^6 ≈ 21.8 億 | UC-01 要件 2「英数字 6 文字」、モデル docs「約 21 億通り」、モックアップの `K7Q2XM`（大文字）。紛らわしい文字（`0` と `O` など）は除かない。除くと docs の通り数が変わるため |
| `PlayerId` | base64url の 64 文字（`A`〜`Z`、`a`〜`z`、`0`〜`9`、`-`、`_`、この順） | 12 | 2^72 | 部屋の中（最大 8 人）で重ならなければよい。URL・JSON・DOM の key にそのまま置ける文字に限る |
| `PlayerToken` | 同上 | 32 | 2^192 | 推測されない秘密の値（docs/architecture の「プレイヤーの識別」）。一般的な目安の 128 ビットを十分に超える。ヘッダーにも保存にもそのまま置ける文字に限る |

### 1-3. `RoomCode`（`src/domain/room/RoomCode.ts`）

- `static generate(random: RandomSource): RoomCode` — 1-2 のとおり
- `static create(value: string): Result<RoomCode, RoomError>` — 入力された部屋コードを、次の順でそろえてから検証する
  1. `value.normalize("NFKC")` で全角英数字を半角にする（`Ｋ７Ｑ２ＸＭ` → `K7Q2XM`）
  2. `trim()` で前後の空白を除く
  3. `/^[0-9A-Za-z]{6}$/` に合わなければ `failure(new RoomError("room_not_found", "Room code must be 6 alphanumeric characters."))`。書式誤りを `room_not_found` にまとめるのは 1.2.1 の決定どおり
  4. `toUpperCase()` で大文字にそろえて `success(new RoomCode(...))`
  - **大文字化は検証の後に行う。** 先に大文字化すると `ß` が `SS` になるなど、英字でない文字が英字に化けて書式を通るため
  - 大文字小文字・全角半角・前後の空白をそろえるのは、部屋コードを口頭やチャットで伝えて手で入れる（UC-02）ため。生成は大文字だけなので、小文字の部屋は存在しない（要確認〔仕様〕）
- `get value(): string`（招待 URL を組む DTO と保存の mapper が使う。図には描かない）
- `equals(other: RoomCode): boolean`

### 1-4. `PlayerId`（`src/domain/room/PlayerId.ts`）

- `static generate(random: RandomSource): PlayerId` — 1-2 のとおり
- `static create(value: string): PlayerId` — **書式を検証せず、渡された値で復元する。Result を返さない。** 呼ぶのは保存の mapper（1.5.1）だけで、利用者の入力から作る場面がこのスライスに無い。図の `create(value) PlayerId$` とそのまま一致する（要確認〔設計〕）
- `get value(): string`（メンバー一覧の DTO と mapper が使う）
- `equals(other: PlayerId): boolean`

### 1-5. `PlayerToken`（`src/domain/room/PlayerToken.ts`）

- `static generate(random: RandomSource): PlayerToken` — 1-2 のとおり
- `static create(value: string): PlayerToken` — **書式を検証せず、Result を返さない。** 要求から受け取ったトークン（開始の要求・待機室へ戻る）も mapper の復元もこれで作る。書式が誤ったトークンは、どのメンバーの `isHeldBy` にも一致しない「持ち主のいないトークン」として集約（1.4.1）が扱う。ここで書式を拒否すると、「メンバーでない人」の判断が use case の Result の分岐と集約の `findMember` の 2 か所に分かれ、どのエラーコードを返すか（`not_host` か、1.7.1 の待機室へ戻る失敗か）を use case が決めることになるため（要確認〔設計〕）
- `get value(): string`（部屋を作る・入るときにトークンを本人へ返す DTO と mapper が使う）
- `equals(other: PlayerToken): boolean` — **定数時間で比べる。** モジュール直下の非公開の関数 `equalsInConstantTime(a, b)` に置く
  - 長さが違えば即 `false`（漏れるのは長さだけで、生成するトークンの長さ 32 は秘密ではない）
  - 長さが同じなら全文字の `charCodeAt` の排他的論理和を `|=` で積み、途中で抜けない。最後に 0 かを返す
  - `node:crypto` の `timingSafeEqual` は使わない。domain は実行環境の I/O 系モジュールに依存させない（`domain-is-pure` は npm の依存だけを見るが、rules/architecture の「Domain から外部ライブラリに依存しない」に寄せる。room の domain を Node 以外で動かす余地も残る）

### 1-6. `Revision`（`src/domain/room/Revision.ts`）

- 実値は保存された回数（`number`）
- `static initial(): Revision` — 0（まだ一度も保存されていない）
- `static restore(value: number): Revision` — 保存先から読んだ値で復元する。**1 以上の整数だけを受け付ける。** 保存された部屋は少なくとも 1 回保存されている（「改訂番号 = 保存された回数」）ため。0 を復元できると、保存済みの部屋が `isInitial` になり、保存の条件が「作るだけ」になって必ず衝突し、use case が部屋コードを作り直し続ける
  - 外れた値（0・負・小数・`NaN`）は**throw する**（`RangeError`、detail は英語 `Revision must be a positive integer.`）。直前に `getLogger().error("復元する改訂番号が 1 以上の整数ではありません", { value })` を出す（rules/development の「throw する直前に原因の入力値を logger に出す」）。利用者の操作で起きる失敗ではなく保存データの破損で、use case が分岐して応答に変える対象ではないため Result にしない。`RoomErrorCode` にも足さない（要確認〔設計〕）
- `next(): Revision` — 1 つ進めた新しい値を返す（自身は変えない）
- `isInitial(): boolean` — 0 か
- `get value(): number`（mapper が保存の条件と次の値を書くのに使う）
- `equals(other: Revision): boolean`

### 1-7. 公開入口（`src/index.ts`）は変えない

- tasks.md は `index.ts` を変更ファイルに挙げているが、この段で公開するものは無い。値オブジェクトを公開しない 1.2.1 の方針を `RandomSource` にも当てはめる。`RandomSource` を外から実装するのは room の中の adapter（1.5.1 の `adapters/random/CryptoRandomSource`）で、composition root（1.6.1）が受け取るのはその実装クラスのため、公開が要るなら 1.5.1 か 1.6.1 で足す（要確認〔予定外〕）

## 5. リスク・注意点

- **大文字化の順序。** `toUpperCase` は英字以外も変える（`ß` → `SS`、`ı` → `I`）。検証を大文字化の後にすると英字でない入力が書式を通る。1-3 の順（NFKC → trim → 検証 → 大文字化）を崩さない。NFKC は丸数字や合字（`①` → `1`、`ﬀ` → `ff`）も変えるが、変えた結果が 6 文字の英数字になっても、存在する部屋に当たるかどうかで判断されるだけで害はない
- **定数時間の比較は最善の努力。** JS の JIT が排他的論理和の積み上げを短絡させない保証は無く、テストでも時間差は検証できない。比べる前に長さが違えば抜ける点は、トークンの長さが固定で公開されているため許容する。トークンの値をログ・エラーの detail に出さないこと（後続の use case と mapper への注意。`get value()` があるため）
- **乱数の源の契約違反を検査しない。** 実装が範囲外の値を返すと `charAt` が空文字を返し、短い部屋コードが黙って作られる。契約は 1.5.1 の `CryptoRandomSource` のテスト（返す値が 0 以上 `bound` 未満の整数であること）で守る。1.5.1 に引き継ぐ
- **1.4.1 の `fixtures/roomFixtures.ts` は `check:model-trace` の「図に無いクラス」に当たる見込み。** `listDomainSourceFiles` は `.test.ts` 以外の `src/domain/` 下の `.ts` をすべてモデル図のクラスと突き合わせ、`fixtures/` を除外しない（カバレッジの設定は除外しているが、model-trace の script は kit 所有で直接編集できない）。1.4.1 では、決まった値の乱数の源と fixture をテストファイルの中に置くか、`src/domain/` の外に置くかを決める必要がある。この段が各テストファイルに `fixedRandom` を置くのは同じ理由
- **識別子の重なり。** `PlayerId` は部屋の中で重ならない前提で、重なりの検査はしない（8 人で 2^72 の空間に重なる確率は実用上 0）。`RoomCode` の重なりは保存の条件（1.5.1）と作り直し（1.6.1）が扱う
- **`Revision` の上限。** `next()` は `Number.MAX_SAFE_INTEGER` を超えると精度を失うが、部屋は 24 時間で期限切れになり到達しない。検査しない
- **`PlayerToken.create` が何でも受け付ける。** 極端に長い文字列でも VO にはなる。`equals` は長さが違えば即座に抜けるので比較の手間は増えない。要求の大きさの上限は API の入口（1.6.1 以降）が持つ
