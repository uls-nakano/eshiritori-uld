# レビュー指摘のルール還元

## Overview

人のレビュー指摘を使い捨てにせず、ルールへ還元します。**「レビュー指摘が減る」という KPI の因果を「ルールが蓄積されるから」に置く**ための仕組みです。

振り分けの基準そのものは `rules/review` の「指摘のルール還元」にあります。このスキルはその手順を実行します。

## 入力

- **レビュー指摘**: 人のレビューコメント、PR コメント、会話中の指摘のいずれか
- **対象の変更**: どの変更に対する指摘か（ブランチ・PR・タスク ID のいずれか）

## 手順

### 1. 指摘の棚卸し

指摘を 1 件ずつ列挙します。1 つのコメントに複数の論点が含まれる場合は分けます。**修正を求める指摘だけ**を対象とし、称賛・質問・情報共有は対象外です。

### 2. 振り分け

各指摘を 3 つのいずれかに振り分けます。**この振り分けを怠るとルールが無限に肥大し、AI レビューが遅く・ブレるようになります。**

| 振り分け | 条件 | 還元先 |
| --- | --- | --- |
| **機械化できる** | 違反を決定的に判定できる（構文・配置・命名パターン・依存方向・ファイルの有無など） | lint ルール、またはリポジトリの `scripts/` の機械チェック（標準の規則なら uld-kit の `uld` CLI） |
| **機械化できない** | 判断に文脈や設計意図が要る | 該当トピックの `rules/<topic>/project.md` |
| **一般化しない** | この変更に固有で、次に同じ状況が来ない | 還元しない。理由を記録に残す |

**機械化を優先します。** 推論に頼るのは機械化できないところだけにする、が原則です（「機械にできることは機械に」）。「ルールに書けば AI が守る」は最後の手段です。

### 3. 反映

#### 機械化できる指摘

1. lint ルールで表現できるなら `eslint.config.mjs` に追加する
2. できないなら `scripts/` にチェックスクリプトを追加し、`package.json` の `check` に組み込む。違反が標準（`standard.md`）の規則なら、チェックは uld-kit の `scripts/` に足して `uld` CLI の command にし、全プロジェクトへ配布する（プロジェクト側で書いたものを後から昇格させてもよい）
3. **チェックが実際に違反を検出することを確認する**。違反を仕込んで落ちることと、直して通ることの両方を確かめる

#### 機械化できない指摘

1. 指摘の内容から該当トピックを決める（`rules/README.md` のトピック一覧）
2. `rules/<topic>/project.md` の適切なセクションに追記する
3. **なぜそうするかを書く。** ルールは What だけでなく Why を伴わないと、状況が変わったときに外せなくなる
4. 同じフォルダに `standard.md` があり、その記述と矛盾する場合は「理由つき上書き」として明示宣言する。**宣言なしに矛盾した記述を置かない**

追記する前に、既に同じ趣旨のルールが無いかを確認します。重複はルールの肥大そのものです。

### 4. 記録

`.designs/REQ-xxx/UC-yy/reviews/` に、テンプレート `rules/design-records/templates/review.md` の形式で記録します。採番に紐づかない指摘の場合は、対象が分かる場所に記録するかをユーザーに確認します。

記録するのは、指摘の内容・振り分け・還元先・反映したかどうかです。

### 5. 適用タイミングの確認

**還元したルールは走行中のループには効かせません。次のループから適用します。** 走行中に前提が変わると、それまでの検証・承認の前提が崩れ、再現性と計測が濁るためです。

いま動いているループがある場合は、その完了を待ってから還元する（または還元したが次から適用する旨を明示する）ことをユーザーに伝えます。

### 6. 報告

- 指摘ごとの振り分けと還元先
- 追加・変更した機械チェックと、それが動作することの確認結果
- `rules/` に追記した内容
- 還元しなかった指摘とその理由

## 注意事項

- **還元先は常に `project.md`。** `standard.md`（配布される標準）へは自動で入れません。複数プロジェクトで同じルールが繰り返し採取されたとき、標準のメンテナーが明示的に取り込みます。一つのプロジェクトの偶然を標準に混ぜないためです
- ルールを追記したら、そのトピックの `project.md` が読み切れる長さに保たれているかを確認する。肥大していたら、機械化できる項目が残っていないかを見直す
- 指摘の内容がルールではなく設計やドキュメントの問題を指している場合は、無理にルール化せず、該当する成果物の修正として扱う
